<objective>
Build F10's admin-facing registry/governance surface: API client management (with one-time-only secret issuance), the record-authority registry, and policy-enforced revocable federation grants. These three endpoints implement three of F10's "four non-negotiable integration behaviors" (record authority, controlled federation, plus the credential layer underneath provenance enforcement).

Purpose: Success criterion 4 ("protected by OAuth2/OIDC bearer tokens... consumable by a registered webhook subscriber") needs API clients to exist as a concept; "policy-enforced revocable federation" is this plan's `federation_grants` endpoints with immediate-effect revocation, mirroring 01-03's immediate-suspend pattern at the federation layer instead of the user layer.
Output: `integration-gateway` module's registry endpoints, mounted independently of `auth-org`'s routes (separate module per TechArch's component boundaries), protected by the same `requirePermission` middleware.
</objective>

- Export a helper `async function checkRecordAuthority(recordType: string): Promise<string>` returning `authoritative_system` for a given type (defaulting to `'EPMP'` if no row exists) — this is the function any Phase 2+ integration write-path will call before persisting an externally-sourced change; Phase 1 has no such write-path yet (F11-F17 are out of scope), but this plan ships the registry + lookup function as the governance surface F13/F15/F16/F17 will depend on later. Document inline that `409 RECORD_AUTHORITY_CONFLICT` enforcement itself happens at the call site in those future modules — this plan provides the registry and lookup, not a consuming write path (none exists in Phase 1 scope).

Create `backend/src/modules/integration-gateway/opa-federation-policy.ts`: `async function syncFederationGrantsToOpa(): Promise<void>` — queries all `federation_grants` where `status='Active' AND (expires_at IS NULL OR expires_at > now())`, `PUT {OPA_URL}/v1/data/federation_grants` with the current active set. Called after every grant create/revoke, synchronously before the HTTP response — same "no caching window" pattern as 01-07's role-permission resync.

Create `backend/src/modules/integration-gateway/federation-grants.ts`:
- `GET /api/v1/admin/federation-grants` (`view`) — returns `FederationGrant[]`.
- `POST /api/v1/admin/federation-grants` (`create`) — body `{partner_jurisdiction_id, scope: {record_types: string[], incident_filters?}, expires_at?}`. **Server-side validation BEFORE the INSERT** (don't rely solely on the DB's `chk_scope_not_empty` constraint — return a clean `400` with a specific message, not a raw constraint-violation error): reject if `scope.record_types` is missing or empty array with a clear validation error. On success: `INSERT`, `AuditService.record(..., 'federation_grant_create', ...)`, then `await syncFederationGrantsToOpa()` before responding.
- `POST /api/v1/admin/federation-grants/{id}/revoke` (`edit`) — `UPDATE federation_grants SET status='Revoked', revoked_at=now() WHERE id=$1`; `AuditService.record(..., 'federation_grant_revoke', ...)`; `await syncFederationGrantsToOpa()` **before** responding `204` — this ordering is what makes revocation take effect "within the same request cycle": by the time the client receives the 204, OPA's data is already updated, so the very next request evaluated against OPA sees the revoked state.
  </action>
