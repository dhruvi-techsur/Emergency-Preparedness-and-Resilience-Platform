Create `backend/src/modules/auth-org/admin-users.ts`, all routes `preHandler: requirePermission('admin', <action>)`:
- `GET /api/v1/admin/users` (`action='view'`) — query params `role`, `jurisdiction`, `status`, `page` (default 1, page_size 25); returns `{items: [{id,name,email,role,jurisdiction_scope,status,last_login_at}], total, page, page_size}` per TechArch's `ListResponse<AdminUserSummary>` shape, joining `roles.name` for the `role` field.
- `POST /api/v1/admin/users` (`action='create'`) — body `{email, name, role_id, jurisdiction_scope}`; `INSERT INTO users (...)`; `AuditService.record(req.epmpUser.id, 'user_create', 'users', newUser.id, {email, role_id})`; returns the created `AdminUserSummary`.
- `PATCH /api/v1/admin/users/{id}` (`action='edit'`) — body `{role_id?, jurisdiction_scope?, status?}`. Before updating, `SELECT` the current row for the before-snapshot. `UPDATE users SET ... WHERE id=$1 RETURNING *`. `AuditService.record(req.epmpUser.id, status change ? 'user_suspend'/'user_reactivate' : 'user_edit', 'users', id, {before: {...}, after: {...}})` — detail MUST carry both snapshots, not just "status changed" (FRD Validation: "logged with the before/after... not just 'permissions changed'" — same principle applies here). No explicit session-revocation call is needed beyond this write: 01-03's `requirePermission` re-queries `users.status` on every request, so suspension takes effect on the suspended user's very next request with no separate Keycloak admin-API call required in Phase 1's architecture (documented deviation from TechArch §5.1's "Keycloak admin API session-revocation call" — Phase 1 enforces this at the EPMP session layer since Keycloak is only the IdP broker for initial authentication, not the source of truth for subsequent request authorization).

Create `backend/src/modules/auth-org/admin-roles.ts`:
- `GET /api/v1/admin/roles` (`action='view'`) — returns `Role[]` with nested `permissions: [{feature, actions}]` per role (join `role_permissions`).
- `PATCH /api/v1/admin/roles/{id}` (`action='edit'`) — body `{permissions: [{feature, actions}]}`. Before-snapshot query, then for each `{feature,actions}` pair: `INSERT INTO role_permissions (role_id, feature, actions, updated_by) VALUES (...) ON CONFLICT (role_id, feature) DO UPDATE SET actions=EXCLUDED.actions, updated_by=EXCLUDED.updated_by, updated_at=now()`. After the DB write succeeds, call `syncRolePermissionsToOpa()` with the full current `role_permissions` table (re-sync all rows, not just the changed ones, to keep OPA's in-memory data consistent) — **do this synchronously, before responding**, so a client polling immediately after the PATCH sees the new permission enforced, satisfying "no caching window." `AuditService.record(req.epmpUser.id, 'role_permission_edit', 'roles', id, {before, after})`.
- Role deletion: no DELETE route exists in TechArch's spec for roles (seeded roles are fixed in Phase 1 — F8's "a role cannot be deleted while assigned" validation is satisfied structurally by **not exposing a delete endpoint at all** in this phase, since Phase 1 ships exactly 5 fixed persona roles with no UI/API to create or remove roles; document this as the Phase 1 scope boundary — full role CRUD beyond permission-editing is not in the FRD's Phase 1 screens either, S8.3 only shows "Editing a role's permissions opens a form," not role creation/deletion).
  </action>

Create `backend/src/modules/auth-org/admin-sso-config.ts`:
- `GET /api/v1/admin/sso-config` (`action='view'`) — returns the single active (or most recent) `sso_config` row shaped as the `SsoConfig` TypeScript interface.
- `POST /api/v1/admin/sso-config/test` (`action='edit'`) — body is a candidate config (not yet saved): `{protocol, idp_metadata_url?, idp_metadata_xml?}`. Attempts to fetch/parse the metadata (`fetch(idp_metadata_url)` for OIDC discovery document, or basic XML-well-formedness check for SAML2 metadata XML — Phase 1 scope: verify the URL is reachable and returns a parseable discovery document / well-formed XML; full SAML assertion validation is exercised at actual login time via 01-03's `handleSsoCallback`, not here). Returns `{success: boolean, details: string}`. Does NOT write to the database — this is explicitly a dry-run per F8's "no untested IdP config goes live" rule.
- `PATCH /api/v1/admin/sso-config` (`action='edit'`) — body `Partial<SsoConfig>`. **Server-side gate**: reject with `422 SSO_CONFIG_INVALID` unless the request includes `tested_at` set by a prior successful `/test` call within a short window (Phase 1 implementation: require the client to pass back the exact config it tested, and re-run the same reachability check server-side before activating — never trust a client-asserted "I tested it" claim; re-verify on the server at PATCH time, setting `tested_at = now()` only on success, `active = true` only when explicitly requested AND the re-verification passes). `AuditService.record(req.epmpUser.id, 'sso_config_change', 'sso_config', id, {before, after})`.

Create `backend/src/modules/auth-org/admin-audit.ts`:
- `GET /api/v1/admin/audit-log` (`action='view'`) — query params `date_range` (ISO start,end), `actor_id`, `action_type`, `record_type`; paginated (`page`, default `page_size=25`). Joins `users` for `actor.name`. Returns `ListResponse<AuditLogEntry>` exactly per TechArch's interface.
- **No PATCH or DELETE route is registered for this path anywhere in the codebase** — enforce this as a structural fact, not just an omission: add a catch-all Fastify route `fastify.patch('/api/v1/admin/audit-log', ...)` and `fastify.delete('/api/v1/admin/audit-log/:id', ...)` that explicitly return `403 AUDIT_LOG_IMMUTABLE` with the FRD's exact message, rather than falling through to a generic 404 — this makes the immutability contract visible in the API surface itself (an explicit rejection, not merely an absent route that could look like a bug).
