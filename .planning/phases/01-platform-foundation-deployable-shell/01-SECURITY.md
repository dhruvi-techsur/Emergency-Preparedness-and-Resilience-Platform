## Resolved findings

### T-01-25: light/dark `--ink-disabled` WCAG AA contrast failure

- **Status:** Fixed in 01-15, with a mid-wave correction during the code-review gate (fixer commits `580d0fc`, `3dc2164`, `a358c96`).
- **Prior finding:** At the prior audit's time (01-15 unexecuted), light theme's `--ink-disabled` (`#8794a0`) measured 3.10:1 against `--bg` and dark theme's (`#5d7284`) measured 3.63:1 — both below the 4.5:1 WCAG AA floor, consumed by `DatePicker.css`'s `.ep-datepicker__day--outside` rule on two reachable admin screens.
- **Fix applied:** `tokens.json`/`tokens.css` light theme `--ink-disabled` → `#6c7680` (4.62:1 vs `#ffffff`) in the first fix pass (`c13d438`), correct on first attempt. Dark theme's first fix attempt (`#6c8499`, verified only against `--bg`) was found by the wave-7 code-review gate (iteration 1, finding B1) to still fail (3.88:1) against the DatePicker popover's REAL background `--bg-raised` (`#12283a`), which the first attempt had not checked. Corrected in the review's own fix round to `#7c95aa` (`580d0fc`), verified against both `--bg` (5.81:1) and `--bg-raised` (4.85:1).
- **Verification:** This audit independently recomputed sRGB relative-luminance contrast for the CURRENT values against both `--bg` and the actual DatePicker popover render context `--bg-raised` (not trusted from either the original plan's verify block, which only checked `--bg`, or the review's own claim) — all three theme values pass 4.5:1 against every real consumer context. Confirmed `--ink-disabled` has exactly one consumer in the codebase (`DatePicker.css:150`), so no other background context remains unchecked.

### T-01-26 companion fix: `contrast-audit.spec.ts` never opened the DatePicker popover before scanning

- **Status:** Fixed in 01-15's review round (fixer commit `3dc2164`, plus `a358c96` for W1 coverage gap).
- **Prior finding:** The wave-7 code-review gate (iteration 1, same B1 finding, part 2) found the original Task 2 spec scanned `/admin/audit-log` without ever opening the DatePicker's popover — since `.ep-datepicker__day--outside` (the only element rendering `--ink-disabled`) is conditionally rendered only while the popover is open, the original spec could not have caught even the known-bad pre-fix value. Separately (W1), the spec only scanned `AuditLogView.tsx`, not `FederationGrants.tsx`, despite the plan naming both as DatePicker-mounting screens.
- **Fix applied:** `contrast-audit.spec.ts` now clicks the "Open calendar" `IconButton` and waits for `.ep-datepicker__popover` to become visible before each `/admin/audit-log` scan (all three themes), and adds a dedicated dark-theme-only scan of `/admin/federation-grants` after opening its "Grant access" modal and that DatePicker's popover.
- **Verification:** Read the current 140-line spec directly (not the plan's original description). Confirmed `contrast-audit.spec.ts:104-105` performs the click-and-wait-for-popover sequence before every audit-log scan, and `contrast-audit.spec.ts:121-137` adds the federation-grants dark-theme block. Confirmed via `DatePicker.tsx`/`IconButton.tsx` (per `01-REVIEW.md`'s own cross-file-seam check, independently spot-checked here) that `getByRole('button', { name: 'Open calendar' })` is an exact accessible-name match, not a guess. This construction would have caught the original pre-fix defect — axe-core resolves `.ep-datepicker__popover`'s own `background: var(--bg-raised)` (DatePicker.css:99) as the effective background for any descendant text-contrast check, so with the popover open and mounted, a failing token value would be flagged.
