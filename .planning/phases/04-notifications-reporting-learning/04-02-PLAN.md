```sql
CREATE TABLE sitreps (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  incident_id UUID NOT NULL REFERENCES incidents(id),
  status VARCHAR(20) NOT NULL DEFAULT 'Draft' CHECK (status IN ('Draft','Approved')),
  content JSONB NOT NULL,
  ai_origin BOOLEAN NOT NULL DEFAULT false,
  ai_draft_id UUID REFERENCES ai_drafts(id),
  approved_by UUID REFERENCES users(id),
  approved_at TIMESTAMPTZ,
  created_by UUID NOT NULL REFERENCES users(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT chk_sitrep_ai_approval CHECK (NOT (ai_origin AND status = 'Approved' AND approved_by IS NULL))
);

CREATE TABLE aars (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  incident_id UUID NOT NULL REFERENCES incidents(id) UNIQUE,
  timeline_export JSONB NOT NULL,
  decisions_log JSONB NOT NULL,
  resource_history JSONB NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'Draft' CHECK (status IN ('Draft','Finalized')),
  finalized_by UUID REFERENCES users(id),
  finalized_at TIMESTAMPTZ,
  created_by UUID NOT NULL REFERENCES users(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT chk_finalized_requires_signoff CHECK (status != 'Finalized' OR (finalized_by IS NOT NULL AND finalized_at IS NOT NULL))
);

CREATE TABLE aar_findings (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  aar_id UUID NOT NULL REFERENCES aars(id),
  finding_text TEXT NOT NULL,
  category VARCHAR(100),
  corrective_action TEXT,
  owner_id UUID REFERENCES users(id),
  due_date DATE,
  closure_status VARCHAR(20) NOT NULL DEFAULT 'Open' CHECK (closure_status IN ('Open','Closed')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT chk_corrective_action_owned CHECK (corrective_action IS NULL OR (owner_id IS NOT NULL AND due_date IS NOT NULL))
);

CREATE INDEX idx_sitreps_incident ON sitreps(incident_id);
CREATE INDEX idx_aar_findings_owner_open ON aar_findings(owner_id) WHERE closure_status = 'Open';
```

  1. `404 RECORD_NOT_FOUND` if incident doesn't exist.
  2. Auto-assemble `content` as a JSONB object with NO manual re-entry required: `{timeline: [...last N incident_timeline rows ordered occurred_at DESC...], task_status_counts: {Open: n, 'In progress': n, ...} (GROUP BY status FROM tasks WHERE incident_id=$1), resource_request_status_counts: {Draft: n, ...} (GROUP BY status FROM resource_requests WHERE incident_id=$1), narrative: ''}`. Document inline: tasks/resource_requests tables are 03-01/03-04's — this module reads them read-only via plain SELECT, never writes, consistent with TechArch's module-boundary rule that `comms-reporting` has no owned FK into `incident-ops`'s tables, only read access.

  4. `INSERT INTO sitreps (incident_id, content, created_by) VALUES ($1, $2, $3) RETURNING *`. Return `201 Sitrep`.
  5. A separate `PATCH /api/v1/incidents/{id}/sitreps/{sitrepId}` (`action='edit'`) lets a user update `content.narrative` and/or finalize: body `{content?: {...}, finalize?: boolean}`. Create an addendum instead."); else `UPDATE sitreps SET status='Approved', approved_by=$1, approved_at=now(), content=$2 WHERE id=$3`. If NOT finalizing and the sitrep is already `Approved`, ALSO reject with `403 DOCUMENT_IMMUTABLE` (Draft SITREPs remain freely editable per FRD's "remains available throughout incident lifecycle" validation note; only Approved ones are immutable).

- `POST /api/v1/incidents/{id}/aar` (`action='create'`) — body `{findings: AarFinding[]}`.
  1. `404 RECORD_NOT_FOUND` if incident doesn't exist. `409 INCIDENT_NOT_CLOSED` if `incidents.status != 'Closed'` (FRD's exact message "Close this incident before generating its after-action report.") — checked BEFORE any write.
  2. Auto-assemble (per TechArch's AAR Inputs/Process): `timeline_export` = full `incident_timeline` rows for this incident as JSONB; `decisions_log` = the subset of `incident_timeline` rows whose `detail` JSONB contains a truthy `is_decision` key OR whose `title` matches a documented decision-marker convention (since no prior plan tags Timeline entries as decisions explicitly, document inline the exact heuristic used: entries from `activation.ts`/`command-roles.ts`/`closure.ts` — i.e. `source='EPMP'` entries with `tone` in `('warning','danger')` or titles matching `Activation changed to|assigned to|Incident closed` — are treated as decision-tagged; this is a Phase-4 documented approximation since Phase 1-3 never added a literal `is_decision` boolean column, and retrofitting one onto the append-only `incident_timeline` table is out of this plan's scope); `resource_history` = full `resource_requests` + `resource_request_status_history` rows for this incident as JSONB.
  3. Per the `aars.incident_id UNIQUE` constraint, use an upsert: `INSERT INTO aars (incident_id, timeline_export, decisions_log, resource_history, created_by) VALUES (...) ON CONFLICT (incident_id) DO UPDATE SET timeline_export=EXCLUDED.timeline_export, decisions_log=EXCLUDED.decisions_log, resource_history=EXCLUDED.resource_history WHERE aars.status != 'Finalized' RETURNING *` — if the `WHERE` clause excludes the conflicting row (i.e. it's already `Finalized`), the `RETURNING` yields no row; in that case return `403 DOCUMENT_IMMUTABLE` instead of silently no-op'ing.
  4. For each item in `findings`, validate: if `corrective_action` is non-empty/non-null, `owner_id` AND `due_date` must both be present — else `422 CORRECTIVE_ACTION_UNOWNED` (FRD's exact message "Assign an owner and due date to every corrective action before finalizing.") BEFORE inserting any finding row for this request (validate the WHOLE array first, fail atomically). `INSERT INTO aar_findings (aar_id, finding_text, category, corrective_action, owner_id, due_date) VALUES (...)` for each valid finding.
  5. Return `201 Aar` (including nested `findings`).

- `PATCH /api/v1/incidents/{id}/aar/{aarId}/finalize` (`action='edit'`) — no body.
  1. `403 DOCUMENT_IMMUTABLE` if already `status='Finalized'` (subsequent edit attempts after finalization, per FRD's validation rule — this IS the literal "edit attempted on finalized document" case the error table names).
  2. Re-run the SAME `CORRECTIVE_ACTION_UNOWNED` validation against the AAR's CURRENT `aar_findings` rows (a finding could have been added without an owner via a separate hypothetical edit path — defensive re-check at finalize time, not just at creation time).
  3. `UPDATE aars SET status='Finalized', finalized_by=$1, finalized_at=now() WHERE id=$2 RETURNING *`. Writes an evidence-log-visible event (document inline: `evidence-log.ts`'s aggregated view already surfaces this via `audit_log` if `AuditService.record()` is called here — call `AuditService.record(req.epmpUser.id, 'aar_finalized', 'aar', aarId, {incident_id})` imported from `../auth-org/audit.js`, the SAME single-writer pattern every other module already uses for audit-visible cross-cutting events, per TechArch 01-components.md's "AuditService.record() called by every other module" rule).
  4. Return `200 Aar`.
