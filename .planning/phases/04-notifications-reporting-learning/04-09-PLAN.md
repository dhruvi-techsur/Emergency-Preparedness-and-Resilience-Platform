<objective>
Fix the message-clarity gap where a signed-in user with a REAL, resolved role who simply lacks one specific permission (e.g. `incident_commander` attempting `reporting:edit`, which only `planning_logistics_chief` holds per 04-04's seed) gets told "Your account isn't assigned a role yet" — `rbac.ts`'s `ROLE_UNRESOLVED` constant, which is accurate ONLY for the genuinely-unresolved-role case (JIT provisioning found no `group_to_role_mapping` match, handled entirely in `sso.ts`/`routes.ts`'s SSO callback, never in `requirePermission()`).

Purpose: `requirePermission()`'s `checkPermission()===false` branch conflates two distinct, structurally-distinguishable cases: (1) a user whose `role_id` never resolved at all (impossible post-login, since `users.role_id` is `NOT NULL REFERENCES roles(id)` — this case can ONLY occur during the SSO callback's JIT-provisioning step, before a `users` row even exists), and (2) a user with a perfectly valid, resolved role who lacks one specific feature/action grant (the common, expected case for every action-level RBAC split this phase and prior phases established, e.g. 03-07's plans review/approve split, 04-04's reporting edit restriction). Case 2 is far more common in day-to-day use and currently gets the SAME alarming "contact your administrator, you have no role" message as case 1's genuine misconfiguration.
Output: A new `PERMISSION_DENIED` error_code/message distinct from `ROLE_UNRESOLVED`, returned specifically by `requirePermission()`'s permission-check-failed branch; `ROLE_UNRESOLVED` remains exactly as-is for its one real use site (the SSO callback in `routes.ts`).
</objective>
