## Summary

This is a re-audit covering TWO new gap-closure plans (04-08, 04-09) executed after the prior audit round confirmed and closed three HIGH findings (F-01 cross-jurisdiction notification compose/send, F-02 evidence-log jurisdiction-filter gap, F-03 AI-draft-approve identity-forgery). All three prior fixes were re-read at their cited locations and are confirmed **still present and unregressed** by 04-08/04-09's edits to shared files (`notifications.ts`, `evidence-log.ts` were not touched by either new plan; `routes.ts` and `IncidentWorkspace.tsx` WERE touched by 04-08, but only in unrelated regions — the fix code at `notifications.ts:303`/`:387` and `evidence-log.ts:147` is untouched and verified byte-identical to the prior audit's citations).

04-08 and 04-09 each carry their own `<threat_model>` block (T-04-14 through T-04-16), so this round remained **verify mode** for the new diff. All three declared mitigations were verified genuinely present in the implemented code (not merely asserted in docs):

- **T-04-14** (OIDC `state` open-redirect guard, `SignInCallback.tsx`): the type-guard (`typeof state === 'string' && state.startsWith('/') && state !== '/auth/callback'`) was adversarially tested against `//evil.com`, `/\evil.com`, `///evil.com`, and percent-encoded (`/%2F%2Fevil.com`) variants. All of these pass `startsWith('/')` syntactically (a real gap in the guard's own logic — it does NOT special-case protocol-relative/backslash prefixes), **but** the actual exploit path was independently traced through react-router v7.18.5's real `resolveTo`/`createPath`/`pushState` pipeline used by this app's `navigate()` call: react-router's own `resolvePath()` unconditionally strips ALL leading-slash runs via `removeDoubleSlashes` + `resolvePathname(toPathname.substring(1), "/")` before ever reaching `history.pushState()`, canonicalizing every one of these payloads down to a same-origin path (`//evil.com` → `/evil.com`, `/\evil.com` → `/evil.com`, `///evil.com` → `/evil.com`). This was verified three ways: (1) static code read of `resolvePath`/`removeDoubleSlashes` in the installed `react-router` package, (2) direct Node invocation of the real `resolveTo`/`createPath` functions against all four payloads confirming same-origin output, (3) a live headless-Chromium `history.pushState()` call with the raw payload strings, which **throws a `DataCloneError`/SecurityError** rather than ever navigating cross-origin (confirmed: `pushState` refuses a state-object URL whose implied origin differs from `document.location`'s). The combination of react-router's own normalization (defense layer 1) and the browser's native same-origin enforcement on `pushState` (defense layer 2) means there is no reachable bypass of this guard with the app's actual `BrowserRouter`/`useNavigate()` wiring, even though the type-guard's own regex is weaker than its own doc comment implies. Disposition: **SAFE, mitigate confirmed** (with a documented lower-severity code-quality note below — see Accepted risks).
- **T-04-15** (nav-config rename, `routes.ts:291-320`): confirmed the repointed `'notification-groups'` item still reads `hasNotifications` from the exact same `permRows.some((r) => r.feature === 'notifications' && r.actions.length > 0)` derivation (unchanged at `:226-228`) that gated it before this plan — a pure label/href presentation change, no RBAC widening. SAFE.
- **T-04-16** (`PERMISSION_DENIED` message, `rbac.ts:40-43`): confirmed the message is generic ("Your role doesn't include this action...") with no feature/action/role enumeration. Also independently re-verified 04-09's own stated risk — that a careless find-replace of `ROLE_UNRESOLVED` → `PERMISSION_DENIED` might have accidentally broken the ONE real `ROLE_UNRESOLVED` call site — and confirmed it did NOT: `routes.ts:85` (the SSO callback's `RoleUnresolvedError` catch block) still returns `error_code: 'ROLE_UNRESOLVED'` verbatim, untouched by either 04-08 or 04-09's diffs (confirmed via `git show` scoped to the actual changed lines in both plans' commits). SAFE.

A retroactive sweep of 04-08/04-09's full `files_modified` set (beyond the declared register) found: no new backend write routes (`NotificationsLanding.tsx` is a pure client-side navigation page with zero new API calls — it only links to existing, already-RBAC-gated routes); no SQL/shell/command injection sinks introduced (04-09's only backend change is a string-constant rename inside an existing, already-parameterized RBAC guard); no secret/token leakage in the new OIDC `state` payload (`state` only ever carries a same-origin relative path string, never a credential); the new `rbac.test.ts`'s bare test-only route (`/api/v1/_test/rbac-reporting-edit-probe`) is registered only inside the test file's own `beforeAll` on the shared `app` instance for test purposes and is NOT reachable in the production `server.ts`/`buildApp()` entry point (confirmed via grep — the string appears nowhere outside the test file); no XSS sinks (`dangerouslySetInnerHTML`/`innerHTML`) in any of the 12 new/modified files. **Zero new HIGH/CRITICAL findings this round.**

- **Refutation (adversarial attempts against T-04-14, the highest-risk candidate this round):** Constructed four candidate bypass payloads for the open-redirect guard — `//evil.com` (protocol-relative), `/\evil.com` (backslash, a known browser-normalization quirk vector), `///evil.com` (triple-slash), and `/%2F%2Fevil.com` (percent-encoded double-slash, to test whether any downstream decode step re-introduces the raw form). All four pass the guard's own `startsWith('/')` check — the guard ALONE does not stop them. Then traced the ACTUAL code path these values would travel: `navigate(returnPath, { replace: true })` → react-router v7.18.5's `useNavigate()` → `resolveTo()` → `resolvePath()`, which the installed package's own source (read directly, not assumed) shows unconditionally strips all leading-slash-run characters via `removeDoubleSlashes` + `resolvePathname(toPathname.substring(1), "/")` for ANY path starting with `/` or `\` — converting all four payloads to a same-origin relative path (`/evil.com`) before `history.pushState()` is ever invoked. Independently confirmed via direct Node invocation of the real `resolveTo`/`createPath` functions (not a reimplementation) against all four payloads, AND via a live headless-Chromium `history.pushState()` call with each raw payload string, which threw a `DataCloneError`/SecurityError rather than navigating cross-origin in every case — the browser's own same-origin enforcement on `pushState()` is a second, independent containment layer. The percent-encoded variant was NOT normalized by react-router (`/%2F%2Fevil.com` → `/%2F%2Fevil.com`, un-decoded) but remains a syntactically-valid same-origin relative path either way (the browser's URL parser treats `%2F` as a literal path-segment character, not a decoded `/`), so it poses no redirect risk regardless. **Conclusion: the open-redirect vector does not survive refutation given this app's actual `BrowserRouter`/`useNavigate()` wiring and the installed react-router version — downgraded from a candidate HIGH to a documented low-severity code-quality note (see Accepted risks) rather than a confirmed finding,** since exploiting the guard's own regex weakness would require either a react-router downgrade/behavior change or routing `state` through a DIFFERENT navigation primitive than this codebase's actual `navigate()` call — neither of which is true of the code as shipped.
