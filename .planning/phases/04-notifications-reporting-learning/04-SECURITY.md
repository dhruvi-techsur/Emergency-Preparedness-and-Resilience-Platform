**Mode:** verify

## Summary

All 13 declared `<threat_model>` mitigations (T-04-01 through T-04-13) across the phase's 7 executed plans were read against the actual implementation and, where feasible, live-attacked against the running compose stack (Postgres + OPA, migrations and seed already applied). 10 of 13 verified genuinely present and effective. Beyond the declared register, a mandated retroactive sweep for IDOR/jurisdiction-scope gaps surfaced the same vulnerability class Phase 3's own `03-SECURITY.md` previously confirmed HIGH for `tasks.ts`/`resource-requests.ts` (creation-time acceptance of a caller-supplied `incident_id` with no jurisdiction check) — and it recurs here, uncaught, in two new places this phase introduces: (1) `POST /api/v1/notifications/compose` + `.../send`, live-proven to let an attacker in jurisdiction A compose, approve, and send a notification linked to a victim incident in jurisdiction B, injecting a Timeline entry onto that incident attributed to the attacker; and (2) `GET /api/v1/evidence-log`, live-proven to let the lowest-privilege seeded role (`field_responder`) read Timeline rows from an incident entirely outside its jurisdiction_scope, because the endpoint's UNION query applies zero jurisdiction filter on either half. A third, independently-surfaced finding: `POST /api/v1/ai-drafts/:id/approve` requires only `notifications:view` (the lowest grant on that feature) and trusts a client-supplied `approver_id` with no check that it equals the signed-in caller — unlike the `/send` route's own `effectiveApproverId === req.epmpUser.id` re-verification — letting any view-only user forge `ai_drafts.approved_by` naming an uninvolved third party who never approved anything, live-proven. Do not ship until all three are fixed; the declared-register items that did verify (approver-identity re-check on send, AI-governance DB-backed guard, AAR/SITREP/evidence-log immutability, analytics' no-invented-target and session-only jurisdiction_scope read, the UNION filter-predicate bug fix from 04-07) are sound and require no further action.

## Confirmed findings

> Each survived adversarial refutation (input is user-controlled, no upstream guard, reachable).

### F-01: Cross-jurisdiction notification compose/send — caller-supplied `incident_id` accepted with no jurisdiction check — HIGH
- **Category:** Tampering / Elevation of privilege
- **Location:** `backend/src/modules/comms-reporting/notifications.ts:322-437` (compose), `:442-535` (send)
- **Description:** `POST /api/v1/notifications/compose` accepts `incident_id` directly from the request body and inserts it into `notifications.incident_id` with **no check** that the incident resolves within the caller's own `jurisdiction_scope` (contrast with every incident-ops route, which calls `fetchIncidentForMutation(incidentId, req.epmpUser!.jurisdiction_scope)` before touching an existing incident by id). `POST /api/v1/notifications/:id/send` then reads that same unchecked `incident_id` off the notification row and calls `TimelineService.append(client, updated.incident_id, ...)` inside the SAME transaction as the approval UPDATE — writing directly into `incident_timeline` for an incident the caller never had jurisdiction-scoped visibility into. This is the identical vulnerability class Phase 3's own `03-SECURITY.md` confirmed HIGH (F-02 there) for `tasks.ts`/`resource-requests.ts`'s creation-time `incident_id` acceptance — recurring here, unfixed, in a brand-new module.
- **Exploit (live-proven this session):** Seeded an attacker user (`incident_commander` role, `notifications:{view,create,approve}`) scoped to jurisdiction A only, and a victim incident scoped to jurisdiction B, created by an unrelated user. The attacker's own session token (jurisdiction_scope=[A]) was used to call `POST /api/v1/notifications/compose` with `incident_id` = the jurisdiction-B victim incident's id and a geotarget polygon (satisfying the audience-required gate without needing a recipient group). Response: `201`. Then `POST /api/v1/notifications/{id}/send` with the attacker as `approver_id`: `200`. A `SELECT title, actor_id FROM incident_timeline WHERE incident_id = <victim incident>` afterward returned `{ title: 'Notification sent: EXPLOIT: cross-jurisdiction notification', actor_id: <attacker> }` — confirming the attacker successfully wrote an attributed Timeline entry onto an incident in a jurisdiction they have zero RBAC/jurisdiction visibility into. Full request/response trace captured and reproduced in this session (test script executed, then removed — repo left clean).
- **Fix:** Before the INSERT in `compose`, resolve `incident_id` (when non-null) via the same pattern `reporting.ts` already correctly uses: `const incident = await fetchIncidentForMutation(incident_id, req.epmpUser!.jurisdiction_scope); if (!incident) return 404 RECORD_NOT_FOUND;` — mirroring `reporting.ts:261,324,393,478`'s own correct usage of this exact helper for every incident-linked route in the SAME module. `send` does not need an additional check if `compose`'s gate is fixed, since `send` only acts on notifications that already passed through `compose`'s INSERT.

### F-02: `GET /api/v1/evidence-log` — cross-jurisdiction information disclosure, zero jurisdiction filter on either half of the UNION — HIGH
- **Category:** Information disclosure
- **Location:** `backend/src/modules/comms-reporting/evidence-log.ts:88-150` (`fetchEvidenceLogRows`, `auditSql`/`timelineSql`)
- **Description:** The evidence-log aggregation joins `audit_log` and `incident_timeline` via `UNION ALL` with filter predicates for `actor_id`/`action_type`/`record_type`/`date_range`, but **neither half ever applies a jurisdiction filter**. Any caller holding `reporting:view` — including `field_responder`, the lowest-privilege seeded role, per `seed.ts`'s own grant (`{feature:'reporting', actions:['view']}`) — can read Timeline entries and audit_log events system-wide, across every jurisdiction, not just their own `jurisdiction_scope`. Compare `analytics.ts` in the SAME module, which correctly scopes all 3 KPI queries by `i.jurisdiction_id = ANY(jurisdiction_scope)` (verified above as T-04-06, SAFE) — the evidence-log endpoint built alongside it in the same plan has no equivalent guard.
- **Exploit (live-proven this session):** Seeded a `field_responder`-role attacker scoped to jurisdiction A only, and a victim incident scoped to jurisdiction B with a real `incident_timeline` row (`'CONFIDENTIAL: Victim jurisdiction B incident activity'`) inserted for it. Called `GET /api/v1/evidence-log?page_size=200` with the attacker's own session token (jurisdiction_scope=[A]): `200`, `total: 26`. Confirmed the response's `items` array contained a row with `record_id` matching the jurisdiction-B victim incident — i.e., the lowest-privileged seeded role read a Timeline entry from an incident it has no jurisdiction-scoped visibility into anywhere else in the system. The same response also included an `audit_log`-sourced row (`action: 'aar_finalized'`), confirming the `audit_log` half is equally unscoped (no per-row jurisdiction link exists on `audit_log` at all, making this half structurally unscopeable without a schema change — a materially harder fix than the `incident_timeline` half, which does have a resolvable jurisdiction via its `incident_id` FK).
- **Fix:** Join `incident_timeline`'s half through `incidents` and add `AND i.jurisdiction_id = ANY($N)` using `req.epmpUser!.jurisdiction_scope`, mirroring `analytics.ts`'s own correct pattern in the same module. The `audit_log` half has no incident/jurisdiction link in its schema at all (`audit_log` records security/admin events like `login`, `sso_config_change`, `user_suspend` that aren't inherently jurisdiction-scoped) — this half likely needs either a `reporting:view` → `admin`-tier permission requirement (restricting audit_log visibility to roles that already have legitimate platform-wide audit access) or an explicit product decision about whether audit_log events should be jurisdiction-filterable at all; document whichever is chosen rather than leaving it silently unscoped.

### F-03: `POST /api/v1/ai-drafts/:id/approve` — forged approval identity, no server-side re-check against the signed-in caller — HIGH
- **Category:** Spoofing / Elevation of privilege
- **Location:** `backend/src/modules/comms-reporting/notifications.ts:284-308`
- **Description:** This route is gated only by `requirePermission('notifications', 'view')` — the lowest grant on the `notifications` feature, held even by `field_responder` per `seed.ts`. It accepts a client-supplied `approver_id` in the request body and writes it directly into `ai_drafts.approved_by` with **no check that `approver_id` equals the signed-in caller** (`req.epmpUser!.id`). Contrast this with the `/send` route in the SAME file (`:468-469`), which correctly enforces `effectiveApproverId !== req.epmpUser!.id` → `403`. The FRD's explicit rule ("AI drafts must be approved by a signed-in person," enforced via the exact string "AI drafts must be approved by a signed-in person" at `:294-296`) is satisfied only in the narrow sense that SOME non-empty id must be supplied — it is never verified to be the id of the person actually making the HTTP call. This also means the client-side claim in T-04-10 ("message field populated only from the server-confirmed approve response") rests on a server guarantee that is itself forgeable: the "server-confirmed" `approved_by` can name anyone the attacker chooses.
- **Exploit (live-proven this session):** Seeded a `field_responder`-role attacker (view-only on `notifications`) and a separate, uninvolved "victim approver" user (`incident_commander` role) who never signed in or participated in this flow at all. The attacker called `POST /api/v1/ai-drafts` (succeeds — only requires `view`), then `POST /api/v1/ai-drafts/{id}/approve` with `{approver_id: <victim's id>}` using the attacker's OWN session token. Response: `200`, `{approved_by: <victim id>, approved_at: ...}`. A direct `SELECT approved_by FROM ai_drafts WHERE id=...` confirmed `ai_drafts.approved_by` now names the victim — who never approved anything, was never authenticated during this request, and has no record of consenting. Because `assertAiOriginApproved` (the shared AI-governance guard reused by both `notifications.ts`'s send route and `reporting.ts`'s SITREP/AAR finalize routes) only checks `approved_by IS NOT NULL`, this forged row would satisfy the AI-governance gate for ANY ai_origin:true notification/SITREP/AAR referencing this draft — meaning a low-privileged user can manufacture a fraudulent "named-person approval" trail attributing AI-drafted content to someone who never reviewed it.
- **Fix:** Add the identical identity check the `/send` route already has: `if (approver_id !== req.epmpUser!.id) return 403 { error_code: 'APPROVAL_REQUIRES_NAMED_USER', ... }` — the approver must be the signed-in caller, never a different asserted identity, matching the FRD's own "enforced server-side, not just hidden client-side" validation rule that the `/send` route already correctly implements for the SAME class of approval action.
