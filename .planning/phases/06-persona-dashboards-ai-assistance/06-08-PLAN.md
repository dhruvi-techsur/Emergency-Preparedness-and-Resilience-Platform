  <action>
Create `frontend/app/src/pages/incidents/IcsFormEditor.tsx`, routed `/incidents/{incidentId}/forms/{formId}` (per the UX mockup's Navigation Map exact route) OR `/incidents/{incidentId}/forms/new` for a fresh ICS-201 form (document inline: this plan builds a SINGLE representative form type, `'ICS-201'`, per S9.3's own "Situation summary" narrative field example — a full multi-step-form/multiple-form-type editor is out of this 2-3-task plan's budget; the underlying `ics_forms.form_type` column accepts any string, so adding more form types later is a data-only extension, not a structural change).

Using `PageHeader` (title = form_type + ": Incident Briefing", `status={<Badge tone="neutral">{form.status}</Badge>}`), `Card`, `TextField` (multiline, the "Situation summary"/"Narrative" field), `Button`, `AIDraft` (from `@epmp/design-system`):

State: `narrativeText` (the field's OWN value, independent of any draft), `activeDraft: {id, draft_text, sources, confidence_label} | null`, `editingDraft: boolean`, `editingDraftValue: string`.

- `GET /api/v1/incidents/{incidentId}/ics-forms` on mount; if a form with `form_type==='ICS-201'` already exists, load it (read-only if `status==='Approved'` — render the `TextField` `disabled`); otherwise render a fresh unsaved form (`POST .../ics-forms` fires on first explicit save, not automatically on page load — document inline this avoids littering the DB with empty draft rows from mere page visits).
- "Draft with AI" `Button variant="secondary"` below the narrative field: on click, `apiPost('/api/v1/ai-drafts', {target_feature: 'ics_form', target_field: 'narrative', context: narrativeText || 'Draft an ICS-201 situation summary for this incident', requesting_user_id: user.id})`, store the response in `activeDraft`. **Crucially: this does NOT touch `narrativeText`** — the TextField's displayed value is completely unaffected by this call, satisfying "never appears pre-inserted into the record" at the UI-state level, not just the backend's.
- When `activeDraft` is set, render `<AIDraft draftText={activeDraft.draft_text} sources={activeDraft.sources} editing={editingDraft} editingValue={editingDraftValue} onEditingValueChange={setEditingDraftValue} onEdit={() => {setEditingDraft(true); setEditingDraftValue(activeDraft.draft_text);}} onDiscard={handleDiscard} onApprove={handleApprove} />` directly below the narrative `TextField` (never wrapped inside it — separate DOM sibling, matching the mockup's explicit "never inside it" placement rule).
- `handleDiscard`: `apiPost('/api/v1/ai-drafts/{activeDraft.id}/discard', {})`, then `setActiveDraft(null)` — the narrative field is untouched (it was never touched in the first place).
- `handleApprove(finalText: string)` — a SINGLE user action (clicking "Approve" inside the AIDraft panel) that cascades through BOTH governance-sensitive endpoints before returning control to the user, so the Timeline entry is produced in the same click, not a second one:
  1. `apiPost('/api/v1/ai-drafts/{activeDraft.id}/approve', {approver_id: user.id, edited_text: finalText !== activeDraft.draft_text ? finalText : undefined})` — this is 06-03's endpoint, the ONLY place `ai_drafts.approved_by` gets set.
  2. **Only after that succeeds**: `setNarrativeText(finalText)` (the field now shows the approved text — this is the ONE and ONLY point in this entire component where the draft text reaches the actual form field) and persist the `ics_forms` row — `POST .../ics-forms` with `{form_type: 'ICS-201', content: {narrative: finalText}, ai_origin: true, ai_draft_id: activeDraft.id}` if this is the first save (06-01 returns `201 IcsForm` including the new row's `id`), or re-POST for a subsequent narrative edit (06-01 does not define a PATCH; document inline as a known Phase-6 simplification: each narrative edit after the first creates a new `ics_forms` row rather than updating in place) — capture the resulting row as `formRow` (its `id` is needed by step 3 below).
  3. **Immediately follow with the cascade this task's own must_haves truth and Task 3 Playwright test require**: `apiPost(`/api/v1/incidents/${incidentId}/ics-forms/${formRow.id}/approve`, {approved_by: user.id})` — 06-01's governance-guarded endpoint, the ONLY place that writes the "ICS form approved" Timeline entry (via `withTimelineTransaction`/`TimelineService.append`). This is NOT optional or deferred to a separate click: a single AIDraft "Approve" click must produce both the `ai_drafts.approved_by` write AND the ics_forms-level approve/Timeline write, or success criterion 4's "approval recorded... in the incident Timeline" is not actually reachable from the AIDraft panel's own Approve button as a one-action flow.
  4. `setActiveDraft(null)` (panel collapses, per the mockup's documented "AIDraft approved" state).
  5. Refetch the incident's Timeline (`queryClient.invalidateQueries(['incident-timeline', incidentId])`) so the newly-logged Timeline entry becomes visible without a manual reload.
- "Approve form" `Button variant="primary"` (separate from the AIDraft panel's own internal Approve) exists for the ONE case `handleApprove`'s cascade does not cover: a narrative written entirely manually, with no AI draft requested at all (`activeDraft` was never set, so `handleApprove`'s cascade never ran) — this button calls the SAME `POST /api/v1/incidents/{incidentId}/ics-forms/{formId}/approve` with `{approved_by: user.id}` directly, for that manual-only path. Disabled whenever `status === 'Approved'` already (whether approved via this button or via the AIDraft cascade above — once Approved, the form is read-only and this button has nothing left to do) OR whenever the `ics_forms` row doesn't yet exist / its content is empty. On success, the form becomes read-only (`status` badge flips to "Approved").
- AI-gateway-unavailable handling: if `POST /api/v1/ai-drafts` itself 503s, show `Alert tone="info" title="AI drafting is temporarily unavailable. You can still write this manually."` (FRD's exact message) — the narrative `TextField` remains fully editable regardless (never blocks manual completion).

Create `frontend/app/src/pages/incidents/IcsFormEditor.css` — matches the mockup's `Progress`-row-adjacent layout minus the actual multi-step `Progress` component (out of scope for this single-form-type plan; document inline), token-only spacing.

Reached from: Incident Workspace → Reports tab").
