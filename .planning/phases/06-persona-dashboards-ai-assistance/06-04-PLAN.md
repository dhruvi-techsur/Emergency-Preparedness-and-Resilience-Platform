  <name>Task 1: Deterministic hazard-feed clustering function + seed sample feed events</name>
  <files>backend/src/modules/ai-assist/signal-clustering.ts, backend/scripts/seed.ts</files>
  <action>
Create `backend/src/modules/ai-assist/signal-clustering.ts`:

```typescript
export async function clusterHazardFeedEvents(): Promise<{ clustersCreated: number }>
```

No live NOAA/NWS/USGS feed credential exists in this sandbox (F12 — Weather & Hazard Feed Ingestion — is explicitly deferred to v2 per `.planning/REQUIREMENTS.md`; this phase only needs the triage/clustering MECHANISM to be real and demonstrable against seeded sample data, not a live external integration). Implement:

1. Query all `hazard_feed_events` rows with no existing `signal_source_events` link (`LEFT JOIN signal_source_events ON hazard_feed_event_id = hazard_feed_events.id WHERE signal_source_events.id IS NULL`).
2. Group them by a real, deterministic rule — NOT a 1:1 passthrough (that would make "clustering" meaningless and fail to demonstrate the FRD's "groups related raw events into candidate signals" process step): group by `(type, ST_SnapToGrid(geometry::geometry, 0.5))` (same `type` hazard within roughly the same 0.5-degree grid cell — "corroborating feeds in the same area" per the FRD's own example confidence reason "High — 3 corroborating NOAA/NWS feeds"), using a single SQL query with `GROUP BY`.
3. For each resulting group with ≥1 event: compute `confidence_label`/`confidence_reason` as: `count >= 2` → `'High'`, reason `` `${count} corroborating feeds (${sources.join(', ')})` ``; `count === 1` → `'Medium'`, reason `` `Single source: ${source}` ``. NEVER a bare percentage — always this qualitative label + stated reason pair, per FRD's explicit rule.
4. `INSERT INTO signals (summary, confidence_label, confidence_reason) VALUES (...) RETURNING id` — `summary` derived as `` `${type} cluster — ${count} event(s) near ${roundedLat},${roundedLng}` ``.
5. For each source event in the group, `INSERT INTO signal_source_events (signal_id, hazard_feed_event_id, source, occurred_at) VALUES (...)`.
6. Return `{ clustersCreated: <number of signals inserted> }`.

Document inline: "TechArch 01-components.md assigns this clustering consumer to the `comms-reporting` module ('reads hazard-feed events via event bus... clusters, writes signals'). This phase hosts it in `ai-assist` instead since `comms-reporting` has zero executed code in this codebase (Phase 4 is unexecuted PLAN.md files only, confirmed via STATE.md) and F9's signal-triage half belongs conceptually with this phase's other AI-governance work; if Phase 4 is executed later and a real `comms-reporting` module materializes, this function can be moved there without changing its exported contract."

Extend `backend/scripts/seed.ts` (append) with 4-5 sample `hazard_feed_config`+`hazard_feed_events` rows simulating a real corroborating cluster (e.g. 3 'NOAA'/'NWS'/'USGS' feed rows with `type='Coastal Flood Watch'`, geometries within 0.5 degrees of each other, `issued_at` within the last few hours) plus 1-2 isolated single-source events (different `type`, far-apart geometry) — enough realistic variety that `clusterHazardFeedEvents()` demonstrably produces one multi-source High-confidence signal and at least one Medium-confidence single-source signal when run against this seed data. Call `clusterHazardFeedEvents()` from within `seed.ts`'s own `main()` after inserting the hazard-feed-event rows, so a fresh `npm run seed` run always leaves the Signal Triage Queue populated for human review/demo purposes — idempotent via the "no existing signal_source_events link" query condition in step 1 above (a second seed run finds zero unclustered events and clusters nothing new).

  1. `404` if signal doesn't exist.
  2. Fetch the signal + its linked `signal_source_events` (for a `type`/`severity` inference — derive `type_suggestion` from the signal's summary text, `severity_suggestion` as `'Elevated'` if `confidence_label === 'High'` else `'Watch'`, a simple deterministic heuristic documented inline as a Phase-6 simplification pending a real classification rule).
  3. Return `200 SignalPromotePrefill` per TechArch's EXACT shape: `{ prefill: { name_suggestion: string; type_suggestion: string; severity_suggestion: Severity; source_signal_id: string } }`. **This endpoint's code path contains NO `INSERT INTO incidents` statement anywhere — write this as a structural guarantee, not just a runtime check**, satisfying FRD's "enforced server-side (the promote endpoint returns a pre-filled draft payload, not a created incident)" validation rule and the `400 PROMOTE_REQUIRES_HUMAN_SUBMIT` error-table entry's intent (a client CANNOT bypass human submission through this endpoint because the endpoint has no code path capable of creating the incident — there is nothing to "bypass").
  4. On success, `UPDATE signals SET status='Promoted' WHERE id=$1` so the queue reflects it was reviewed (NOT that an incident exists — the row only proves a human clicked "Promote," not that they completed the resulting incident-creation form; document this distinction inline).

  1. `422` with message **"A reason is required to dismiss a signal."** if `reason` is missing/empty (app-layer pre-check backstopped by the DB's own `chk_dismissed_requires_reason` CHECK constraint).
  2. `UPDATE signals SET status='Dismissed', dismissed_reason=$1 WHERE id=$2 RETURNING *`. Return `200 Signal`.
