<objective>
Populate `role_landing_config` (the F18 reference table Phase 1 migrated but explicitly left empty — "Populating/consuming role_landing_config for full persona-dashboard routing is explicitly F18/Phase 6 scope") with a distinct default landing route and `SideNav` configuration for each of the 5 consolidated personas (PER-01 through PER-05), and expose it via `GET /api/v1/me/landing-config`.

Purpose: Success criterion 1 ("Each of the 5 consolidated personas lands on a distinct default dashboard with role-based navigation") requires a real, queryable source of truth for "what route does this role land on and what nav does it see" — this plan builds that source of truth. 06-05 through 06-07's frontend dashboard pages and RouteGuard's post-login redirect both consume this endpoint.
Output: 5 seeded `role_landing_config` rows (one per persona role) and the `GET /api/v1/me/landing-config` endpoint resolving them with a documented non-blank fallback for any future unmapped role.

Sequencing note: Wave 2, depends_on 06-01 (explicit `depends_on` edge, added in revision to fix a checker-flagged same-wave `backend/scripts/seed.ts` conflict — both plans previously sat at wave 1 with no enforced ordering between them) — this plan now runs strictly AFTER 06-01, appending its own `role_landing_config` seed rows after 06-01's `incidentsFullAccessRoles` approve-grant edit already exists. `backend/src/modules/auth-org/routes.ts` remains exclusively this plan's own file, not touched by 06-01 or any other plan in this phase.
</objective>
