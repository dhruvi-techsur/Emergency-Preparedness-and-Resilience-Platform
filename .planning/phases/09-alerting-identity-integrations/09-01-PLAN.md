4. **Recognized-vs-unrecognized trigger**: if the resolved provider for `req.channel` isn't `KNOWN_PROVIDER`'s config (i.e. `req.channel` isn't one of `['SMS','Email']` for the Everbridge config OR `'IPAWS'` for the IPAWS config) OR `req.message === 'FORCE_PROVIDER_OUTAGE'` (a literal test-injection trigger, documented inline exactly like `cad-adapter.ts`'s `simulateFailure` param doc comment), call `recordProviderHealth(providerName, 'offline')`, INSERT a `notification_dispatch_log` row with `dispatch_status = 'failed'`, and return `{ external_message_id: '', dispatch_status: 'queued_for_retry' }` (NOT a throw here — unlike the approval/CAP gates above, a provider outage is F14's documented "queue for retry" graceful-failure path, not a hard rejection; this function's caller, `notifications.ts`, must NOT treat this return value as a dispatch success). 5. `export function buildCapEnvelope(req: { notification_id: string; message: string; sender: string; event: string; urgency: string; severity: string; certainty: string; area: string }): string` — a pure function building a minimal, well-formed OASIS CAP 1.2-shaped XML string containing ALL of: `<identifier>`, `<sender>`, `<sent>`, `<status>Actual</status>`, `<scope>Public</scope>`, and an `<info>` block with `<category>`, `<event>`, `<urgency>`, `<severity>`, `<certainty>`, `<area><areaDesc>` — e.g.:
```xml
<?xml version="1.0" encoding="UTF-8"?>
<alert xmlns="urn:oasis:names:tc:emergency:cap:1.2">
  <identifier>{uuid}</identifier>
  <sender>{sender}</sender>
  <sent>{isoTimestamp}</sent>
  <status>Actual</status>
  <msgType>Alert</msgType>
  <scope>Public</scope>
  <info>
    <category>{event-derived category, e.g. 'Met'}</category>
    <event>{event}</event>
    <urgency>{urgency}</urgency>
    <severity>{severity}</severity>
    <certainty>{certainty}</certainty>
    <description>{message, XML-escaped}</description>
    <area><areaDesc>{area}</areaDesc></area>

</alert>
```
