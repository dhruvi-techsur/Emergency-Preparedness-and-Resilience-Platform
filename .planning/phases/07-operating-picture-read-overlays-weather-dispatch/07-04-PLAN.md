Add a `DispatchStatusResponse` interface matching Plan 07-02's exact backend shape:
```ts
interface DispatchStatusResponse {
  linked: boolean;
  status?: string;
  unit_ids?: string[];
  source?: string;
  updated_at?: string;
}
```

Add a new query alongside the existing `incidentQuery`/`timelineQuery`:
```ts
const dispatchStatusQuery = useQuery({
  queryKey: ['incident-dispatch-status', id],
  queryFn: () => apiGet<DispatchStatusResponse>(`/api/v1/incidents/${id}/dispatch-status`),
  enabled: Boolean(id),
});
```

In the sidebar (`<div className="ep-incident-workspace__side">`), add a new `Card title="Dispatch status"` BETWEEN the existing "Command roles" and "Map" cards (command roles is the most operationally urgent, map is the least — dispatch status sits in between per its own operational relevance, matching no explicit mockup ordering since Screen-05's own layout predates F15, so this ordering is this plan's own reasonable discretion):

- While loading: a simple `<p className="caption" aria-busy="true">Loading…</p>` (same loading-text convention the Reports tab above already uses).
- If `!dispatchStatusQuery.data?.linked`: render `<EmptyState title="No dispatch data linked">This incident has no matched CAD/911 dispatch event.</EmptyState>` — matching the F15 Process step 3's "remains unlinked" rule rendered honestly, not as an error.
- If linked: render the status as plain text (NOT a Badge — F15 doesn't define a fixed tone-mapped status vocabulary the way incident severity does; a plain `<p>Status: {status}</p>` is the correct, non-invented treatment), the `unit_ids` joined as a comma-separated list if present, and a `<Provenance source={source} time={new Date(updated_at).toLocaleString()} />` call — **never pass `verified={false}` here**: CAD data isn't an "unverified feed" being validated, it's read-only data whose authority lives elsewhere, so the default verified-true branch (plain Provenance chip, no dashed treatment) is the semantically correct rendering, distinct from F12's hazard layers.
- **Structurally, this Card contains NO button, NO form, NO onClick handler that could mutate dispatch data** — this is the literal mechanism satisfying "no edit action anywhere in the UI." Do not add a "Refresh" or "Edit" button even as a disabled placeholder — per F15's "absence, not merely hidden" rule (mirroring 04-06's AarGenerator closure-gate precedent of omitting entirely rather than disabling).
