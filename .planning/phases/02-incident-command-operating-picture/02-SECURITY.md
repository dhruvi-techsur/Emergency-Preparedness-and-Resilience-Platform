## Summary

This audit verified every `<threat_model>` entry declared across the 7 EXECUTED plans of Phase 2 (02-01 through 02-07; T-02-01 through T-02-15) against the actual implemented code — not plan prose. 02-08 (the Keycloak/OIDC gap-closure plan) was explicitly excluded per scope instructions since it has not been executed.

Critically, this phase's own internal code-review/verification cycle (`02-REVIEW.md`, iteration 2) already found and fixed a real BLOCKER-adjacent issue — **W1: jurisdiction-scope filtering was missing on every mutating incident-ops route** (the exact gap T-02-03/T-02-09 in the plans' own threat models had flagged as "deferred"/"accept"). This audit independently re-verified that fix is genuinely present in the delivered code (not just claimed in a review doc): `fetchIncidentForMutation`/`fetchIncidentDetailShape` are now called with `req.epmpUser.jurisdiction_scope` at every list/detail/PATCH/timeline/activation/command-roles/closure call site in `incidents.ts`, `activation.ts`, `command-roles.ts`, and `closure.ts`, confirmed by direct file read (line citations below), not by trusting the review document. Two regression tests (`incidents.test.ts`, `activation.test.ts`) construct genuinely separate jurisdictions/users and assert 404 on cross-jurisdiction access — read in full, not merely grepped for a function name.

All server-side security boundaries declared as `mitigate` (T-02-01, T-02-02, T-02-04, T-02-05, T-02-07, T-02-08, T-02-10) were confirmed structurally present and correctly implemented — transaction wrapping, FOR UPDATE row-locking, structural confirmation gates, provenance-gated fallback-as-default, and Provenance's dual-branch unverified rendering all exist exactly as declared. All `transfer` dispositions (T-02-03's successor scoping, T-02-11, T-02-13, T-02-15) were confirmed to genuinely land on the backend enforcement point named, not merely assumed from code structure — each backend `requirePermission` + jurisdiction-scope check was read directly. The one remaining `accept` disposition still open at phase-end, T-02-06 (tasks-cascade error-message matching instead of Postgres code 42P01), was confirmed to be bounded exactly as declared: no `tasks` table exists anywhere in the migrations yet, so the masking risk cannot currently manifest, and it is correctly owned by Phase 3.

No new HIGH/CRITICAL issues were found beyond what this phase's own review cycle already caught and fixed. Ship as-is; carry the two disclosed accepted-risk items (T-02-06, DB-layer RLS backstop) into Phase 3's planning.

## Resolved findings

### W1: Jurisdiction-scope filtering missing on mutating incident-ops routes
- **Status:** Fixed in commit `e214583` (02-REVIEW.md iteration 2), independently re-verified by this audit
- **Prior finding:** `GET /api/v1/incidents` (list), `GET/PATCH /api/v1/incidents/{id}`, `GET /api/v1/incidents/{id}/timeline`, and all three state-machine mutation routes (`activation`, `command-roles`, `closure`) performed no jurisdiction-scope check — any authenticated user holding `incidents:view`/`incidents:edit` (regardless of their own `jurisdiction_scope`) could read or mutate ANY incident in the system by id, a cross-tenant IDOR. This matches exactly what T-02-03/T-02-09's own `accept`/`transfer` dispositions in the 02-01/02-02/02-03 plans had flagged as deferred — the gap was disclosed, not hidden, but it was a genuine exploitable path through the normal API for any authenticated incidents-permission holder.
- **Fix applied:** `incidents.ts:233-238` (list WHERE clause), `incidents.ts:152-158` (`fetchIncidentForMutation` shared guard, scoped `WHERE id=$1 AND jurisdiction_id=ANY($2)`), `incidents.ts:127-143` (`fetchIncidentDetailShape` now takes an optional `jurisdictionScope` param, threaded through GET/PATCH/timeline), `activation.ts:67-70`, `command-roles.ts:54-57`, `closure.ts:42-45` — each mutation route now calls `fetchIncidentForMutation(id, req.epmpUser!.jurisdiction_scope)` before any read or write, returning the same `INCIDENT_NOT_FOUND` 404 for both "doesn't exist" and "exists in another jurisdiction" (deliberately indistinguishable, preventing existence-leakage).
- **Verification:** Read all 6 call sites directly (not trusting 02-REVIEW.md's line citations blindly — independently confirmed the `jurisdiction_scope` parameter is actually threaded through at `incidents.ts:366`, `391`, `430`, `activation.ts:67`, `command-roles.ts:54`, `closure.ts:42`). Read both new regression tests in full: `incidents.test.ts:193-230`-ish ("jurisdiction-scope isolation... W1 fix") and `activation.test.ts:240-`-ish ("jurisdiction-scope isolation: a caller cannot activate, assign command roles on, or close an incident outside their own jurisdiction_scope") — both construct a genuinely separate jurisdiction + user via direct SQL `INSERT`, not a mock, and assert 404 against the live schema.
