<objective>
Close UAT gap ref 2 (blocker): a human tester reached the app only through Pivota's port-7777 preview proxy and found no reachable sign-in option. Root cause (independently diagnosed and empirically re-confirmed in this planning session, not just taken from the debug log): `frontend/app/src/auth/oidc-config.ts` hardcodes `KEYCLOAK_AUTHORITY = 'http://localhost:8081/realms/epmp'`, a sandbox-internal-only address that `signinRedirect()` sends the real tester's browser to — a dead address from outside the sandbox, indistinguishable from "no login option exists." Three compounding infrastructure gaps make even a same-origin fix insufficient on their own: Keycloak doesn't trust forwarded headers (so it would keep emitting internal-only URLs in its own login-page HTML even behind a proxy), the realm's `redirectUris` only allow-lists `localhost:5173`/`localhost:8080`, and Vite's dev proxy has no entry for Keycloak's browser-facing paths at all.

This plan fixes all four, verified empirically in this planning session with throwaway Keycloak containers (not assumed from documentation): (1) making the OIDC authority same-origin, mirroring the file's own already-correct `redirect_uri` pattern; (2) extending Vite's dev proxy to forward Keycloak's browser-facing paths (`/realms`, `/resources`, `/js`) with `xfwd: true`; (3) configuring Keycloak to trust forwarded headers (`KC_PROXY_HEADERS=xforwarded`, `KC_HOSTNAME_STRICT=false`); (4) widening the realm client's `redirectUris` to a host-less relative pattern that validates against whichever origin Keycloak resolves per-request — confirmed by direct testing to work for both a simulated external preview host AND direct sandbox access, with zero need to pre-register every possible preview hostname.

Purpose: Unblock every Phase 2 UAT test that requires a signed-in user (tests 2-5, all currently blocked) — and every future phase's UAT, since this is Phase 1's foundational SSO flow, not something scoped to Phase 2's own feature surface.
Output: A real browser reaching the app exclusively through the preview proxy can sign in and reach the role-scoped shell, proven by a scripted reproduction through the actual port-7777 proxy infrastructure (not merely inferred from direct-sandbox access).

Scope note: the backend's own ID-token validation (`backend/src/modules/auth-org/sso.ts::handleSsoCallback`, `jose.jwtVerify(idToken, jwks)`) was inspected directly in this planning session — it is called with NO `issuer`/`audience` options, so `jose` does not check the token's `iss` claim at all today. This means the per-request-varying `iss` Keycloak will now stamp into tokens (matching whatever origin the browser used) requires NO backend change: the JWKS fetch URL stays on the internal `KEYCLOAK_ISSUER` env var (server-side, sandbox-internal access is correct and unaffected), and signature validation is unaffected by which origin the browser used. This plan does not touch `sso.ts`, `backend/src/config/env.ts`, or `.env`/`.env.example` — confirmed unnecessary, not merely out of scope by assumption.
</objective>

**1. `frontend/app/src/auth/oidc-config.ts`** — Replace the hardcoded `KEYCLOAK_AUTHORITY` constant:

```ts
// BEFORE (line 20):
const KEYCLOAK_AUTHORITY = 'http://localhost:8081/realms/epmp';

// AFTER:
const KEYCLOAK_AUTHORITY = `${window.location.origin}/realms/epmp`;
```

This mirrors the SAME file's already-correct `redirect_uri: \`${window.location.origin}/auth/callback\`` on line 26 — the asymmetry between these two lines was the diagnostic smoking gun in the debug session. `oidc-client-ts`'s `UserManager` will now fetch its OIDC discovery document from `${window.location.origin}/realms/epmp/.well-known/openid-configuration` — same-origin, reachable through whichever proxy actually served the SPA (Pivota's preview proxy in production/UAT, or direct sandbox access in dev/Playwright).

**2. `frontend/app/vite.config.ts`** — Add three proxy entries for Keycloak's browser-facing paths (per `runtime-environment.md` §9's own named Keycloak example: `/realms/`, `/resources/`, `/js/`), each with `xfwd: true` so Keycloak receives `X-Forwarded-Host`/`X-Forwarded-Proto`:

```ts
server: {
  host: '0.0.0.0',
  port: 5173,
  proxy: {
    '/api': {
      target: 'http://localhost:8080',
      changeOrigin: true,
    },
    '/realms': {
      target: 'http://localhost:8081',
      changeOrigin: true,
      xfwd: true,
    },
    '/resources': {
      target: 'http://localhost:8081',
      changeOrigin: true,
      xfwd: true,
    },
    '/js': {
      target: 'http://localhost:8081',
      changeOrigin: true,
      xfwd: true,
    },
  },
},
```

`xfwd: true` is REQUIRED (not optional) — confirmed by reading Vite's bundled http-proxy source (`node_modules/vite/dist/node/chunks/dep-BK3b2jBa.js`, `XHeaders` function): without it, `options.xfwd` is falsy and no `X-Forwarded-*` headers are added at all, which is exactly the "even a same-origin proxy fix needs Keycloak itself reconfigured" compounding factor the debug session identified. `changeOrigin: true` alone (as the existing `/api` entry already has) only rewrites the outbound `Host` header to the target — it does not add forwarded headers.

**3. `docker-compose.yml`** — Add two environment variables to the `keycloak` service (do not touch any other service):

```yaml
keycloak:
  image: quay.io/keycloak/keycloak:25.0
  command: ["start-dev", "--import-realm"]
  environment:
    KEYCLOAK_ADMIN: admin
    KEYCLOAK_ADMIN_PASSWORD: devpass
    KC_PROXY_HEADERS: xforwarded
    KC_HOSTNAME_STRICT: "false"
  ports: ["8081:8080"]
  volumes: ["./backend/keycloak:/opt/keycloak/data/import:ro"]
  healthcheck:
    test: ["CMD-SHELL", "exec 3<>/dev/tcp/localhost/8080"]
    interval: 3s
    timeout: 3s
    retries: 40
```

`KC_PROXY_HEADERS=xforwarded` is the specific setting empirically confirmed in this planning session (via a throwaway `quay.io/keycloak/keycloak:25.0` container) to make Keycloak derive its OIDC discovery document's `issuer`/`authorization_endpoint`/`jwks_uri` — and its login page's form `action` and asset `href`/`src` paths — from `X-Forwarded-Proto`/`X-Forwarded-Host` instead of the literal internal address. Without it, forwarded headers are present on the request but Keycloak ignores them and keeps emitting `127.0.0.1:8081`-rooted URLs (confirmed: this is the exact behavior observed BEFORE adding the env var, and it reverses immediately after). `KC_HOSTNAME_STRICT: "false"` is already this image's `start-dev` default (confirmed via `kc.sh show-config` against the currently-running container: `kc.hostname-strict = false (classpath keycloak.conf)`) but is made explicit here per `runtime-environment.md` §9's prescribed fix shape, rather than relying on an undocumented default that a future base-image bump could change. No `KC_HOSTNAME` key is set (also per the doc) and no `KC_HTTP_ENABLED` is added — `start-dev` mode already serves plain HTTP, confirmed by every `curl` against port 8081 in this planning session, so adding it would be a documentation-only no-op.

**4. `backend/keycloak/epmp-realm.json`** — Change the `epmp-app` client's `redirectUris` from two literal sandbox-internal origins to a host-less relative pattern:

```json
// BEFORE:
"redirectUris": [
  "http://localhost:5173/*",
  "http://localhost:8080/*"
],

// AFTER:
"redirectUris": [
  "/auth/callback",
  "/auth/callback/*"
],
```

This was the single hardest-to-verify-by-reasoning-alone part of the fix, so it was proven empirically with throwaway Keycloak containers rather than assumed from Keycloak's documentation: a realm configured with ONLY this relative pattern (a) accepted `redirect_uri=https://some-preview-host.example.com/auth/callback` when the authorization request carried `X-Forwarded-Proto: https` + `X-Forwarded-Host: some-preview-host.example.com` (simulating a real external preview tester, with `KC_PROXY_HEADERS=xforwarded` set), returning the real login form (HTTP 200) rather than Keycloak's `Invalid parameter: redirect_uri` error; and (b) ALSO accepted `redirect_uri=http://localhost:5173/auth/callback` with a plain `Host: localhost:5173` header and NO forwarded headers at all (simulating direct sandbox/Playwright access), confirming this single change covers BOTH access patterns without needing to guess or pre-register the preview host's domain pattern (which changes per session per `runtime-environment.md` §9's own warning: "never hard-code it"). A literal `https://*.<preview-domain>/*` wildcard entry was tried FIRST and empirically REJECTED by Keycloak 25.0 (`Invalid parameter: redirect_uri`, confirmed in this session) — Keycloak's redirect-URI wildcard matching does not support subdomain wildcards the way this fix initially assumed; the host-less relative pattern is the form that actually works, confirmed by direct test, not by documentation alone. Do not touch any other key in this file (`groups`, `users`, `webOrigins`, the `groups` protocol mapper) — this is a single-field, surgical change.
