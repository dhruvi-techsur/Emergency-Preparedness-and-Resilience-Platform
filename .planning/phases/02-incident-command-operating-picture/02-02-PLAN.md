<objective>
Build the three remaining state-machine actions on an incident: command-role assignment (with reassignment semantics), activation-level change (with the server-side Incident-Commander gate and an explicit `confirmed:true` request-body gate so the consequence-confirmation requirement can never be bypassed by a direct API call), and closure (which cascades open tasks to `Overdue`). Every one of these writes exactly one Timeline entry inside the same transaction as its domain mutation.

Purpose: Success criterion 2 ("every assignment, status change, and decision writes exactly one entry to the incident's append-only Timeline") and criterion 3 ("at least one Incident Commander must be assigned before activating above Monitoring") are entirely this plan's responsibility on the backend side — the frontend Modal in a later plan is a UX safeguard, but THIS plan is the actual security/business-rule boundary.
Output: Three new route files extending `incident-ops`, each calling `TimelineService.append`/`withTimelineTransaction` from 02-01.
</objective>

  <files>backend/src/modules/incident-ops/command-roles.ts</files>
  <action>
Create `backend/src/modules/incident-ops/command-roles.ts`:

- `POST /api/v1/incidents/{id}/command-roles` (`preHandler: requirePermission('incidents', 'edit')`) — body `{ role_title: CommandRoleTitle; person_id: string }` where `CommandRoleTitle` is exactly `'Incident Commander'|'Planning'|'Logistics'|'Operations'|'Finance/Admin'|'Public Information'` per TechArch. Inside `withTimelineTransaction`:
  1. `SELECT id, person_id FROM incident_command_roles WHERE incident_id=$1 AND role_title=$2 AND unassigned_at IS NULL FOR UPDATE` — lock any existing active assignment for this role on this incident.
  2. If one exists and `person_id` differs: `UPDATE incident_command_roles SET unassigned_at = now() WHERE id = $prior_id` (reassignment — the prior row becomes historical, never deleted, per the FRD's named-person-accountability requirement needing a durable assignment history).
  3. If one exists with the SAME `person_id`: no-op, return the existing row (idempotent re-assignment of the same person is not an error, just a no-op — document inline).
  4. Otherwise (or after step 2): `INSERT INTO incident_command_roles (incident_id, role_title, person_id, assigned_by) VALUES ($1,$2,$3,$4) RETURNING *`.
  5. `TimelineService.append(client, incidentId, title, meta, 'brand', req.epmpUser.id, 'EPMP', {role_title, person_id, prior_person_id})` where `title` is `"${role_title} assigned to ${person.name}"` (reassignment) or `"${role_title} assigned to ${person.name}"` (first-time) — fetch the person's `name` via a join/lookup before building the title so the Timeline entry is human-readable, not just an id. `meta` states "Reassigned from [prior name]" when applicable, otherwise omitted.
  6. Return `201 IncidentDetail['command_roles'][0]` shaped per TechArch (`{role_title, person:{id,name}, assigned_at}`).
  On any DB error inside the transaction, respond `500 TIMELINE_WRITE_FAILED` per FRD's error table.
  </action>

<task type="auto">
  <name>Task 2: Activation-level change (server-side commander gate + confirmation gate)</name>
  <files>backend/src/modules/incident-ops/activation.ts</files>
  <action>
Create `backend/src/modules/incident-ops/activation.ts`:

- `POST /api/v1/incidents/{id}/activation` (`preHandler: requirePermission('incidents', 'edit')`) — body `{ activation_level: ActivationLevel; confirmed: true }`.
  1. **Confirmation gate (structural, not UI trust)**: if `confirmed !== true`, return `400` with `error_code: 'ACTIVATION_CONFIRMATION_REQUIRED'`, `message: "Confirm the activation-level change before it takes effect."` — this makes the FRD's "Modal confirmation must be accepted before the change takes effect" an API-enforced rule, not merely a frontend affordance a direct API caller could skip.
  2. Fetch the incident's current `activation_level`. If the target level is the SAME as current, return the current `IncidentDetail` as a no-op (200), no Timeline entry (not a real change).
  3. **Commander gate**: if the target `activation_level` is `'Partial'` or `'Full'` (i.e., above `'Monitoring'`), run `SELECT count(*) FROM incident_command_roles WHERE incident_id=$1 AND role_title='Incident Commander' AND unassigned_at IS NULL`. If zero, return `422 NO_COMMANDER_ASSIGNED` with the FRD's exact message "Assign an Incident Commander before activating above Monitoring." — do NOT change `activation_level`.
  4. Otherwise, inside `withTimelineTransaction`: `UPDATE incidents SET activation_level=$1, updated_at=now() WHERE id=$2 RETURNING *`. Determine `tone`: escalation (moving to a higher level) → `'warning'`; de-escalation → `'brand'`. `TimelineService.append(client, incidentId, `Activation changed to ${activation_level}`, undefined, tone, req.epmpUser.id, 'EPMP', {from: priorLevel, to: activation_level})`.
  5. Return `200 IncidentDetail`.

Document inline: per FRD's Validation ("Activation level cannot jump directly from Monitoring to Full without the Modal confirmation explicitly naming the intermediate consequence skipped") — this is satisfied at the UI layer (the frontend Modal in 02-06 states the specific target level's consequence regardless of skip-distance); the API itself only enforces that SOME valid target level was explicitly confirmed, since the API has no concept of "the Modal's wording" — document this division of responsibility clearly.
  </action>
  <verify>
