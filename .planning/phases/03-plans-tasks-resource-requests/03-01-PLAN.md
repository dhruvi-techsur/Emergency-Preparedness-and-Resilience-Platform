<objective>
Build the `tasks` schema (extending Phase 2's incident-ops migration file set, NOT recreating any Phase-2-owned table) and the task CRUD/status-transition API: create, list/filter, and the state-machine-enforced `PATCH .../status` endpoint. Every status change writes a `task_status_history` row and — when the task belongs to an incident — exactly one `incident_timeline` entry, reusing Phase 2's `TimelineService`/`withTimelineTransaction` rather than reimplementing transactional Timeline-writing.

Purpose: Success criterion 3's create/assign/track-to-close half of the task lifecycle terminates here. The Overdue time-based auto-flip (the other half of criterion 3) is deliberately NOT built in this plan — see the reconciliation note below — it is 03-02's exclusive responsibility, built on top of the `tasks` table this plan creates.
Output: `tasks`/`task_status_history`/`resource_requests`/`resource_request_status_history` schema (resource_requests columns created here so 03-04's resource-request plan has its table ready, but this plan's API surface only touches `tasks`), plus the task CRUD/status API.

**Reconciliation with Phase 2's `closure.ts` (critical — read before writing migration):** Phase 2's `02-02-PLAN.md` already wrote `backend/src/modules/incident-ops/closure.ts` with `UPDATE tasks SET status='Overdue', updated_at=now() WHERE incident_id=$1 AND status NOT IN ('Done','Overdue') RETURNING id`, defensively wrapped in try/catch treating a "relation does not exist" error as "0 tasks cascaded" (since Phase 2 had no `tasks` table yet). **This plan's migration FINALLY creates that table** — from this plan forward, `closure.ts`'s cascade query is live and functional, not a no-op. This plan does NOT edit `closure.ts` itself — **03-02 does**, extending the bulk cascade UPDATE into a per-task loop that writes a `task_status_history` row (`changed_by=NULL`, same system-attribution convention as the time-based sweep) and a Timeline entry for EACH cascaded task, not just the one generic "Incident closed" entry — because this plan's own truth #4 ("every task status transition writes exactly one `task_status_history` row") must hold for the closure-cascade path too, and a bulk `UPDATE ... RETURNING id` with no corresponding history INSERT would silently violate it. See 03-02's objective for the full fix; it is listed here only so a reader of THIS plan understands why `closure.ts` isn't "already correct" as Phase 2 left it, and why that correction belongs to 03-02 rather than here (03-02 already owns the Overdue-audit-trail convention this fix reuses). The cascade-on-closure mechanism (incident closes → open tasks flip to Overdue) and the criterion-3 time-based mechanism (task's own `due_at` passes → flips to Overdue even while the incident stays open) are two DISTINCT, non-conflicting triggers for the identical terminal state: closure is an immediate, synchronous, incident-scoped cascade; the time-based check is a scheduled, task-scoped sweep across ALL open tasks regardless of incident status, built in 03-02 as `backend/src/modules/incident-ops/overdue-sweep.ts`. Both write to the same `status='Overdue'` value via the same `task_status_history` log — there is no competing state machine, just two independent triggers converging on one terminal status, exactly as F4's FRD describes ("Tasks past their due time... automatically flip to Overdue" is independent of, and additional to, the closure cascade's "closes all open tasks to Overdue unless completed").
</objective>

CREATE TABLE resource_requests (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  resource_type VARCHAR(50) NOT NULL CHECK (resource_type IN ('Personnel','Equipment','Supplies')),
  description TEXT NOT NULL CHECK (char_length(description) <= 1000),
  quantity INTEGER NOT NULL CHECK (quantity >= 1),
  status VARCHAR(20) NOT NULL DEFAULT 'Draft'
    CHECK (status IN ('Draft','Awaiting approval','Approved','Fulfilled','Declined')),
  incident_id UUID NOT NULL REFERENCES incidents(id),
  task_id UUID REFERENCES tasks(id),
  requesting_role VARCHAR(100) NOT NULL,
  needed_by TIMESTAMPTZ NOT NULL,
  requested_by UUID NOT NULL REFERENCES users(id),
  approved_by UUID REFERENCES users(id),
  decline_reason TEXT,
  assigned_to VARCHAR(200),
  fulfilled_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT chk_decline_requires_reason CHECK (NOT (status = 'Declined' AND decline_reason IS NULL))
);

CREATE TABLE resource_request_status_history (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  resource_request_id UUID NOT NULL REFERENCES resource_requests(id),
  from_status VARCHAR(20),
  to_status VARCHAR(20) NOT NULL,
  changed_by UUID NOT NULL REFERENCES users(id),
  changed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_tasks_owner_status ON tasks(owner_id, status);
CREATE INDEX idx_tasks_incident ON tasks(incident_id);
CREATE INDEX idx_tasks_due ON tasks(due_at) WHERE status NOT IN ('Done','Overdue');
CREATE INDEX idx_task_status_history_task ON task_status_history(task_id, changed_at DESC);
CREATE INDEX idx_resource_requests_incident_status ON resource_requests(incident_id, status);
CREATE INDEX idx_resource_requests_task ON resource_requests(task_id);

```typescript
export const TaskService = {
  // The single in-process entry point 03-03's `plans` module calls to
  // materialize a task from a linked plan_task_template when an incident
  // activates — per TechArch 01-components.md's explicit cross-module rule
  // ("plans emits the template list; incident-ops performs the actual task
  // creation — keeping task-creation logic in one place"). Accepts an
  // already-open transaction client so the CALLER (plans module) can wrap
  // its own template-resolution logic and this task-creation call in ONE
  // transaction if it chooses to — this function does NOT open its own
  // transaction via withTimelineTransaction, unlike the HTTP POST handler,
  // because it is designed to be called FROM WITHIN another module's
  // transaction, not as a standalone entry point.
  async createFromTemplate(
    client: PoolClient,
    params: { title: string; owner_id: string; due_at: string; incident_id: string; plan_section_id: string; requires_approval?: boolean; created_by: string }
  ): Promise<{ id: string; title: string; status: string }> {
    const result = await client.query(
      `INSERT INTO tasks (title, owner_id, incident_id, plan_section_id, due_at, requires_approval, created_by)
       VALUES ($1,$2,$3,$4,$5,$6,$7) RETURNING id, title, status`,
      [params.title, params.owner_id, params.incident_id, params.plan_section_id, params.due_at, params.requires_approval ?? false, params.created_by]
    );
    const task = result.rows[0];
    await client.query(
      `INSERT INTO task_status_history (task_id, from_status, to_status, changed_by) VALUES ($1, NULL, 'Open', $2)`,
      [task.id, params.created_by]
    );
    await TimelineService.append(client, params.incident_id, `Task created from plan template: ${task.title}`, undefined, 'brand', params.created_by, 'EPMP', { task_id: task.id, plan_section_id: params.plan_section_id });
    return task;
  },
};
```
