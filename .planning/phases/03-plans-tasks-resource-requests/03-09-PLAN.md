  <name>Task 1: Extend operating-picture markers query with resource-request triangles</name>
  <files>backend/src/modules/incident-ops/operating-picture.ts</files>
  <action>
Edit `backend/src/modules/incident-ops/operating-picture.ts` (02-03's file, already registered in `routes.ts`). Locate the existing incident-markers query (`SELECT id, name, severity, activation_level, status, ST_Y(location::geometry) as lat, ST_X(location::geometry) as lng FROM incidents WHERE status='Open' AND location IS NOT NULL AND jurisdiction_id = ANY($1)`) and, immediately after mapping its results to `MapMarker[]`, add a SECOND query and mapping step for resource requests:

```sql
SELECT rr.id, rr.resource_type, rr.quantity, rr.status,
       ST_Y(i.location::geometry) as lat, ST_X(i.location::geometry) as lng
FROM resource_requests rr
JOIN incidents i ON i.id = rr.incident_id
WHERE rr.status NOT IN ('Fulfilled', 'Declined')
  AND i.location IS NOT NULL
  AND i.jurisdiction_id = ANY($1)
```

Map each row to a `MapMarker`: `{id: rr.id, type:'resource', shape:'triangle', tone: resourceStatusToTone(rr.status), label: `${rr.quantity} ${rr.resource_type}`, status: rr.status, location:{lat,lng}}` where `resourceStatusToTone`: `Draft`→`'brand'`, `Awaiting approval`→`'warning'`, `Approved`→`'info'` (matching the UX mockup's resource-request Badge tone vocabulary 03-06 already established, reused here for marker tone consistency — a resource request's tone on the map should match its tone everywhere else in the UI). Document inline WHY `Fulfilled`/`Declined` are excluded from the `WHERE` clause entirely (not just tone-dimmed): "A completed or declined request is no longer an ACTIONABLE item needing situational awareness on the live map — per the FRD's framing of the operating picture as a live coordination surface, not a historical log (that's F7/reporting's job, Phase 4 scope) — so terminal-status requests are omitted from markers the same way Phase 2 omits Closed incidents from this same query's incident half."

Document inline why a resource request with NO linked incident location is omitted (not a broken marker): "resource_requests.location does not exist in the TechArch schema — the request inherits its incident's marker position, exactly as the FRD's criterion 4 implies ('linked to an incident or task') rather than carrying independent geography. A resource request whose incident has no location (same as any location-less incident) simply has nothing to plot — this is incomplete optional data, not a feed failure, and is handled identically to 02-03's existing incident-location-omission convention, not a new simplification."

Concatenate both mapped arrays into the single `markers` response array — this is the ENTIRE change to the response shape: no new top-level fields, no `OperatingPictureResponse` interface change, exactly matching 02-03's stated design intent that this extension requires "no response-shape change." The existing GIS schematic-fallback try/catch block (wrapping the base-layer fetch, not the incident/resource queries) is completely untouched by this plan — this is a pure additive change to which rows become markers, with zero interaction with the fallback logic success criterion 5 already covers.

Also extend `GET /api/v1/operating-picture/layers`'s single-entry Phase 2 response (`[{id:'incidents', label:'Incidents', ...}]`) with a second entry `{id:'resource-requests', label:'Resource requests', source:'EPMP', as_of: <now>, verified:true, count: <in-flight resource-request count>, checked:true}` — so the `LayerPanel` can toggle resource-request markers independently of incident markers, per the design system's documented layer-toggle contract (02-07 already wires `LayerPanel`'s `onToggle` to filter `MapCanvas`'s `markers` prop by layer, so this new layer entry is immediately functional once the frontend task below maps `type:'resource'` markers to this layer id).
