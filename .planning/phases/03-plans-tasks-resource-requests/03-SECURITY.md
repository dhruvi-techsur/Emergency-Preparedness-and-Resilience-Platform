# Security Report — Phase 3: Plans, Tasks & Resource Requests

**Mode:** verify (all 9 plan `<threat_model>` blocks loaded and checked against implemented code) + 1 additional finding surfaced by independent attack-surface review beyond the plans' own registers
**Audited:** 2026-11-17
**Verdict:** OPEN_THREATS
**Confirmed HIGH/CRITICAL:** 1

## Summary

All 18 threats (T-03-01 through T-03-18) declared across the 9 phase-3 plans' `<threat_model>` blocks were checked against the actual implemented code (not just the plan's stated intent), and every one of them is genuinely mitigated, accepted-with-documented-rationale, or correctly transferred to an already-verified server-side control. The self-approval segregation-of-duties design (T-03-06/T-03-14, app-layer 403 + `chk_no_self_approval` DB CHECK + asymmetric `review`/`create`+`edit` seed grants) is real and independently confirmed at both the application and database layer. The decline-reason requirement (T-03-09/T-03-13) and the Overdue-is-system-only state machine (T-03-01/T-03-12) are likewise genuinely enforced server-side, with the client-side affordances correctly scoped as cosmetic.

However, independent attack-surface review (per this audit's mandate to form its own judgment on security-adjacent code-review WARNINGs, not defer to their classification) surfaced **one CONFIRMED HIGH finding that none of the 9 plans' threat_model registers caught**: Phase 3's `plans`, `tasks`, and `resource_requests` modules — and the cross-module `materialize-tasks` endpoint — apply **zero jurisdiction-scope filtering** on any single-record GET, PATCH, or state-transition route, unlike Phase 2's `incidents`/`closure` modules, which established and consistently apply a `jurisdiction_id = ANY($jurisdiction_scope)` WHERE-clause guard on every equivalent operation (`fetchIncidentForMutation`). This is a cross-jurisdiction IDOR: any authenticated user holding the ordinary `tasks:edit` / `resource_requests:approve` / `plans:review` permission (not a privileged role — any seeded non-admin role) can read, approve, decline, fulfill, reassign, or edit/review ANY task, resource request, or plan in the system by UUID, regardless of which jurisdiction it belongs to or whether that jurisdiction is in the caller's `jurisdiction_scope`. OPA's Rego policy (`backend/opa/policy.rego`) has no jurisdiction concept at all — it only evaluates `role_id`/`feature`/`action` — so there is no secondary enforcement layer either; jurisdiction scoping in this codebase exists exclusively as an app-layer WHERE-clause convention, and Phase 3 does not apply it anywhere in the three new feature modules.

This does not block the self-approval workflow or any of the 18 declared threats from being individually sound — it is a new, systemic gap the plans' own threat models never registered as a trust boundary to defend (none of the 9 `<threat_model>` blocks list "client→API, resource scoped to caller's jurisdiction" as a boundary for plans/tasks/resource_requests the way Phase 2's incidents plans did). Ship decision: do not ship Phase 3 to a multi-jurisdiction deployment until this is closed; a single-jurisdiction pilot deployment is not immediately exposed (no second jurisdiction to leak across) but the gap is latent and will activate the moment a second jurisdiction or federation partner is onboarded.

## Confirmed findings

### F-01: Cross-jurisdiction IDOR on plans/tasks/resource-requests single-record routes — HIGH
- **Category:** idor (missing jurisdiction-scope / workspace-membership check)
- **Location:**
  - `backend/src/modules/incident-ops/tasks.ts:84-95` (`fetchTaskRow`) — consumed by `GET /:id` (`:340`), `PATCH /:id/owner` (`:372`), `PATCH /:id/status` (`:392`)
  - `backend/src/modules/incident-ops/resource-requests.ts:44-59` (`fetchResourceRequestRow`) — consumed by `GET /:id` (`:152`), `POST /:id/approve` (`:287`), `POST /:id/decline` (`:355`), `POST /:id/fulfill` (`:429`)
  - `backend/src/modules/plans/plans.ts:58-70` (`fetchPlanRow`) — consumed by `GET /:id` (`:254`), `PATCH /:id` (`:279`), `POST /:id/submit-review` (`:366`), `POST /:id/review` (`:440`), `POST /:id/sections/:sectionId/link-tasks` (`:542`)
  - `backend/src/modules/plans/materialize.ts:40-66` (`POST /:id/materialize-tasks`) — no jurisdiction check on either the plan or the target `incident_id`
  - `backend/src/modules/incident-ops/tasks.ts:200-225` and `resource-requests.ts:85-139` and `plans.ts:134-197` — the LIST endpoints also apply no `jurisdiction_scope` WHERE-clause (unlike `incidents.ts:237-238`'s `conditions.push('i.jurisdiction_id = ANY($1)')`)
- **Description:** Every route in this diff that reads or mutates a single `task`/`resource_request`/`plan` row by UUID resolves that row with no jurisdiction check whatsoever. Compare to Phase 2's established, still-in-use pattern: `incidents.ts:152-158`'s `fetchIncidentForMutation(incidentId, jurisdictionScope)` filters `WHERE id = $1 AND jurisdiction_id = ANY($2)`, and `closure.ts:42` calls it correctly (`fetchIncidentForMutation(incidentId, req.epmpUser!.jurisdiction_scope)`). None of the three new Phase 3 "fetch-by-id" helper functions take a `jurisdictionScope` parameter at all, and no caller passes one. `req.epmpUser.jurisdiction_scope` is available on every request (set by `rbac.ts:67`) but is simply never read in `tasks.ts`, `resource-requests.ts`, `plans.ts`, or `materialize.ts`. OPA's authorization policy (`backend/opa/policy.rego`) also has zero jurisdiction awareness — it decides purely on `role_id`/`feature`/`action` — so there is no secondary enforcement layer that could catch this either. TechArch 04-security.md §5.2 explicitly documents jurisdiction scope as a required server-side check "regardless of client," and 02c-data-plans-comms-reporting.md's own migration comment acknowledges RLS is "reserved for a later hardening pass" with app-layer WHERE-clause filtering as the interim control for this exact phase — but that interim control was never implemented for any of the three new feature modules.
- **Exploit:** Any authenticated user holding the ordinary `resource_requests:approve` permission (e.g. a `planning_logistics_chief` seeded for Jurisdiction A) can `POST /api/v1/resource-requests/{other-jurisdiction-uuid}/approve` or `/decline` against a resource request that belongs to Jurisdiction B, which they have no `jurisdiction_scope` membership in — the request succeeds with a 200, approving/declining resource allocations for an incident/jurisdiction outside their authority. Equivalently, any `eoc_director` can `POST /api/v1/plans/{other-jurisdiction-plan-id}/review` and approve a plan belonging to a jurisdiction they don't serve, and any role with `tasks:edit` can `PATCH /api/v1/tasks/{other-jurisdiction-task-id}/status` or reassign its owner. IDs are UUIDs (not enumerable by increment), so this requires the attacker to already know or guess a target UUID (e.g. leaked via a shared link, a cross-tenant support ticket, log output, or a federation partner's UI) — but once known, there is no further barrier: no 403, no 404, straight to a successful mutation. The LIST endpoints additionally return a mixed-jurisdiction result set to ANY caller with `view` permission (no jurisdiction filter applied at all, not even a soft default), meaning a `field_responder` in Jurisdiction A sees every task/resource-request/plan row across ALL jurisdictions in `GET /api/v1/tasks`, `GET /api/v1/resource-requests`, `GET /api/v1/plans` — a direct information-disclosure path requiring no guessed UUID at all.
- **Fix:** Add a `jurisdictionScope: string[]` parameter to `fetchTaskRow`, `fetchResourceRequestRow`, and `fetchPlanRow` (mirroring `fetchIncidentForMutation`'s signature exactly), threading `req.epmpUser!.jurisdiction_scope` through every call site in `tasks.ts`, `resource-requests.ts`, `plans.ts`, and `materialize.ts`. For tasks/resource-requests, the scope check is one join away via `incident_id → incidents.jurisdiction_id`; for plans, `jurisdiction_id` already lives directly on the `plans` row. Apply the identical `jurisdiction_id = ANY($N)` WHERE-clause addition to the three LIST endpoints' base conditions array (same pattern as `incidents.ts:237-238`). Return the same indistinguishable-from-404 `RECORD_NOT_FOUND`/`PLAN_NOT_FOUND` response for an out-of-scope id that these modules already use for a genuinely-nonexistent id, preserving the existing "don't leak existence" convention. `materialize-tasks` additionally needs the target `incident_id` from the request body checked against the caller's scope before any task is created against it.
- **Resolution:** fixed (08f7545) — `jurisdictionScope?: string[]` threaded through `fetchTaskRow`/`fetchResourceRequestRow`/`fetchPlanRow` (mirroring `fetchIncidentForMutation`'s signature) and every mutation/single-record-read call site in `tasks.ts`, `resource-requests.ts`, and `plans.ts`; tasks/resource-requests scope via a join to `incidents.jurisdiction_id` (standalone tasks with `incident_id IS NULL` are left unscoped, since they carry no jurisdiction data to check); plans filter directly on `plans.jurisdiction_id`. The three LIST endpoints gained an `i.jurisdiction_id = ANY($1)` / `p.jurisdiction_id = ANY($1)` base condition (same pattern as `incidents.ts`'s list route). `materialize.ts` now checks both the source plan's and the target `incident_id`'s `jurisdiction_id` against the caller's scope before creating any tasks. The create-route round-trip fetches (`fetchTaskRow(query, task.id)`, `fetchPlanRow`/`fetchPlanDetail` right after a `POST`) are deliberately left unscoped, mirroring `incidents.ts`'s own precedent for a caller fetching the record they just created. Verified: `tsc --noEmit` clean; full backend suite (11 files / 55 tests) passed on first run, including `tasks.test.ts`, `resource-requests.test.ts`, and `plans.test.ts` (which covers `materialize-tasks`).
