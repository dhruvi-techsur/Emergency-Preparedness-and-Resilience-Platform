## Resolved findings

### F-01: Cross-jurisdiction IDOR on plans/tasks/resource-requests single-record routes — HIGH
- **Status:** RESOLVED (re-verified this round via independent diff re-read + full test suite re-run + 5 new adversarial live-attack tests against the real stack, not just the fixer's commit message or claimed test counts)
- **Prior finding:** Every route that read/mutated a single `task`/`resource_request`/`plan` row by UUID (`fetchTaskRow` `tasks.ts:84-95` old, `fetchResourceRequestRow` `resource-requests.ts:44-59` old, `fetchPlanRow` `plans.ts:58-70` old, plus `materialize-tasks` and the three LIST endpoints) resolved that row with **zero jurisdiction check**, unlike Phase 2's `incidents.ts`'s `fetchIncidentForMutation(incidentId, jurisdictionScope)` precedent. Any authenticated user holding an ordinary `tasks:edit` / `resource_requests:approve` / `plans:review` permission could read, approve, decline, fulfill, reassign, edit, or review ANY task/resource-request/plan in the system by UUID regardless of jurisdiction, and the three LIST endpoints leaked a mixed-jurisdiction result set to any caller with `view` permission with no guessed UUID required at all. OPA's Rego policy has no jurisdiction concept, so there was no secondary enforcement layer either. Full original description preserved in git history (`git show 98ac46b`) and in this file's prior revision.
- **Fix applied:** Commit `08f7545` ("fix(phase-3): idor — cross-jurisdiction read/write on plans, tasks, resource-requests"), 4 files changed (+142/-41):
  - `backend/src/modules/incident-ops/tasks.ts:94-116` — `fetchTaskRow(client, taskId, jurisdictionScope?)` now joins `LEFT JOIN incidents i ON i.id = t.incident_id` and adds `AND (t.incident_id IS NULL OR i.jurisdiction_id = ANY($N))` when `jurisdictionScope` is passed. Threaded through `GET /:id` (`:369`), `PATCH /:id/owner` (`:402`), `PATCH /:id/status` (`:423`), and the LIST endpoint's base `conditions` (`:197-198`, `:226`, `:238`).
  - `backend/src/modules/incident-ops/resource-requests.ts:53-76` — `fetchResourceRequestRow(client, id, jurisdictionScope?)` joins `JOIN incidents i ON i.id = r.incident_id` (incident_id is `NOT NULL` on this table, so no standalone carve-out needed) and adds `AND i.jurisdiction_id = ANY($N)`. Threaded through `GET /:id` (`:174`), `/approve` (`:310`), `/decline` (`:379`), `/fulfill` (`:454`), and the LIST endpoint (`:113-114`, `:133`, `:146`).
  - `backend/src/modules/plans/plans.ts:66-88` — `fetchPlanRow(client, planId, jurisdictionScope?)` adds `AND p.jurisdiction_id = ANY($N)` directly (plans.jurisdiction_id is `NOT NULL` per `1700000000007...js:15`). Threaded through `GET /:id` (`:278`), `PATCH /:id` (`:305`, `:382`), `/submit-review` (`:393`, `:401`, `:448`), `/review` (`:470`, `:541`), `/sections/:sectionId/link-tasks` (`:573`), and the LIST endpoint (`:172-173`, `:192`).
  - `backend/src/modules/plans/materialize.ts:46-73` — the source-plan lookup (`:46-49`) and target-incident lookup (`:70-73`) now both carry `AND jurisdiction_id = ANY($2)` directly in the SQL, checked BEFORE any task is created.
  - Create-route round-trip fetches (fetching the record the caller just created, e.g. `tasks.ts:342`, `plans.ts:259`) are deliberately left unscoped — same precedent `incidents.ts` already established, and not a gap since the caller demonstrably just created that exact row.
  - Out-of-scope lookups return the SAME `RECORD_NOT_FOUND`/`PLAN_NOT_FOUND` 404 already used for genuinely-nonexistent ids, preserving the pre-existing "don't leak existence" convention (confirmed, not just claimed — see Verification below).
- **Verification (this re-audit round, independent of the fixer's own claims):**
  1. **Diff re-read in full:** `git show 08f7545` read line-by-line for all 4 files; confirmed every single-record call site enumerated in the original finding now passes `req.epmpUser!.jurisdiction_scope` and every helper's SQL actually applies the `ANY($N)` scope clause (not just accepts the parameter without using it).
  2. **Schema cross-check:** Read `1700000000004_plans-tasks-resources-schema.js` and `1700000000007_plans-schema.js` directly — confirmed `tasks.incident_id` is nullable (standalone-task carve-out is schema-correct), `resource_requests.incident_id` is `NOT NULL` (no carve-out needed, correctly omitted), and `plans.jurisdiction_id` is `NOT NULL` (direct filter, no join needed — correctly implemented as such).
  3. **`tsc --noEmit`:** clean, no errors.
  4. **Full existing backend suite:** `npx vitest run` — **11 files / 55 tests, 100% pass**, independently re-run (not trusted from the commit message) — exactly matches the fixer's claimed result.
  5. **New adversarial live-attack suite** (5 tests, written and run against the real Postgres+OPA+NATS docker-compose stack this round, then deleted — never committed to the repo, zero implementation files touched):
     - User A (jurisdiction A) attempts `GET`/`approve`/`decline` on a resource request belonging to jurisdiction B → all **404** (was 200 pre-fix); DB row confirmed unchanged (`status` still `Awaiting approval`, `decline_reason` still `NULL`); LIST endpoint confirmed does not return B's row to A.
     - User A attempts `GET`/`PATCH status`/`PATCH owner` (reassignment hijack) on a task linked to a jurisdiction-B incident → all **404** (was 200 pre-fix, including the owner-hijack case); DB row confirmed unchanged (`status` still `Open`, `owner_id` still user B, NOT hijacked to user A); LIST endpoint confirmed does not leak it.
     - User A attempts `GET`/`PATCH` (content hijack) on a jurisdiction-B plan → both **404** (was 200 pre-fix); DB row's `name` confirmed NOT overwritten; LIST endpoint confirmed does not leak it.
     - User A attempts `materialize-tasks` against (a) a plan that belongs to jurisdiction B, and (b) a plan in A's own scope but targeting an incident that belongs to jurisdiction B → **both return 404** (both were reachable pre-fix — case (b) in particular proves the TARGET-incident check, not just the source-plan check, is live). Cross-jurisdiction plan-review attempt by a non-scoped reviewer also confirmed blocked (plan status remained `Review`, not flipped to `Approved`).
     - **Regression check:** a standalone task created with no `incident_id` remains fully reachable by its creator/owner — `GET` returns 200, `PATCH status` returns 200 and applies, and it appears in the owner's own task LIST — confirming the fix did **not** newly break the documented "standalone task has no jurisdiction data to check" resting state. (Also confirmed, per the fix's own documented design, that a standalone task is visible to ANY caller holding `tasks:view`, not just its owner — this is the intentional, documented scope of the carve-out, not an accidental new over-exposure, since there is genuinely no jurisdiction boundary to enforce against a task with no linked incident.)
     - All 5 tests passed on the real stack. Full output and exact assertions available in the audit session transcript; the verification script itself was intentionally not retained in the repo per the read-only-on-implementation mandate.
- **Disposition:** F-01 is genuinely closed. No regression found in the one legitimate use case flagged for scrutiny (standalone tasks). Safe to ship to a multi-jurisdiction deployment.
