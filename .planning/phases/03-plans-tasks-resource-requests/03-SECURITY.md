## Summary

This is an independent re-audit of the prior round's own `03-SECURITY.md`, not a continuation of it. Every claim in that report — both the headline open finding (F-02) and the claimed-resolved finding (F-01) — was re-derived from scratch this session: by reading the current `tasks.ts`, `resource-requests.ts`, `plans.ts`, and `materialize.ts` in full, by querying the live, already-running Postgres instance directly for the structural backstops (CHECK constraints, FK presence, applied migrations), and by writing and running a brand-new, independently-authored adversarial test suite (10 tests, 2 new attack-surface items plus 8 re-verification items) against the live stack — never by trusting the prior round's assertions as given.

**F-02 is independently CONFIRMED, live, this session.** `POST /api/v1/tasks` (`tasks.ts:254-352`) and `POST /api/v1/resource-requests` (`resource-requests.ts:191-302`) both accept a caller-supplied `incident_id` in the request body and insert it directly with **no jurisdiction-scope check against that incident** before the write. An attacker holding only an ordinary `tasks:create`/`resource_requests:create` grant scoped to their own jurisdiction can `POST` a task or resource request that attaches to ANY incident UUID, including one belonging to a jurisdiction they have zero visibility into. This session's own freshly-written test (not copied from the prior round's now-deleted test files) proved: (a) both POSTs return `201` against a victim-jurisdiction incident; (b) a Timeline entry is injected onto the victim's incident, attributed to the attacker; (c) the victim's own jurisdiction-scoped task/resource-request LIST genuinely surfaces the spoofed row (because it is now a real row attached to their own incident); (d) a legitimate victim-jurisdiction approver can — and in this test's live run, did — successfully `POST .../approve` the spoofed resource request with `200`, consuming real approval attention on a request their own jurisdiction never actually created. This is a distinct code path from the already-fixed F-01 (reading/mutating an EXISTING record you don't own) — F-02 is about a NEW write that attaches itself to a foreign incident at creation time, a check `materialize.ts` (03-03) correctly applies to its own target-incident lookup but `tasks.ts`/`resource-requests.ts` do not apply to theirs. Reading OPA's full `policy.rego` this session confirms there is no jurisdiction concept at the authorization layer at all (`allow { actions := data.role_permissions[input.role_id][input.feature]; input.action in actions }`) — jurisdiction enforcement is exclusively an app-layer SQL-clause responsibility in this codebase, and these two routes are missing it.

**F-01 is independently RE-CONFIRMED FIXED**, this session, not accepted on the prior report's word. This session's own fresh adversarial suite re-attacked every F-01 vector directly: cross-jurisdiction task GET (404), cross-jurisdiction task status-PATCH (404), cross-jurisdiction task LIST non-leak, cross-jurisdiction resource-request GET+approve (both 404), cross-jurisdiction resource-request LIST non-leak, cross-jurisdiction plan GET (404) + plan LIST non-leak, cross-jurisdiction materialize-tasks via the out-of-scope source-plan path (404, driven through a genuine submit-review→cross-reviewer-approve cycle to reach real `Approved` status so a 409 status-gate couldn't mask a missing 404 jurisdiction-gate), and a standalone-task (no `incident_id`) regression check confirming the owner can still GET/PATCH their own unlinked task. All 10 tests passed in this session's live run against the real stack. The temporary test file was deleted immediately after the run; `git status --short` confirmed clean before writing this report.

Beyond F-01/F-02, this session independently re-walked the full phase file surface (not limited to the prior report's named line numbers) and re-confirmed: the no-self-approval gate (app `403` + DB `chk_no_self_approval`, both read directly off the live `\d+ plan_versions` output this session), the decline-reason-required gate (app `422` + DB `chk_decline_requires_reason`, confirmed live), Overdue's system-only PATCH rejection (`isValidTransition` rejects `next === 'Overdue'` unconditionally before consulting the transition table), the deferred `plan_section_id` FK window (confirmed closed — `fk_tasks_plan_section` present on the live `tasks` table, 7/7 expected migrations applied per `pgmigrations`), and 03-10's frontend diff (`MaterializeTasksModal.tsx` read in full this session — zero `dangerouslySetInnerHTML`/`innerHTML`, errors rendered via `ApiRequestError.message` strings never raw codes, skip reasons mapped through a human-string lookup table never the raw `reason` code; the one `grep` hit for "token" across the plans/tasks-resources page trees is a CSS custom-property comment — `--reading-max` design token — not a secret). ## Confirmed findings

### F-02: Creation-time cross-jurisdiction write — Tasks and Resource Requests accept an attacker-chosen `incident_id` with no scope check — HIGH
- **Category:** authz_bypass / IDOR-adjacent (write-side)
- **Location:** `backend/src/modules/incident-ops/tasks.ts:254-352` (`POST /api/v1/tasks`); `backend/src/modules/incident-ops/resource-requests.ts:191-302` (`POST /api/v1/resource-requests`)
- **Description:** Both POST-creation handlers accept a caller-supplied `incident_id` in the request body and use it directly in the `INSERT` (and in the same-transaction `TimelineService.append` call) with no check that the incident belongs to the caller's own `jurisdiction_scope`. `requirePermission('tasks','create')`/`requirePermission('resource_requests','create')` only checks the feature-level RBAC grant via OPA — confirmed this session by reading the full `policy.rego`, which has no jurisdiction concept whatsoever (`allow { actions := data.role_permissions[input.role_id][input.feature]; input.action in actions }`). Every other creation-adjacent route in this phase that touches a cross-module foreign key (`materialize.ts`'s target-incident lookup at `:70-73`) gets this right; these two do not.
- **Exploit (independently live-verified this session, fresh test suite written/run/deleted — `_audit_phase3_independent.test.ts`, 10 tests, 100% pass):** An authenticated user ("Re-audit Attacker") holding only an ordinary `tasks:create`/`resource_requests:create` grant scoped to Jurisdiction A `POST /api/v1/tasks` or `POST /api/v1/resource-requests` with `incident_id` set to a real incident UUID belonging to Jurisdiction B ("Re-audit Victim"'s incident). Observed live this session:
  1. Both requests succeed with `201`. The task response body confirms `incident_id` matches the victim's incident exactly.
  2. A Timeline entry is written to the victim's incident ("CROSS-JURISDICTION SPOOF TASK ...") and confirmed present via the victim's own `GET /api/v1/incidents/{id}/timeline` call.
  3. The victim's own jurisdiction-scoped `GET /api/v1/tasks?incident={id}` LIST genuinely includes the spoofed task — this is NOT a LIST-filter bug (the list filter is correct), it's that the spoofed row genuinely now belongs to the victim's own incident.
  4. The victim's own approver account successfully `POST .../approve`d the spoofed resource request and received `200` — live-observed in this session's test run, proving the confused-deputy impact concretely, not theoretically: a legitimate jurisdiction-B approval workflow can be made to act on a request jurisdiction B never actually originated.
- **Fix:** Before the `INSERT`, both handlers must look up the target `incident_id`'s `jurisdiction_id` and verify it is `= ANY(req.epmpUser!.jurisdiction_scope)` — mirroring the pattern `materialize.ts:70-73` already correctly applies (`SELECT jurisdiction_id FROM incidents WHERE id=$1 AND jurisdiction_id = ANY($2)`), returning the same `404`-style not-found convention used elsewhere in the phase when the incident doesn't resolve within scope. `tasks.ts`'s version additionally needs to allow `incident_id` to remain `NULL` (the documented standalone-task resting state, which this session's regression test confirmed is not itself a bug) without requiring a scope check in that case.

## Resolved findings

### F-01: Cross-jurisdiction IDOR on plans/tasks/resource-requests single-record read/mutate routes — HIGH
- **Status:** Confirmed FIXED, independently re-derived in THIS session (not accepted on the prior `03-SECURITY.md` round's conclusion, nor on any round before it — re-verified from scratch against the current code and a brand-new adversarial test suite written and run this session)
- **Prior finding (as independently confirmed, by reading the inline code comments documenting the pre-fix shape, to be an accurate description of a real gap that once existed):** Every route that read/mutated a single `task`/`resource_request`/`plan` row by UUID, plus the LIST endpoints, previously resolved the row with no jurisdiction check — any authenticated user holding an ordinary feature-level permission could read/approve/decline/fulfill/reassign/edit/review ANY row in the system by UUID regardless of jurisdiction.
- **Fix applied (confirmed present in the current code, this session, by direct read):**
  - `backend/src/modules/incident-ops/tasks.ts:94-116` — `fetchTaskRow(client, taskId, jurisdictionScope?)` joins `LEFT JOIN incidents i ON i.id = t.incident_id` and applies `AND (t.incident_id IS NULL OR i.jurisdiction_id = ANY($N))` when `jurisdictionScope` is passed. Threaded through `GET /:id` (`:369`), `PATCH /:id/owner` (`:402`), `PATCH /:id/status` (`:423`), and the LIST endpoint's base `conditions` (`:197-198`).
  - `backend/src/modules/incident-ops/resource-requests.ts:53-76` — `fetchResourceRequestRow(client, id, jurisdictionScope?)` joins `JOIN incidents i ON i.id = r.incident_id` and applies `AND i.jurisdiction_id = ANY($N)`. Threaded through `GET /:id` (`:174`), `/approve` (`:310`), `/decline` (`:379`), `/fulfill` (`:454`), and the LIST endpoint (`:113-114`).
  - `backend/src/modules/plans/plans.ts:66-88` — `fetchPlanRow(client, planId, jurisdictionScope?)` applies `AND p.jurisdiction_id = ANY($N)` directly. Threaded through `GET /:id` (`:278`), `PATCH /:id` (`:305`), `/submit-review` (`:393`), `/review` (`:470`), `/sections/:sectionId/link-tasks` (`:573`), and the LIST endpoint (`:172-173`).
  - `backend/src/modules/plans/materialize.ts:46-73` — the source-plan lookup (`:46-49`) and target-incident lookup (`:70-73`) both carry `AND jurisdiction_id = ANY($2)` directly in the SQL.
  - `backend/src/modules/incident-ops/incidents.ts:235-238` — `GET /api/v1/incidents` LIST route itself also leads with `i.jurisdiction_id = ANY($1)`, resolving a gap STATE.md's Phase-2 notes (T-02-03) had flagged as open at that time.
