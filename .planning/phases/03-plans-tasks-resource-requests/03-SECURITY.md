## Summary

This is an independent re-audit, not a continuation of the prior `03-SECURITY.md`'s trust chain. Every threat declared in the 9 original plans' `<threat_model>` blocks (T-03-01 through T-03-18) plus 03-10's gap-closure register (T-03-12, T-03-13) was re-verified against the code currently on disk, with live evidence gathered this session (migration files read directly, constraints confirmed against the running Postgres instance via `psql`, and the full backend test suite — 11 files / 55 tests — run live and passing). The previously-reported F-01 finding (cross-jurisdiction IDOR on single-record GET/PATCH/POST-transition routes and the three LIST endpoints) was independently re-attacked this session with a freshly-written adversarial test suite (4 tests: cross-jurisdiction task GET/status-PATCH/owner-PATCH hijack, cross-jurisdiction resource-request GET/approve/decline, cross-jurisdiction plan GET/PATCH/link-tasks/materialize-tasks via BOTH the source-plan and target-incident paths, and a standalone-task regression check) — **all 4 confirmed the fix holds**: every cross-jurisdiction attempt against an *existing* record returns 404, and the standalone-task carve-out is not a regression.

However, this round's own independent attack-surface review — auditing every POST-creation route, not just the single-record mutation/read routes the prior F-01 fix targeted — surfaced a **genuine, un-fixed HIGH finding (F-02)**: `POST /api/v1/tasks` and `POST /api/v1/resource-requests` accept a caller-supplied `incident_id` with **zero jurisdiction check on that incident at creation time**. A live adversarial test this session proved an authenticated user holding only an ordinary `tasks:create`/`resource_requests:create` grant for their own jurisdiction can create a task or resource request linked to an incident belonging to a **different jurisdiction they have no access to** — the write succeeds (201), a Timeline entry is injected onto the victim's incident, and the victim jurisdiction's own users see the spoofed record in their own list and can act on it (approve/decline/reassign) as if it were legitimate. This is a different code path from F-01 (F-01 was about reading/mutating a record you don't own; F-02 is about writing a NEW record that attaches itself to an incident you don't own) and was not declared in any of the 9 plans' `<threat_model>` registers, nor caught by the prior audit round's fix. `materialize-tasks` (03-03) and `plans.ts` were NOT found to have this gap — both independently re-verified this session to apply the `jurisdiction_id = ANY($N)` check to the target incident before writing anything (the one creation-adjacent route in the phase that gets this right).

Beyond F-02, every other declared threat across the 9 plans' registers was independently confirmed genuinely mitigated, accepted-with-documented-rationale, or correctly transferred to an already-verified server-side control — including the no-self-approval segregation of duties (app-layer 403 + `chk_no_self_approval` DB CHECK, both independently confirmed live against the running database), the decline-reason requirement (app-layer 422 + `chk_decline_requires_reason` DB CHECK, confirmed live), the Overdue-is-system-only state machine, the deferred-FK window (confirmed closed within-phase), and 03-10's frontend-only diff (no `dangerouslySetInnerHTML`, no secret/token leakage, client-side materialize gate confirmed to be a strict subset of the server's gate).

## Confirmed findings

### F-02: Creation-time cross-jurisdiction write — Tasks and Resource Requests accept an attacker-chosen `incident_id` with no scope check — HIGH
- **Category:** authz_bypass / IDOR-adjacent (write-side)
- **Location:** `backend/src/modules/incident-ops/tasks.ts:254-352` (`POST /api/v1/tasks`); `backend/src/modules/incident-ops/resource-requests.ts:191-302` (`POST /api/v1/resource-requests`)
- **Description:** Both POST-creation handlers accept a caller-supplied `incident_id` in the request body and use it directly in the `INSERT` (and in the same-transaction `TimelineService.append` call) with **no check that the incident belongs to the caller's own `jurisdiction_scope`**. `requirePermission('tasks','create')`/`requirePermission('resource_requests','create')` only checks the *feature-level* RBAC grant via OPA (`backend/opa/policy.rego` has no jurisdiction concept at all — confirmed by reading the full policy file: `allow { actions := data.role_permissions[input.role_id][input.feature]; input.action in actions }`), not which specific incident the write targets. Every OTHER creation-adjacent route in this phase that touches a cross-module foreign key (`materialize.ts`'s target-incident lookup) gets this right; these two do not.
- **Exploit (live-verified this session):** An authenticated user holding only an ordinary `tasks:create` or `resource_requests:create` grant, scoped to Jurisdiction A, can `POST /api/v1/tasks` or `POST /api/v1/resource-requests` with `incident_id` set to a real incident UUID belonging to Jurisdiction B (obtained by any means — enumeration, a leaked link, a prior legitimate cross-org interaction, etc.). The request succeeds with `201`, the new task/resource-request row is created and linked to the Jurisdiction-B incident, and a Timeline entry is written to that incident ("Task created: ...", "Resource request: ...") attributed to the Jurisdiction-A attacker. Jurisdiction B's own users — who DO have legitimate access to their own incident — then see the spoofed task/resource-request in their own `GET /api/v1/tasks`/`GET /api/v1/resource-requests` list (confirmed live: the victim's list query correctly includes it, since it genuinely now belongs to their jurisdiction's incident) and can act on it (a resource-request approver was confirmed able to `POST .../approve` the spoofed row with `200`). This is a cross-jurisdiction **injection/spam/noise-pollution** vector at minimum (an attacker can flood a rival jurisdiction's incident with bogus tasks/resource-requests demanding response), and a **confused-deputy** vector at worst (a Jurisdiction-B approver who trusts their own incident's task list could unknowingly approve/action a request they never actually needed, consuming real logistics attention during an active incident).
- **Fix:** Before the `INSERT`, both handlers must look up the target `incident_id`'s `jurisdiction_id` and verify it is `= ANY(req.epmpUser!.jurisdiction_scope)` — mirroring exactly the pattern `materialize.ts:70-73` already correctly applies to its own target-incident lookup (`SELECT jurisdiction_id FROM incidents WHERE id=$1 AND jurisdiction_id = ANY($2)`), returning the same `404 RECORD_NOT_FOUND`/`INCIDENT_NOT_FOUND` convention used elsewhere in the phase when the incident doesn't resolve within scope. `tasks.ts`'s version additionally needs to allow `incident_id` to remain `NULL` (the documented standalone-task resting state) without requiring a scope check in that case — identical to the carve-out `fetchTaskRow` already documents for reads.

## Resolved findings

### F-01: Cross-jurisdiction IDOR on plans/tasks/resource-requests single-record read/mutate routes — HIGH
- **Status:** Confirmed FIXED, independently re-verified this session (not inherited from the prior `03-SECURITY.md`'s own conclusion — re-derived from scratch against the current code and a freshly-authored adversarial test suite)
- **Prior finding (as described in the prior audit round, independently re-confirmed as the correct description of the gap by reading the pre-fix code shape documented inline in the current comments):** Every route that read/mutated a single `task`/`resource_request`/`plan` row by UUID, plus the three LIST endpoints, resolved the row with no jurisdiction check — any authenticated user holding an ordinary feature-level permission could read/approve/decline/fulfill/reassign/edit/review ANY row in the system by UUID regardless of jurisdiction.
- **Fix applied (confirmed present in the current code, this session, by direct read — not by trusting a commit message that doesn't resolve in this single-commit sandbox):**
  - `backend/src/modules/incident-ops/tasks.ts:94-116` — `fetchTaskRow(client, taskId, jurisdictionScope?)` joins `LEFT JOIN incidents i ON i.id = t.incident_id` and applies `AND (t.incident_id IS NULL OR i.jurisdiction_id = ANY($N))` when `jurisdictionScope` is passed. Threaded through `GET /:id` (`:369`), `PATCH /:id/owner` (`:402`), `PATCH /:id/status` (`:423`), and the LIST endpoint's base `conditions` (`:197-198`).
  - `backend/src/modules/incident-ops/resource-requests.ts:53-76` — `fetchResourceRequestRow(client, id, jurisdictionScope?)` joins `JOIN incidents i ON i.id = r.incident_id` and applies `AND i.jurisdiction_id = ANY($N)`. Threaded through `GET /:id` (`:174`), `/approve` (`:310`), `/decline` (`:379`), `/fulfill` (`:454`), and the LIST endpoint (`:113-114`).
  - `backend/src/modules/plans/plans.ts:66-88` — `fetchPlanRow(client, planId, jurisdictionScope?)` applies `AND p.jurisdiction_id = ANY($N)` directly. Threaded through `GET /:id` (`:278`), `PATCH /:id` (`:305`), `/submit-review` (`:393`), `/review` (`:470`), `/sections/:sectionId/link-tasks` (`:573`), and the LIST endpoint (`:172-173`).
  - `backend/src/modules/plans/materialize.ts:46-73` — the source-plan lookup (`:46-49`) and target-incident lookup (`:70-73`) both carry `AND jurisdiction_id = ANY($2)` directly in the SQL, checked before any task is created.
- **Verification (this session, independent of any prior round's claims):**
  1. Read all four files above in full on the current HEAD — confirmed every single-record call site enumerated above passes `req.epmpUser!.jurisdiction_scope` and every helper's SQL actually applies the `ANY($N)` scope clause.
  2. Confirmed live against the running Postgres: migrations `1700000000004`, `1700000000006`, `1700000000007` all applied (`SELECT name FROM pgmigrations` — 7 rows, all expected names present); `fk_tasks_plan_section` FK present on `tasks`; `chk_no_self_approval` present on `plan_versions`; `chk_decline_requires_reason` present on `resource_requests`.
  3. Ran the full existing backend suite live against the running docker-compose stack (db/opa/nats/keycloak all healthy): **11 files / 55 tests, 100% pass**, self-observed this session.
  4. Wrote and ran a brand-new, independently-authored 4-test adversarial suite (temporary, deleted immediately after — never committed) directly attacking the fixed endpoints over HTTP against the real stack: (a) cross-jurisdiction task GET/status-PATCH/owner-PATCH(hijack) all **404**, underlying row confirmed unchanged, LIST confirmed non-leaking; (b) cross-jurisdiction resource-request GET/approve/decline all **404**, row unchanged, LIST non-leaking; (c) cross-jurisdiction plan GET/PATCH(content-hijack)/link-tasks all **404**, row unchanged, LIST non-leaking, PLUS materialize-tasks blocked via BOTH the out-of-scope source-plan path and (after driving the plan through a genuine submit-review + cross-reviewer approve cycle to reach real `Approved` status, removing any ambiguity that a 409 status-gate could mask a 404 jurisdiction gate) the out-of-scope target-incident path — both correctly 404, zero tasks created in the foreign incident; (d) standalone-task (no `incident_id`) regression check — owner can still GET (200) and PATCH-status (200) their own standalone task, confirming the carve-out is not a regression. **All 4 passed.**
- **Disposition:** F-01 is genuinely closed for every single-record READ/MUTATE route and all three LIST endpoints. It does NOT, however, cover the POST-creation routes' own `incident_id` input — that gap is tracked separately as F-02 above, since it is a structurally different code path (writing a brand-new row that attaches to a foreign incident, not reading/mutating an existing row).
