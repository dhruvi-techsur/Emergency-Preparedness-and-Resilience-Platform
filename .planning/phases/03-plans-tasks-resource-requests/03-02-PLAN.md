<objective>
Build the TIME-based automatic Overdue flip: a scheduled, idempotent sweep that finds every task with `due_at < now()` and `status NOT IN ('Done','Overdue')` and flips it to `Overdue`, independent of incident status, writing the same `task_status_history`/Timeline audit trail 03-01's user-driven transitions write — satisfying success criterion 3's "a task left open past its due time automatically flips to Overdue without any manual status update" as a mechanism genuinely distinct from Phase 2's incident-closure cascade.

Purpose: This is the other half of success criterion 3, and the plan responsible for resolving the two-Overdue-mechanism question the orchestrator flagged explicitly. Resolution (restated in code, not just prose): Phase 2's `closure.ts` cascade (incident closes → ALL its open tasks flip to Overdue, synchronously, inside the closure transaction, scoped to one incident) and this plan's sweep (due_at passes → THAT task flips to Overdue, on its own schedule, regardless of incident status, scoped globally across all tasks) are two independent triggers writing to the identical `tasks.status` enum value and the identical `task_status_history`/Timeline pattern. Neither supersedes the other; a task can reach `Overdue` via either path, and once there, both paths' effects (history row, Timeline entry) are correct regardless of which path fired. The only interaction between them: the sweep's `WHERE status NOT IN ('Done','Overdue')` guard means a task the closure cascade already flipped is simply skipped by the next sweep run (idempotent no-op), and vice versa — closure's cascade query already excludes `'Overdue'` from its own `WHERE` clause, so it equally skips tasks the sweep already flipped. No race, no double-write, no competing state machine.
Output: `overdue-sweep.ts` with a transactional, idempotent sweep function and a scheduler wired into `server.ts`'s boot sequence.
</objective>

```typescript
import { pool, query } from '../../db/client';
import { TimelineService, withTimelineTransaction } from './timeline';

// Time-based Overdue flip — DISTINCT from Phase 2's closure.ts cascade.
// closure.ts flips tasks to Overdue synchronously when an incident closes
// (scoped to that incident, inside the closure transaction). THIS function
// flips tasks to Overdue on a schedule, purely because due_at has passed,
// regardless of incident status (including tasks with incident_id=NULL,
// i.e. standalone tasks). Both converge on the same tasks.status='Overdue'
// terminal value via the same task_status_history/Timeline audit pattern;
// neither supersedes the other. The WHERE clause below excludes tasks
// already 'Done' or 'Overdue', making repeated sweep runs a no-op against
// already-flipped tasks (idempotent), and symmetric with closure.ts's own
// `status NOT IN ('Done','Overdue')` exclusion — a task flipped by either
// path is simply skipped by the other on its next run, never double-flipped.
export async function runOverdueSweep(): Promise<{ flipped_count: number }> {
  const candidates = await query<{ id: string; title: string; incident_id: string | null }>(
    `SELECT id, title, incident_id FROM tasks
     WHERE due_at < now() AND status NOT IN ('Done','Overdue')`
  );

  let flippedCount = 0;
  for (const task of candidates) {
    // One transaction per task — a failure on one overdue task must not
    // roll back the sweep's progress on every other task it already flipped
    // in this run (unlike a single-incident closure cascade, which IS one
    // atomic unit; this sweep spans many independent tasks/incidents).
    await withTimelineTransaction(async (client) => {
      const updated = await client.query(
        `UPDATE tasks SET status='Overdue', updated_at=now()
         WHERE id=$1 AND status NOT IN ('Done','Overdue') RETURNING id`,
        [task.id]
      );
      if (updated.rowCount === 0) return; // already flipped by a concurrent path (closure cascade or a prior sweep tick) — no-op, not an error
      await client.query(
        `INSERT INTO task_status_history (task_id, from_status, to_status, changed_by)
         VALUES ($1, NULL, 'Overdue', NULL)`, // changed_by=NULL marks this as system-driven, per TechArch's task_status_history.changed_by comment
        [task.id]
      );
      if (task.incident_id) {
        await TimelineService.append(
          client, task.incident_id, `Task overdue: ${task.title}`, undefined, 'danger', null, 'system'
        );
      }
    });
    flippedCount += 1;
  }

  await query(
    `INSERT INTO background_jobs (job_type, status, last_run_at)
     VALUES ('task_overdue_sweep', 'running', now())
     ON CONFLICT (job_type) DO UPDATE SET status='running', last_run_at=now()`
  ).catch(() => {
    // background_jobs may use a different unique-key shape than job_type alone
    // (Phase 1's 01-01 migration owns this table) — if the ON CONFLICT target
    // doesn't match, fall back to a plain insert so the sweep itself never
    // fails due to a monitoring side-effect; document and revisit if Phase 1's
    // actual background_jobs schema differs from this assumption.
    return query(`INSERT INTO background_jobs (job_type, status, last_run_at) VALUES ('task_overdue_sweep', 'running', now())`).catch(() => {});
  });

  return { flipped_count: flippedCount };
}

let intervalHandle: NodeJS.Timeout | undefined;

export function startOverdueSweepScheduler(intervalMs: number = 60_000): void {
  // Runs every 60s by default — frequent enough that "automatically flips...
  // without any manual status update" is observable within a minute of the
  // due time passing, per FRD's implicit real-time expectation, without
  // hammering the DB. A production deployment may tune this via the
  // intervalMs param; tests call runOverdueSweep() directly without the
  // scheduler for determinism (see overdue-sweep.test.ts).
  if (intervalHandle) return; // idempotent against double-start (e.g. hot reload)
  intervalHandle = setInterval(() => {
    runOverdueSweep().catch((err) => console.error('[overdue-sweep] failed', err));
  }, intervalMs);
}
```
