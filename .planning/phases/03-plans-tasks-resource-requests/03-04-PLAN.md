  <name>Task 1: Resource-request CRUD + approve/decline/fulfill lifecycle with event-bus publish</name>
  <files>backend/src/modules/incident-ops/resource-requests.ts</files>
  <action>
Create `backend/src/modules/incident-ops/resource-requests.ts`, all routes `preHandler: requirePermission('resource_requests', <action>)` (new feature-permission, seeded in 03-07):

- `GET /api/v1/resource-requests` (`action='view'`) — query params `status`, `type`, `incident`, `page`/`page_size`. Returns `ListResponse<ResourceRequest>` per TechArch's interface (join `users.name` for `requested_by`).

- `POST /api/v1/resource-requests` (`action='create'`) — body `{ resource_type, description, quantity, incident_id, task_id?, needed_by, requesting_role }`. Validate `quantity >= 1` (DB CHECK already enforces this, but return a clean `422` before hitting the constraint violation — "Quantity must be at least 1."). Inside `withTimelineTransaction`: `INSERT INTO resource_requests (..., status) VALUES (..., 'Draft') RETURNING *`; `INSERT INTO resource_request_status_history (resource_request_id, from_status, to_status, changed_by) VALUES ($1, NULL, 'Draft', $2)`. Per the UX mockup's Create/Edit Resource Request form, submitting the FORM immediately moves `Draft → Awaiting approval` in one step (the mockup shows no separate "save as draft" action for resource requests, unlike Plans) — so this POST handler, after creating the Draft row, IMMEDIATELY also performs the Draft→Awaiting-approval transition in the SAME transaction (two status_history rows: Draft then Awaiting approval, both from this one API call) UNLESS the body carries an explicit `save_as_draft: true` flag for the rare case a caller wants to persist without submitting (document this inline as a reasonable extension since the FRD's Inputs section doesn't show a distinct "draft-save" request shape, but the schema's `Draft` status needs SOME path to be reachable as a resting state, not just a transient one-tick value). `TimelineService.append(client, incident_id, `Resource request: ${resource_type} (${description})`, undefined, 'brand', req.epmpUser.id, 'EPMP', {resource_request_id, quantity})`. After the transaction commits, call `publishEvent('resource_request.status_changed', {id, status: finalStatus, incident_id}).catch(err => req.log?.warn(err, 'event publish failed'))` — never block the response on publish failure, same non-blocking pattern 01-09 established for `user.login`. Return `201 ResourceRequest`.

- `POST /api/v1/resource-requests/{id}/approve` (`action='approve'`) — no body. Validate current `status='Awaiting approval'` (else `409 INVALID_STATUS_TRANSITION`). Inside `withTimelineTransaction`: `UPDATE resource_requests SET status='Approved', approved_by=$1, updated_at=now() WHERE id=$2 RETURNING *`; status-history row; `TimelineService.append(..., 'Resource request approved: ...', 'success', ...)`; publish event. Return `200 ResourceRequest`.

- `POST /api/v1/resource-requests/{id}/decline` (`action='approve'` — declining is itself an approval-adjacent decision requiring the same permission level as approving, document inline) — body `{ reason: string }`. If `reason` is empty/missing, return `422 DECLINE_REASON_REQUIRED` with FRD's exact message "State why this request is declined." before any write. Validate current `status='Awaiting approval'` (else `409`). Inside transaction: `UPDATE resource_requests SET status='Declined', decline_reason=$1, updated_at=now() WHERE id=$2` (the `chk_decline_requires_reason` DB constraint from 03-01's migration is the structural backstop here, same defense-in-depth pattern as 03-03's self-approval gate); status-history; `TimelineService.append(..., 'danger', ...)`; publish event. Return `200 ResourceRequest`.

- `POST /api/v1/resource-requests/{id}/fulfill` (`action='edit'`) — body `{ assigned_to: string }`. Validate current `status='Approved'` (else `409` — "Mark fulfilled" is only reachable once Approved AND assigned per the UX mockup's exact state description "Mark fulfilled action becomes available... only available once assigned"; since TechArch's schema has no separate "Assigned" status value — only `Draft/Awaiting approval/Approved/Fulfilled/Declined` — the UX mockup's "Assigned" is a SUB-STATE of `Approved` distinguished by `assigned_to IS NOT NULL`, not a distinct status enum value; document this inline as the exact reconciliation between the mockup's descriptive language and TechArch's literal 5-value enum). If `assigned_to` is empty, treat this call as ASSIGNING ONLY (not yet fulfilling): `UPDATE resource_requests SET assigned_to=$1, updated_at=now() WHERE id=$2` with NO status change and NO status-history row (assignment is metadata, not a status transition, per the schema's lack of a distinct "Assigned" status) — if `assigned_to` was ALREADY set on this request (this is a true fulfill call, not the first assign call), additionally `UPDATE ... SET status='Fulfilled', fulfilled_at=now()`, write status-history, Timeline, and publish event. Document this two-phase (assign-then-fulfill, both via this same endpoint) behavior clearly inline since the UX mockup describes them as the SAME "Mark fulfilled" action triggering an "optional assignment step" first.
  </action>
