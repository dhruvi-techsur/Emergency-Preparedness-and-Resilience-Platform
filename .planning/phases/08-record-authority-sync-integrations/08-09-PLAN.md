  <name>Task 1: POST /api/v1/plans/import — land an import/link into a real Plan</name>
  <files>backend/src/modules/plans/plans.ts</files>
  <action>
Add a new route `POST /api/v1/plans/import` — a DIFFERENT endpoint from `document-adapter.ts`'s existing `/api/v1/integrations/documents/{id}/import|link` routes (those stay exactly as-is; 08-07 already fixed their jurisdiction check). This new route is the "land it as a Plan" step the FRD describes as a separate process step from the document-system fetch itself.

```ts
app.post<{
  Body: {
    source_document_ref: string;       // external_document_id, e.g. 'DOC-EOP-001'
    mode: 'import_copy' | 'link_live';
    name: string;                      // new plan's name — ignored when plan_id is provided
    type: PlanType;                    // new plan's type — ignored when plan_id is provided
    jurisdiction_id: string;           // required when creating a new plan; ignored when plan_id is provided
    plan_id?: string;                  // when provided, attach to this EXISTING plan instead of creating a new one
  };
}>(
  '/api/v1/plans/import',
  { preHandler: requirePermission('plans', 'create') },
  async (req, reply) => {
    const { source_document_ref, mode, name, type, jurisdiction_id, plan_id } = req.body ?? ({} as never);

    // Permission check FIRST — before any plans-table write — so a
    // rejected import never leaves an orphaned Draft plan behind. This is
    // the critical ordering: importDocument/linkDocument's own access-set
    // check must run before the plan-creation transaction opens, not
    // after, which is why this route does NOT simply wrap the existing
    // create-transaction and call the adapter function afterward.
    //
    // Both importDocument() and linkDocument() perform the identical
    // accessSet.includes(externalDocId) check as their very first
    // statement (confirmed by reading document-adapter.ts directly) and
    // throw synchronously before touching the database at all — calling
    // either one FIRST, before the plans-table work below, is therefore
    // both correct and sufficient; no separate pre-flight check needed.

    let targetPlanId: string;

    if (plan_id) {
      // Attach to an EXISTING plan — same jurisdiction-scope enforcement
      // every other plans-mutating route uses (F-08-01's fix, 08-07).
      const existing = await fetchPlanRow(query, plan_id, req.epmpUser!.jurisdiction_scope);
      if (!existing) {
        return reply.code(404).send(PLAN_NOT_FOUND);
      }
      targetPlanId = plan_id;

      try {
        await linkDocument(req.epmpUser!.id, source_document_ref, targetPlanId, req.epmpUser!.jurisdiction_scope);
      } catch (err) {
        if (err instanceof Error && err.message === 'IMPORT_PERMISSION_DENIED') {
          return reply.code(403).send({
            error_code: 'IMPORT_PERMISSION_DENIED',
            message: "You don't have access to this document in the source system.",
          });
        }
        throw err;
      }
    } else {
      // No plan_id — create a NEW plan. Run the permission check (via a
      // throwaway importDocument/linkDocument call semantics) BEFORE the
      // plans-table INSERT transaction opens.
      try {
        if (mode === 'import_copy') {
          await importDocument(req.epmpUser!.id, source_document_ref);
        } else {
          // link_live with no plan_id: link first with planId=undefined
          // is NOT an option here (linkDocument always needs the real
          // target plan id to write document_links.plan_id correctly) —
          // so for link_live + new-plan, create the plan FIRST inside the
          // permission-check-first ordering by doing the access-set check
          // via a throwaway call is not possible without a real plan id
          // to pass. Resolve this by creating the plan row INSIDE the
          // same try block, immediately followed by the real linkDocument
          // call using the new plan's id — if linkDocument then throws
          // IMPORT_PERMISSION_DENIED, roll back the plan creation in the
          // catch block below so no orphan survives.
        }

        // Mirrors POST /api/v1/plans's own create transaction exactly
        // (BEGIN/INSERT plans/COMMIT), additionally setting
        // source_document_ref — the column that has existed since Phase
        // 3's own migration specifically for this moment, never
        // previously written by any code path.
        const client = await pool.connect();
        try {
          await client.query('BEGIN');
          const insertedRows = await client.query<{ id: string }>(
            `INSERT INTO plans (name, type, jurisdiction_id, owner_id, source_document_ref)
             VALUES ($1,$2,$3,$4,$5) RETURNING id`,
            [name, type, jurisdiction_id, req.epmpUser!.id, source_document_ref],
          );
          targetPlanId = insertedRows.rows[0].id;
          await client.query('COMMIT');
        } catch (err) {
          await client.query('ROLLBACK');
          req.log.error(err, 'Plan import-creation transaction failed');
          throw err;
        } finally {
          client.release();
        }

        if (mode === 'link_live') {
          // Now that the plan exists, perform the real link_live write
          // against it. importDocument() above (for import_copy mode)
          // already fully succeeded by this point — its own permission
          // check already passed, so mode==='import_copy' never reaches
          // this branch. For link_live, the access-set check inside
          // linkDocument() runs again here (cheap — it's an in-memory
          // Set lookup, not a second DB round trip) using the newly
          // created targetPlanId.
          await linkDocument(req.epmpUser!.id, source_document_ref, targetPlanId, req.epmpUser!.jurisdiction_scope);
        }
      } catch (err) {
        if (err instanceof Error && err.message === 'IMPORT_PERMISSION_DENIED') {
          // If a plan was already created in this block before the
          // failure (only possible for the link_live sub-path, since
          // import_copy's check runs BEFORE any plan INSERT), delete it
          // so no orphan survives a rejected import. targetPlanId is
          // only assigned after a successful INSERT above, so checking
          // it here is a safe, correct guard.
          if (typeof targetPlanId! !== 'undefined') {
            await query(`DELETE FROM plans WHERE id = $1`, [targetPlanId]).catch(() => {});
          }
          return reply.code(403).send({
            error_code: 'IMPORT_PERMISSION_DENIED',
            message: "You don't have access to this document in the source system.",
          });
        }
        throw err;
      }
    }

    const detail = await fetchPlanDetail(targetPlanId!, req.epmpUser!.jurisdiction_scope);
    return reply.code(201).send(detail);
  },
);
```

**Re-examine the ordering above carefully before finalizing:** the goal is "no orphaned plan survives a rejected import" (must-have 4). The simplest, most robust way to guarantee this for BOTH `import_copy` and `link_live` new-plan paths is: call the relevant permission-checking function (`importDocument` for `import_copy`, or a lightweight equivalent check for `link_live` that doesn't require a real plan id yet) and let it throw BEFORE any `plans` INSERT ever runs, full stop — rather than the delete-after-the-fact fallback sketched above for the `link_live` sub-path. Concretely: `document-adapter.ts`'s `linkDocument()` needs a real `plan_id` to write its row, but the ACCESS-SET CHECK itself (`accessSet.includes(externalDocId)`) does not depend on `plan_id` at all — it's checked before the `plan_id` is ever used. If `document-adapter.ts` exposes (or you add, as a small additive export, NOT modifying `linkDocument`'s existing behavior) a standalone `hasDocumentAccess(userId, externalDocId): boolean` check that both `importDocument`/`linkDocument` already call internally, call THAT standalone check first for the `link_live`-plus-new-plan case, throw `IMPORT_PERMISSION_DENIED` before the plan INSERT if it fails, and only then proceed to create the plan and call the real `linkDocument()` (which will trivially re-pass the same check). This avoids ever needing the delete-after-the-fact rollback path, which is strictly safer. If adding this small export to `document-adapter.ts` is out of this plan's stated `files_modified` scope, the delete-after-the-fact fallback above is an acceptable, documented alternative — but attempt the cleaner pre-check-first approach if it fits within a minimal, additive change to `document-adapter.ts`'s exports (note: this would require also updating `files_modified` — if you take this route, mention the additional file touched in your SUMMARY).

Add the necessary import: extend `plans.ts`'s existing `import { revalidateDocumentLinkPermission } from '../integration-gateway/document-adapter.js';` line to also import `importDocument, linkDocument` (do NOT add a second, duplicate import line from the same module). Confirm via grep that `document-adapter.ts` has not grown a reverse import of `plans.ts` (it should not have — 08-07's fix was self-contained to `document-adapter.ts` with no new cross-module import) before finalizing, to keep this a clean one-directional `plans.ts` → `document-adapter.ts` dependency, not a two-file cycle.

Register this route in the same `export default async function plansRoutes(app: FastifyInstance)` function, after the existing `POST /api/v1/plans` route.
