```sql
CREATE TABLE eoc_cots_config (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  vendor VARCHAR(50) NOT NULL CHECK (vendor IN ('WebEOC','Veoci','DisasterLAN')),
  endpoint_url TEXT NOT NULL,
  auth_config JSONB NOT NULL,
  active BOOLEAN NOT NULL DEFAULT true,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE eoc_cots_sync_log (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  config_id UUID NOT NULL REFERENCES eoc_cots_config(id),
  record_type VARCHAR(50) NOT NULL CHECK (record_type IN ('incident','resource_request','status','activity_log')),
  external_id VARCHAR(300),
  epmp_record_id UUID,
  direction VARCHAR(20) NOT NULL CHECK (direction IN ('inbound','outbound')),
  sync_status VARCHAR(20) NOT NULL DEFAULT 'ok',
  synced_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE eoc_cots_conflicts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  config_id UUID NOT NULL REFERENCES eoc_cots_config(id),
  record_type VARCHAR(50) NOT NULL,
  epmp_record_id UUID NOT NULL,
  epmp_value JSONB NOT NULL,
  external_value JSONB NOT NULL,
  resolution VARCHAR(20) CHECK (resolution IN ('keep_epmp','keep_external')),
  resolved_by UUID REFERENCES users(id),
  resolved_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_eoc_cots_sync_log_config_time ON eoc_cots_sync_log(config_id, synced_at DESC);
CREATE INDEX idx_eoc_cots_conflicts_unresolved ON eoc_cots_conflicts(config_id) WHERE resolution IS NULL;
```

**`eoc-cots-adapter.ts`** — mirror `gis-adapter.ts`/`hazard-feed-adapter.ts`'s structure and commenting style exactly:

1. `const KNOWN_VENDOR = 'WebEOC';` — the ONE vendor this stub treats as a live, successfully-reachable vendor (documented inline exactly like `gis-adapter.ts`'s `KNOWN_LAYER_ID` comment: no real WebEOC/Veoci/DisasterLAN credential exists in this sandbox; this stub simulates the adapter's normalized exchange-record output shape so record-authority enforcement/conflict-detection/health-wiring is built and tested against the real contract). On the success path, return 1-2 normalized `ExchangeRecord`s for the given `type` (`external_system: 'WebEOC'`, `last_modified_external: new Date().toISOString()`), reject on missing `external_system`/`last_modified_external` (structurally guaranteed, explicit-check-anyway per this codebase's established provenance style), then record success. **For `type === 'incident'` specifically, one of the 1-2 returned records MUST carry the hardcoded `external_id: 'EOC-CONFLICT-001'`** (the other, if present, gets any other fixed id, e.g. `'EOC-INCIDENT-002'`) — this is the literal, deterministic trigger point 4's conflict-detection rule and Task 2 test #4 both depend on; without this record actually being returned by the fetch, no conflict could ever be detected downstream. 4. **New exported helper, written BEFORE `runEocCotsSync` and used by both it and the route in point 5**: `export async function isRecordTypeDeclared(recordType: string): Promise<boolean>` — a direct existence check (`SELECT 1 FROM record_authority_registry WHERE record_type = $1 LIMIT 1`, imported `query` from `../../db/client.js`), returning `true` iff a row exists, `false` otherwise. **This is the structural fix for the collapsed-default problem**: `checkRecordAuthority()` (`record-authority.ts`, already existing, NEVER MODIFIED by this plan) returns the literal string `'EPMP'` in TWO genuinely different cases — "a row exists and explicitly names EPMP as authoritative" and "no row exists at all (undeclared)" — and callers that only branch on that string cannot tell those two cases apart. `isRecordTypeDeclared()` is what lets `runEocCotsSync()` and the outbound route both ask the EXISTENCE question first, independently of what `checkRecordAuthority()` would separately report.

   `export async function runEocCotsSync(): Promise<{ synced: number; conflicts: number }>` — the scheduled job, run once per the four record types (`'incident','resource_request','status','activity_log'`):
   - For each type, FIRST call `isRecordTypeDeclared(type)`. **If `false` (undeclared), skip this type ENTIRELY — do not call `fetchExchangeRecords`, do not write to `eoc_cots_sync_log`, do not check for conflicts.** This is the literal "undeclared record types are not synced" FRD rule, now structurally impossible to bypass: an undeclared type never reaches the fetch/log/conflict logic below at all.
   - Only for a DECLARED type, call `fetchExchangeRecords(type)` inside a per-type `try/catch` (one type's failure must not abort the others — same per-item fault isolation as Phase 7's per-feed loop).
   - **Record-authority check, now meaningful because declaration is already confirmed** (F13's Validation rule, literal): `const authority = await checkRecordAuthority(type)` (imported from `./record-authority.js`). Since this point is only reached for a type we already know has a registry row, `authority` here reliably means "the row's actual declared value," never the collapsed undeclared-default. If `authority === 'EPMP'`, treat the inbound value as a CANDIDATE and check for conflict against the current EPMP-side value (see below) rather than applying it directly. If `authority !== 'EPMP'` (external system is authoritative), accept and log the inbound value directly into `eoc_cots_sync_log` (`direction: 'inbound'`, `sync_status: 'ok'`) with provenance noting the external source — no application-side write to an EPMP-owned table happens in THIS MVP-depth stub (TechArch's `eoc_cots_sync_log` is itself the sync-cycle's own audit record; this plan does not additionally mutate `incidents`/`resource_requests` rows, since the FRD's MVP depth scopes the exchange to the four logged record types with no literal field-level incident-table write path specified — document this as an explicit scope boundary, matching 02-01/03-09's own precedent of documenting MVP-depth simplifications inline rather than over-building).
   - **Conflict detection**: for the `authority === 'EPMP'` case, compare the inbound `ExchangeRecord.payload` against a simple EPMP-side "current value" stand-in (since this MVP stub has no literal field-level diff target — use a deterministic test-reproducible rule: if the inbound record's `external_id` matches the literal seeded test marker `'EOC-CONFLICT-001'` — the exact id point 2 wires into the `'incident'`-type fetch response — ALWAYS detect a conflict, documented inline exactly like `hazard-feed-adapter.ts`'s/`cad-adapter.ts`'s own recognized-trigger convention). On conflict: `INSERT INTO eoc_cots_conflicts (config_id, record_type, epmp_record_id, epmp_value, external_value) VALUES (...)` — `epmp_value`/`external_value` both populated as JSONB, `resolution` left `NULL` (never auto-resolved — F13's hard constraint, "never auto-resolved by any heuristic e.g. last-write-wins"). On no conflict: log to `eoc_cots_sync_log` as a normal inbound sync.
   - Find-or-update a `background_jobs` row scoped to `job_type = 'sync_reconciliation'` EXCLUSIVELY — **confirm this value is unused by grepping `grep -rn "sync_reconciliation" backend/src` BEFORE using it** (it exists in Phase 1's original CHECK constraint list but — per this plan's own research — no other adapter has claimed it yet, making it the correct, already-available value rather than requiring a new migration ALTER like Plan 07-02's `'cad_ingestion'` needed). On any DECLARED type's failure this run, set `status = 'backoff'`, bump `failure_count`, `next_retry_at` via `computeBackoff(failureCount)` (imported from `./webhook-delivery-worker.js`, never reimplemented); on all-declared-types-success, set `status = 'idle'`, `last_run_at = now()` (an undeclared, skipped type is neither a success nor a failure for this bookkeeping — it simply never participates).
