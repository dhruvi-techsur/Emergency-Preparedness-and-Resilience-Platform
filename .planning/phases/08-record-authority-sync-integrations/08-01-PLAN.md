CREATE TABLE eoc_cots_config (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  vendor VARCHAR(50) NOT NULL CHECK (vendor IN ('WebEOC','Veoci','DisasterLAN')),
  endpoint_url TEXT NOT NULL,
  auth_config JSONB NOT NULL,
  active BOOLEAN NOT NULL DEFAULT true,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()

CREATE TABLE eoc_cots_sync_log (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  config_id UUID NOT NULL REFERENCES eoc_cots_config(id),
  record_type VARCHAR(50) NOT NULL CHECK (record_type IN ('incident','resource_request','status','activity_log')),
  external_id VARCHAR(300),
  epmp_record_id UUID,
  direction VARCHAR(20) NOT NULL CHECK (direction IN ('inbound','outbound')),
  sync_status VARCHAR(20) NOT NULL DEFAULT 'ok',
  synced_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE eoc_cots_conflicts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  config_id UUID NOT NULL REFERENCES eoc_cots_config(id),
  record_type VARCHAR(50) NOT NULL,
  epmp_record_id UUID NOT NULL,
  epmp_value JSONB NOT NULL,
  external_value JSONB NOT NULL,
  resolution VARCHAR(20) CHECK (resolution IN ('keep_epmp','keep_external')),
  resolved_by UUID REFERENCES users(id),
  resolved_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_eoc_cots_sync_log_config_time ON eoc_cots_sync_log(config_id, synced_at DESC);
CREATE INDEX idx_eoc_cots_conflicts_unresolved ON eoc_cots_conflicts(config_id) WHERE resolution IS NULL;

**`eoc-cots-adapter.ts`** — mirror `gis-adapter.ts`/`hazard-feed-adapter.ts`'s structure and commenting style exactly:

1. `const KNOWN_VENDOR = 'WebEOC';` — the ONE vendor this stub treats as a live, successfully-reachable vendor (documented inline exactly like `gis-adapter.ts`'s `KNOWN_LAYER_ID` comment: no real WebEOC/Veoci/DisasterLAN credential exists in this sandbox; this stub simulates the adapter's normalized exchange-record output shape so record-authority enforcement/conflict-detection/health-wiring is built and tested against the real contract). Find-or-insert a single `eoc_cots_config` row for `'WebEOC'` on first use (same lazy find-or-insert pattern Plan 07-02's `cad-adapter.ts` uses for its own `cad_config` row — read that file's Task 1 point 1 for the exact idiom).

2. `export async function fetchExchangeRecords(type: 'incident'|'resource_request'|'status'|'activity_log', since?: string): Promise<ExchangeRecord[]>` — if the configured vendor is not `KNOWN_VENDOR` OR an explicit test-injection trigger fires (a `since` value of the literal string `'FORCE_AUTH_FAILURE'`, documented inline exactly like `cad-adapter.ts`'s `simulateFailure` param doc comment), record the failure (see point 3) and throw `EOC_ADAPTER_AUTH_FAILED: ...`. On the success path, return 1-2 normalized `ExchangeRecord`s for the given `type` (`external_system: 'WebEOC'`, `last_modified_external: new Date().toISOString()`), reject on missing `external_system`/`last_modified_external` (structurally guaranteed, explicit-check-anyway per this codebase's established provenance style), then record success.

3. `async function recordEocCotsHealth(status: 'online'|'offline'): Promise<void>` — UPSERT into `integration_health`: `system_name = 'WebEOC'` (the vendor name itself, per F13's "System name" column — matching S13.1's literal "System name" header), `last_sync_at = now()`, `direction = 'bidirectional'` (F13's adapter both reads AND writes per its approved contract — distinct from Plan 07-01/07-02's `'inbound'`-only adapters), `record_authority = 'WebEOC'` for record types the registry declares external-authoritative, bump/reset `error_count` exactly like Plan 07-01/07-02's `recordFeedHealth`/`recordCadHealth`.

4. `export async function runEocCotsSync(): Promise<{ synced: number; conflicts: number }>` — the scheduled job, run once per the four record types (`'incident','resource_request','status','activity_log'`):
   - For each type, call `fetchExchangeRecords(type)` inside a per-type `try/catch` (one type's failure must not abort the others — same per-item fault isolation as Phase 7's per-feed loop).
   - **Record-authority check FIRST, before applying anything** (F13's Validation rule, literal): `const authority = await checkRecordAuthority(type)` (imported from `./record-authority.js`). If `authority === 'EPMP'`, treat the inbound value as a CANDIDATE and check for conflict against the current EPMP-side value (see below) rather than applying it directly. If `authority !== 'EPMP'` (external system is authoritative), accept and log the inbound value directly into `eoc_cots_sync_log` (`direction: 'inbound'`, `sync_status: 'ok'`) with provenance noting the external source — no application-side write to an EPMP-owned table happens in THIS MVP-depth stub (TechArch's `eoc_cots_sync_log` is itself the sync-cycle's own audit record; this plan does not additionally mutate `incidents`/`resource_requests` rows, since the FRD's MVP depth scopes the exchange to the four logged record types with no literal field-level incident-table write path specified — document this as an explicit scope boundary, matching 02-01/03-09's own precedent of documenting MVP-depth simplifications inline rather than over-building).
   - **Conflict detection**: for the `authority === 'EPMP'` case, compare the inbound `ExchangeRecord.payload` against a simple EPMP-side "current value" stand-in (since this MVP stub has no literal field-level diff target — use a deterministic test-reproducible rule: if the inbound record's `external_id` matches the literal seeded test marker `'EOC-CONFLICT-001'`, ALWAYS detect a conflict, documented inline exactly like `hazard-feed-adapter.ts`'s/`cad-adapter.ts`'s own recognized-trigger convention). On conflict: `INSERT INTO eoc_cots_conflicts (config_id, record_type, epmp_record_id, epmp_value, external_value) VALUES (...)` — `epmp_value`/`external_value` both populated as JSONB, `resolution` left `NULL` (never auto-resolved — F13's hard constraint, "never auto-resolved by any heuristic e.g. last-write-wins"). On no conflict: log to `eoc_cots_sync_log` as a normal inbound sync.
   - Find-or-update a `background_jobs` row scoped to `job_type = 'sync_reconciliation'` EXCLUSIVELY — **confirm this value is unused by grepping `grep -rn "sync_reconciliation" backend/src` BEFORE using it** (it exists in Phase 1's original CHECK constraint list but — per this plan's own research — no other adapter has claimed it yet, making it the correct, already-available value rather than requiring a new migration ALTER like Plan 07-02's `'cad_ingestion'` needed). On any type's failure this run, set `status = 'backoff'`, bump `failure_count`, `next_retry_at` via `computeBackoff(failureCount)` (imported from `./webhook-delivery-worker.js`, never reimplemented); on all-types-success, set `status = 'idle'`, `last_run_at = now()`.

5. `export async function eocCotsRoutes(app: FastifyInstance)`:
   - `GET /api/v1/integrations/eoc-cots/exchange-records?type={...}&since={...}` (`preHandler: requirePermission('admin','view')` — this is admin-console integration data, matching F13's S13.1 "embedded in F8 S8.6" framing) — calls `fetchExchangeRecords` live and returns the array per TechArch's literal shape.

## Trust Boundaries

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-01 | Tampering | `runEocCotsSync()`'s inbound-apply branch | mitigate | `checkRecordAuthority(type)` is called and its result branches the logic BEFORE any value is treated as authoritative or compared for conflict — an undeclared record type is skipped entirely (zero `eoc_cots_sync_log` rows written), never defaulted to "apply anyway" |
| T-08-02 | Tampering | Conflict auto-resolution | mitigate | `eoc_cots_conflicts.resolution` is NEVER set by `runEocCotsSync()` itself — only Plan 08-03's dedicated resolve route (gated on an explicit named-person action) can set it; this plan's own migration leaves the column nullable with no default and no code path in this file writes to it |
| T-08-03 | Information disclosure | `GET /api/v1/integrations/eoc-cots/exchange-records`, `/conflicts`, `/health` | mitigate | Gated `requirePermission('admin','view')`, matching this codebase's existing admin-console integration-data permission convention (federation-grants.ts, record-authority.ts) |
| T-08-04 | Elevation of privilege | `POST /api/v1/integrations/eoc-cots/exchange-records` (outbound) | mitigate | Gated `requirePermission('admin','edit')` AND re-validates `checkRecordAuthority(type) === 'EPMP'` server-side before accepting an outbound write request — a caller cannot push an EPMP-originated change for a record type the registry says EPMP doesn't own, even with `admin:edit` |
| T-08-05 | Denial of service | `runEocCotsSync()`'s per-type loop | mitigate | Each of the four record types is wrapped in its own `try/catch` (per-item fault isolation, same pattern as Phase 7's per-feed loop) — one type's adapter failure cannot abort the other three's sync attempts within the same run |
