Create `eoc-cots-conflicts.ts`, a NEW file (deliberately separate from Plan 08-01's `eoc-cots-adapter.ts`, per that plan's own documented decision to keep the resolve route isolated):

```
POST /api/v1/integrations/eoc-cots/conflicts/{id}/resolve
Request: { resolution: 'keep_epmp' | 'keep_external', resolved_by: string }
```
(exact shape per `project_specs/FRD/Y1d-api-integrations.md` §EOC COTS)

- `preHandler: requirePermission('admin', 'edit')` — conflict resolution is an admin-console/IT-SecOps action per F13's "typically PER-01 or PER-05 admin facet" framing; grant this action-level in seed.ts if it doesn't already exist on `secops_admin`'s `admin` permission row (check first — `secops_admin` already holds the full `['view','create','edit','approve']` set on `admin` per the existing seed, so this likely needs NO new seed change; confirm via `grep -n "secopsAdminId.*'admin'" backend/scripts/seed.ts` and only add a seed change if the existing grant doesn't already include `edit`).
- **Caller-identity equality** (mirrors `sync-conflicts.ts`'s and `hazard-feed-adapter.ts`'s established pattern exactly, NOT a role-permission lookup on the asserted id): if `resolved_by !== req.epmpUser!.id`, return `403 { error_code: 'VERIFICATION_REQUIRES_NAMED_USER', message: 'Resolve this conflict as yourself — you cannot resolve on behalf of another person.' }`.
- Fetch the conflict row by `id`; if not found, `404 { error_code: 'EOC_CONFLICT_NOT_FOUND', message: 'This conflict no longer exists or has already been resolved.' }`. If `resolution IS NOT NULL` already (someone else resolved it first, or a double-submit), return the SAME 404-shaped response rather than silently succeeding a second time — resolving twice is not idempotent by design (F13's "never silently overwritten" rule extends to the resolution action itself: a second click must not look like it worked).
- On `resolution === 'keep_epmp'`: `UPDATE eoc_cots_conflicts SET resolution='keep_epmp', resolved_by=$1, resolved_at=now() WHERE id=$2 AND resolution IS NULL` (the `AND resolution IS NULL` guard is the race-safety mechanism — a concurrent double-click resolves at most once, matching `activation.ts`'s row-lock-adjacent discipline though a lighter WHERE-guard suffices here since there's no multi-statement transaction to protect). ALSO insert a row into `eoc_cots_sync_log` (`direction: 'outbound'`, `sync_status: 'ok'`, `record_type` = the conflict's own `record_type`, `epmp_record_id` = the conflict's `epmp_record_id`) — this is F13's "written back through the adapter to the external system if EPMP's value was kept" requirement, logged as the outbound write (this stub does not make a live vendor call, matching every other adapter's stub-depth convention; the log entry IS the "written back" proof at this MVP depth).
- On `resolution === 'keep_external'`: same `UPDATE` with `resolution='keep_external'`, PLUS an `eoc_cots_sync_log` row with `direction: 'inbound'` (the external value is now accepted/applied locally — logged as the inbound acceptance).
- If zero rows were affected by the `UPDATE` (lost the race, or already resolved — the `AND resolution IS NULL` guard caught it), return the SAME 404-shaped `EOC_CONFLICT_NOT_FOUND` response.
- On success, return `200` with the updated conflict row (`{ id, record_type, resolution, resolved_by, resolved_at }`).
- Call `AuditService.record(req.epmpUser!.id, 'eoc_cots_conflict_resolve', 'eoc_cots_conflict', id, { resolution })` (matches `record-authority.ts`'s established audit-on-sensitive-write convention exactly — resolving an EOC COTS conflict is exactly this kind of sensitive, auditable administrative action).

Register this file's default export in `integration-gateway/routes.ts` alongside the other integration-gateway route plugins (append).
