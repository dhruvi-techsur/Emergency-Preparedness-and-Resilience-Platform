# Security Report — Phase 8: Record Authority & Sync Integrations

**Mode:** retroactive
**Audited:** 2026-11-20
**Verdict:** OPEN_THREATS
**Confirmed HIGH/CRITICAL:** 1

## Summary

This phase shipped two new adapter contracts (EOC COTS/WebEOC-class bidirectional sync with admin-gated conflict resolution, and a permission-aware SharePoint-class document browse/import/link flow) plus a background "Link live" document-change-detection sync job wired into `plans.ts`'s reading view. The EOC COTS conflict-resolution route (`eoc-cots-conflicts.ts`) is well-built: caller-identity equality, a race-safe `WHERE resolution IS NULL` UPDATE guard, `admin`/`edit`-gated (held only by `secops_admin` per seed), and audited — all claims in the SUMMARY/REVIEW hold up to direct grep/test verification, and the sole-writer claims for `eoc_cots_conflicts.resolution`, `document_links.content_status`, and `document_links.permission_status` are structurally confirmed (exactly one UPDATE site each across the whole diff). The document adapter's permission-boundary enforcement (server-side re-check at call time, not client-filtered) is real and proven by a genuine direct-API-bypass test. However, one HIGH-severity IDOR survives adversarial refutation: `POST /api/v1/integrations/documents/:id/link` accepts a caller-supplied `plan_id` in its request body and passes it straight into `document_links`'s INSERT with **no existence check, no ownership check, and no jurisdiction-scope check** — every other mutating route in `plans.ts` (including this very phase's own new acknowledge route) enforces `fetchPlanRow(..., jurisdiction_scope)` before touching a plan by id, but `linkDocument()` in `document-adapter.ts` never calls into `plans.ts` at all. A user holding `plans:edit` in any jurisdiction (held broadly — `planning_logistics_chief` — across the whole org) can attach a document link (including a flagged 'link_live' row) to ANY plan UUID in the system, regardless of jurisdiction scope or even `plans:view` on that target plan, polluting a foreign jurisdiction's plan with an attacker-controlled document link that will appear as legitimate content in that other team's reading view. All other candidate findings (command injection in migrations/seed, secret leakage, path traversal, unsafe deserialization, facility-field over-exposure, conflict-resolve authz/race-safety) were examined and refuted as safe. Ship decision: fix the `plan_id` ownership/jurisdiction check in `linkDocument`'s route handler before this phase can be considered closed.

## Confirmed findings

### F-08-01: `linkDocument`'s `plan_id` parameter bypasses jurisdiction-scope enforcement — HIGH
- **Category:** idor (missing workspace/jurisdiction-membership check)
- **Location:** `backend/src/modules/integration-gateway/document-adapter.ts:151-172` (`linkDocument`), `:432-449` (`POST /api/v1/integrations/documents/:id/link` route handler)
- **Description:** The route handler extracts `req.body?.plan_id` and passes it directly into `linkDocument(userId, externalDocId, planId)`, which writes `INSERT INTO document_links (plan_id, external_document_id, source_system, mode, imported_by) VALUES ($1, $2, $3, 'link_live', $4)` with `planId` used verbatim. No code path anywhere in `document-adapter.ts` calls `fetchPlanRow` or checks `req.epmpUser!.jurisdiction_scope` against the target plan's `jurisdiction_id`, nor does it verify the plan is even one the caller holds `plans:view` on. This is a direct structural inconsistency with the rest of the phase and the rest of `plans.ts`: every single mutating plans.ts route (`PATCH /:id`, `POST /:id/review`, `POST /:id/sections/:sectionId/link-tasks`, and this very phase's own new `PATCH /:id/document-links/:linkId/acknowledge`) calls `fetchPlanRow(query, id, req.epmpUser!.jurisdiction_scope)` first and 404s if the plan isn't in-scope — but the document-link route, despite writing into the exact same `document_links` table keyed by `plan_id`, has no equivalent check at all. The only gate on the route is `requirePermission('plans', 'edit')`, which is held broadly (`planning_logistics_chief` org-wide, not scoped per-jurisdiction by RBAC — jurisdiction scoping in this codebase is enforced at the query/app layer per plan, never by OPA).
- **Exploit:** An authenticated user holding `plans:edit` (e.g. `planning_logistics_chief`) in Jurisdiction A learns or guesses a valid plan UUID belonging to Jurisdiction B (plan ids are not secret — they appear in shareable URLs `/plans/{id}`, audit logs, support tickets, or could be obtained via any other IDOR/leak in the wider system). They call `POST /api/v1/integrations/documents/DOC-SOP-002/link` with `{ "plan_id": "<jurisdiction-B-plan-uuid>" }`. Because their own delegated document-access set (not the target plan) is the only thing checked, the call succeeds and writes a `mode='link_live'` `document_links` row against the foreign plan. On Jurisdiction B's next `GET /api/v1/plans/{id}`, their own legitimate users (who ARE in-scope for that plan) see the attacker-injected document link appear in the response's `document_links` array, and — once `runDocumentLinkSync`'s fixed `DOC-SOP-002` trigger fires — a "Source changed, review" Alert surfaces in `PlanDetail.tsx`'s reading view for content the Jurisdiction-B team never linked, consented to, or can trace to anyone in their own jurisdiction's audit trail (no audit event is emitted on link creation either — only on the later `acknowledge` action). This is a cross-tenant integrity violation of the identical kind the FRD's own jurisdiction-scope model was built to prevent, and it bypasses that model structurally, not through a mistaken permission grant.
- **Fix:** In the `/:id/link` route handler (or inside `linkDocument` itself), when `plan_id` is provided, call the existing `fetchPlanRow(query, planId, req.epmpUser!.jurisdiction_scope)` helper (already imported transitively via `plans.ts`, or re-exported for cross-module use) and return the same `PLAN_NOT_FOUND`-shaped 404 if the plan doesn't exist or isn't in the caller's jurisdiction scope — mirroring the exact pattern every other plan-mutating route in this phase and prior phases already uses.
