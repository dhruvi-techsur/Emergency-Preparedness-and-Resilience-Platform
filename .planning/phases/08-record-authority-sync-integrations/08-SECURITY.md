## Confirmed findings

### F-08-01: `linkDocument`'s `plan_id` parameter bypasses jurisdiction-scope enforcement — HIGH
- **Status:** UNCHANGED from prior audit — not fixed. A gap-closure plan (`08-07-PLAN.md`) exists describing the intended fix, but it has not been executed (no `08-07-SUMMARY.md` exists anywhere in the phase directory) and the implementation file is byte-identical to the prior audit's citation.
- **Category:** idor (missing workspace/jurisdiction-membership check)
- **Location:** `backend/src/modules/integration-gateway/document-adapter.ts:151-172` (`linkDocument`), `:432-449` (`POST /api/v1/integrations/documents/:id/link` route handler) — line numbers re-verified identical to the prior audit's citation; `git diff c3352b6..HEAD -- backend/src/modules/integration-gateway/document-adapter.ts` shows the file was added once (`c19d384`, before the prior audit's own base commit) and modified only once since (`ad51b49`, the W1 fix, which touches only lines 58-79 — the `simulateDocumentAccessRevocation` addition — and does not touch `linkDocument` or the route handler at all).
- **Description:** The route handler extracts `req.body?.plan_id` and passes it directly into `linkDocument(userId, externalDocId, planId)`, which writes `INSERT INTO document_links (plan_id, external_document_id, source_system, mode, imported_by) VALUES ($1, $2, $3, 'link_live', $4)` with `planId` used verbatim (confirmed at `document-adapter.ts:164-169`, unchanged). Direct re-verification this audit: `grep -n "jurisdiction" backend/src/modules/integration-gateway/document-adapter.ts` returns **zero matches** — no code path in the file calls `fetchPlanRow` or checks `req.epmpUser!.jurisdiction_scope` against the target plan's `jurisdiction_id`, nor verifies the caller holds `plans:view` on that specific plan. Every mutating `plans.ts` route (`PATCH /:id`, `POST /:id/review`, `POST /:id/sections/:sectionId/link-tasks`, and this same phase's own `PATCH /:id/document-links/:linkId/acknowledge`) calls `fetchPlanRow(query, id, req.epmpUser!.jurisdiction_scope)` first and 404s if the plan isn't in-scope (`plans.ts:360,448,525,628,683` — all five call sites re-confirmed present and unchanged) — but the document-link route, despite writing into the exact same `document_links` table keyed by `plan_id`, still has no equivalent check. The only gate is `requirePermission('plans', 'edit')`, held broadly org-wide (not scoped per-jurisdiction by RBAC).
- **Exploit:** Unchanged from the prior audit. An authenticated user holding `plans:edit` (e.g. `planning_logistics_chief`) in Jurisdiction A learns or guesses a valid plan UUID belonging to Jurisdiction B. They call `POST /api/v1/integrations/documents/DOC-SOP-002/link` with `{ "plan_id": "<jurisdiction-B-plan-uuid>" }`. The call succeeds and writes a `mode='link_live'` `document_links` row against the foreign plan — visible to Jurisdiction B's legitimate users on their next `GET /api/v1/plans/{id}`, and will trigger `runDocumentLinkSync`'s "Source changed, review" alert in their reading view for content they never linked or consented to. No audit event is emitted on link creation (only on later acknowledge), so this is also unattributable in Jurisdiction B's own audit trail.
- **Fix:** In the `/:id/link` route handler (or inside `linkDocument` itself), when `plan_id` is provided, call the existing `fetchPlanRow(query, planId, req.epmpUser!.jurisdiction_scope)` helper and return the same `PLAN_NOT_FOUND`-shaped 404 if the plan doesn't exist or isn't in the caller's jurisdiction scope — mirroring every other plan-mutating route. `08-07-PLAN.md` already describes this exact fix direction; it needs to be executed, reviewed, and re-audited before this finding can move to Resolved.
- **Resolution:** fixed (a5230d4) — added a private `planIsInScope(planId, jurisdictionScope)` helper in `document-adapter.ts` itself (not a cross-module import from `plans.ts`, avoiding the reverse-import-cycle risk `08-07-PLAN.md` flagged) mirroring `fetchPlanRow`'s `jurisdiction_id = ANY($2)` scoping clause. `linkDocument()` gained an optional 4th `jurisdictionScope?: string[]` parameter; when `planId` is provided it must now resolve in-scope or the function throws `Error('PLAN_NOT_FOUND')`, caught by the route handler and mapped to the identical `PLAN_NOT_FOUND` 404 shape `plans.ts` uses elsewhere. The route handler now passes `req.epmpUser!.jurisdiction_scope` as the 4th argument. `backend/scripts/seed.ts:1334`'s `linkDocument(plannerUser.id, 'DOC-SOP-002', uatUnlinkedPlan.id)` call site was updated to pass `[jurisdiction.id]` (confirmed via grep as the in-scope jurisdiction variable already used to create `uatUnlinkedPlan` itself) as a 4th argument. Three new integration tests added to `facility-document-adapter.test.ts`'s existing `describe('Plan 08-02: F17 document adapter — permission-boundary enforcement', ...)` block prove: (1) a cross-jurisdiction `plan_id` is rejected 404 `PLAN_NOT_FOUND` with zero `document_links` row written; (2) a nonexistent `plan_id` is rejected 404 `PLAN_NOT_FOUND` (never a 500 FK-violation); (3) a legitimate in-scope `plan_id` still succeeds 201 with a real row written. A 4th test confirms `linkDocument()` called with no `jurisdictionScope`/no `planId` (the standalone-import-style call) is unaffected. Verification: `npx tsc --noEmit` clean; `grep -n "PLAN_NOT_FOUND" document-adapter.ts` → 5 matches; targeted test file 14/14 passed; full backend suite 148/148 passed (22 files); `npm run seed` ran idempotently (`document_links=0 inserted/1 already-present`).
