```sql
CREATE TABLE field_reports (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  client_report_id VARCHAR(100) NOT NULL UNIQUE,
  incident_id UUID REFERENCES incidents(id),
  observation_type VARCHAR(100) NOT NULL,
  description TEXT,
  location GEOGRAPHY(POINT, 4326),
  location_accuracy_m NUMERIC,
  submitted_by UUID NOT NULL REFERENCES users(id),
  captured_at TIMESTAMPTZ NOT NULL,
  synced_at TIMESTAMPTZ,
  sync_status VARCHAR(20) NOT NULL DEFAULT 'synced' CHECK (sync_status IN ('synced','conflict','failed')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT chk_report_not_empty CHECK (description IS NOT NULL OR location IS NOT NULL)
);

CREATE TABLE field_report_photos (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  field_report_id UUID NOT NULL REFERENCES field_reports(id),
  storage_ref TEXT,
  upload_status VARCHAR(20) NOT NULL DEFAULT 'pending' CHECK (upload_status IN ('pending','uploaded','failed')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE sync_conflicts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  entity_type VARCHAR(50) NOT NULL,
  entity_id UUID NOT NULL,
  field_version JSONB NOT NULL,
  eoc_version JSONB NOT NULL,
  resolution VARCHAR(20) CHECK (resolution IN ('keep_mine','keep_eoc')),
  resolved_by UUID REFERENCES users(id),
  resolved_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_field_reports_incident ON field_reports(incident_id);
CREATE INDEX idx_field_reports_location ON field_reports USING GIST(location);
CREATE INDEX idx_field_reports_submitted_by ON field_reports(submitted_by);
CREATE INDEX idx_field_report_photos_report ON field_report_photos(field_report_id);
CREATE INDEX idx_sync_conflicts_unresolved ON sync_conflicts(entity_type) WHERE resolution IS NULL;
```

All routes `preHandler: requirePermission('field_reports', <action>)` (new `field_reports` feature-permission — document inline that the seed grant for this permission belongs to 05-04, the seed/RBAC plan, same split every prior phase established between schema/routes and seed data). From `project_specs/TechArch/03b-api-incident-ops.md`'s "Field Reports (F6)" table, exact contract:

```
POST /api/v1/field-reports
Request: FieldReport { client_report_id, incident_id?, observation_type, description?, location?, location_accuracy_m?, captured_at }
Response: 201 { id, sync_status }
Errors: 422 REPORT_EMPTY, 507 QUEUE_STORAGE_FULL (client-side guard, not server-enforced)

POST /api/v1/field-reports/sync-batch
Request: { reports: FieldReport[] }  -- creation order
Response: { results: [{ client_report_id, status: 'synced'|'conflict'|'failed', conflict_id? }] }

POST /api/v1/field-reports/{id}/photos
Request: multipart
Response: 204
Errors: 500 PHOTO_UPLOAD_FAILED (non-blocking)
```

1. **`POST /api/v1/field-reports`** (`action='create'`) — idempotent via `client_report_id`'s UNIQUE constraint: first `SELECT id, sync_status FROM field_reports WHERE client_report_id=$1`; if a row already exists, return `201 { id, sync_status }` for THAT row unchanged (no second INSERT, no error) — this is what makes a flaky-retry resubmission safe. If not found, validate `description IS NOT NULL OR location IS NOT NULL` client-side-mirroring server check (mirrors the DB's own `chk_report_not_empty` CHECK — return `422 REPORT_EMPTY` with message "A report needs a description or a location — add one before submitting." before attempting the INSERT, so the CHECK-constraint violation path is never hit in the happy case). Insert with `submitted_by: req.epmpUser!.id`, `sync_status: 'synced'` (this single-report path has no batch-conflict-detection race — conflicts are only possible from the batch endpoint reconciling an item that was queued offline while something else changed server-side in the gap). If `incident_id` is present, wrap in `withTimelineTransaction` and append a Timeline entry `"Field report received"` tone `'brand'`, source `'EPMP'`, actor `req.epmpUser!.id`, `detail: { observation_type, client_report_id }` — same transactional invariant every other incident-ops write follows. If `incident_id` is absent (a field report not tied to any specific incident is valid per the FRD), skip the Timeline write entirely — there is no incident to append to.

2. **`POST /api/v1/field-reports/sync-batch`** (`action='create'`) — processes `reports: FieldReport[]` **in the array's given order** (the client sends them in creation order per the TechArch note), sequentially (not `Promise.all` — order matters for the idempotency/conflict semantics below), accumulating `results: SyncBatchResult[]` one per input item:
   - For each report, first check idempotency exactly as the single-POST route does (`client_report_id` lookup) — if it already exists, push `{ client_report_id, status: existing.sync_status }` and move to the next item without re-inserting.
   - If new: **conflict detection** — if `incident_id` is present, check whether the referenced incident's `updated_at` (or, for a report whose `observation_type` affects a `task_status`-style record — out of this plan's exact scope per the FRD's `entity_type` generality, document inline that this plan's conflict detection covers the `field_report`-vs-`incident` case explicitly and treats any other `entity_type` as a documented extension point for a later plan if F4's task-status sync-batch reconciliation needs its own detection rule) was modified AFTER the report's `captured_at` timestamp — if so, this is a conflict: INSERT a `sync_conflicts` row with `entity_type: 'field_report'`, `entity_id` = the new field_reports row's id (insert the field_reports row FIRST with `sync_status: 'conflict'`, THEN the sync_conflicts row referencing it), `field_version: JSON.stringify(the incoming report body)`, `eoc_version: JSON.stringify({ incident_updated_at: incident.updated_at, incident_name: incident.name })` — both versions preserved exactly as submitted/as-found, neither discarded. Push `{ client_report_id, status: 'conflict', conflict_id: <sync_conflicts.id> }`.
   - If no conflict: INSERT the field_reports row with `sync_status: 'synced'`, `synced_at: now()`. If `incident_id` present, wrap this single item's INSERT in `withTimelineTransaction` and append `"Field report synced"` tone `'brand'`, source `'EPMP'`, actor `req.epmpUser!.id`, `detail: { observation_type, client_report_id, captured_at }` — THIS is the "appends a Timeline entry noting the sync" success criterion from the phase goal, fired once per synced item, not once per batch. Push `{ client_report_id, status: 'synced' }`.
   - On any unexpected per-item DB error (not a conflict — an actual failure), catch it, push `{ client_report_id, status: 'failed' }` for that item, and continue processing the REST of the batch — one failed item must never abort the whole batch (every item resolves to synced/conflict/failed, per the FRD's "queue never silently drops an item" hard requirement).
   - Return `200 { results }` always (the per-item statuses carry the outcome, not the HTTP status).

3. **`POST /api/v1/field-reports/{id}/photos`** (`action='create'`) — multipart upload via the locally-registered `@fastify/multipart` plugin. `req.file()` reads the one uploaded part; validate the `field_reports` row with `id` exists (404 if not — reuse the `INCIDENT_NOT_FOUND`-style pattern, naming it `FIELD_REPORT_NOT_FOUND`). On success, INSERT `field_report_photos (field_report_id, storage_ref, upload_status)` — since this phase has no object-storage adapter configured yet (TechArch doesn't specify one for Phase 5; deferred per the object-store I/O rule's own guidance that presigned URLs need the adapter TechArch doesn't name here), store the uploaded buffer's content under `upload_status: 'uploaded'` with `storage_ref` set to a locally-generated opaque key (`field-reports/{field_report_id}/{randomUUID()}.{ext}`) and persist the actual bytes to a local `backend/uploads/` directory (gitignored — add `uploads/` to `.gitignore` if not already present) read back by a same-origin `GET /api/v1/field-reports/{id}/photos/{photoId}` route this task ALSO adds, gated by the same `field_reports:view` permission, streaming the file back — never exposing a raw filesystem path or external URL to the client, consistent with the object-store I/O rule's "bytes go through your own API" requirement even though this is a local-disk stand-in rather than a real object store. Document inline: a later phase's real object-storage adapter (MinIO/S3) would replace this local-disk implementation behind the exact same two routes without any API contract change. On any write failure, catch and return `500 PHOTO_UPLOAD_FAILED` with message "This photo couldn't be saved. The rest of your report was submitted." — per the FRD's explicit "does not block the rest of the report" error semantics; the route returns `204` on success with no body.

Create `backend/src/modules/incident-ops/sync-conflicts.ts`:

4. **`GET /api/v1/sync-conflicts`** (`action='view'`) — lists unresolved conflicts (`WHERE resolution IS NULL`, using `idx_sync_conflicts_unresolved`), joined to `users` for a readable summary, paginated per the shared `page`/`page_size` convention. This is what "surfaced to a named person" renders against — a named person must be able to SEE the list of conflicts awaiting them.

5. **`POST /api/v1/sync-conflicts/{id}/resolve`** (`action='resolve'`, a distinct action-level from `view` — mirrors the no-single-role segregation pattern Phase 3's `plans`/`resource_requests` review/approve split established) — body `{ resolution: 'keep_mine' | 'keep_eoc' }`. Load the conflict row; 404 if not found or already resolved (`SYNC_CONFLICT_ALREADY_RESOLVED` if `resolution IS NOT NULL`, reusing the not-found code otherwise for a missing id). If `resolution='keep_mine'`: parse `field_version` JSONB and re-apply it as authoritative — for the `entity_type='field_report'` case this plan implements, that means `UPDATE field_reports SET sync_status='synced', synced_at=now() WHERE id=$entity_id` (the field version's content is already the field_reports row itself from Task 2's step 2, so "keep mine" just flips the status forward rather than re-writing fields that were never actually overwritten by anything — document this inline as the correct behavior for the field_report entity_type: the conflict was the DETECTION, not a competing write, so resolution is a status transition, not a data merge). If `resolution='keep_eoc'`: leave `field_reports.sync_status='failed'` (the field version is explicitly NOT applied — the EOC's existing state wins, and the field submission is marked failed rather than silently vanishing, so the responder can see it didn't take and resubmit if they disagree with this outcome). EITHER way: `UPDATE sync_conflicts SET resolution=$1, resolved_by=$2, resolved_at=now() WHERE id=$3`, and if the conflict's underlying field_reports row has a non-null `incident_id`, wrap in `withTimelineTransaction` and append a Timeline entry `"Field sync conflict resolved: {resolution}"` tone `'warning'`, source `'EPMP'`, actor `req.epmpUser!.id` — the resolution is ALWAYS visibly recorded, satisfying "never silently keeps one value and discards the other." Return `200` with the updated `sync_conflicts` row shape `{ id, entity_type, entity_id, resolution, resolved_by, resolved_at }`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | A field device's queued offline submissions (field_reports/sync-batch bodies, multipart photo bytes) crossing into the server, often hours after capture and outside the responder's direct control (auto-sync on reconnect) |
| db→render | `sync_conflicts.field_version`/`eoc_version` JSONB, captured verbatim from client input, later rendered back to the resolving user |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Tampering | `backend/src/modules/incident-ops/field-reports.ts` POST /field-reports, /sync-batch | mitigate | All INSERT/UPDATE statements use parameterized queries (`$1`/`$2`/...) via `pg`'s `query()`/`client.query()`, never string interpolation of request-body fields — same pattern every prior incident-ops route uses. |
