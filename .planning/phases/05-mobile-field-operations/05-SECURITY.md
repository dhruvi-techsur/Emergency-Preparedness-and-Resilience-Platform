# Security Report — Phase 5: Mobile Field Operations

**Mode:** verify (all 5 plans — 05-01 through 05-05 — carry a `<threat_model>` STRIDE register; T-05-01 through T-05-14 verified against the current code on disk, not against the plans' own claims)
**Audited:** 2026-11-18
**Verdict:** OPEN_THREATS
**Confirmed HIGH/CRITICAL:** 1

## Summary

All 14 declared threat-model entries were checked against the code as it exists after the review's 7 fix commits (`25f92ff`, `a3f0880`, `67bcb5c`, `6634781`, `6eda07c`, `5bc63c8`, `c7c86d4`). 13 of 14 are CONFIRMED — their claimed mitigations genuinely exist and still hold after the fix pass; none of B1/B2/B3's changed seams broke a mitigation another threat model depended on. One NEW vulnerability class, not anticipated by any of the 5 plans' own threat registers, was found and survives adversarial refutation: **field_reports/sync_conflicts carry no jurisdiction-scope enforcement at all** — every other incident-touching feature in this codebase (tasks, resource_requests, plans, incidents — see `03-SECURITY.md`'s F-01/F-02 findings from the prior phase) threads `req.epmpUser!.jurisdiction_scope` through its row-level queries; `field-reports.ts` and `sync-conflicts.ts` do not, for any of their 7 routes. Any authenticated holder of `field_reports:view`/`resolve` (which, per 05-05's seed, is `field_responder`, `incident_commander`, `eoc_director`, and `planning_logistics_chief` — i.e. most of the user base) can read, and in three of the four roles' cases also *resolve*, a field report or sync conflict belonging to ANY jurisdiction in the system, not just their own. This is a cross-jurisdiction IDOR, structurally identical in kind to Phase 3's F-01 that 03-SECURITY.md already fixed everywhere else — Phase 5 reintroduced the same gap in a new feature.

**Ship/no-ship: do not ship the jurisdiction-scope gap unmitigated** — it is live-exploitable by design (no crafted input needed beyond a valid UUID/conflict id) and grants cross-jurisdiction read+write (resolve) access to data the FRD's own jurisdiction model exists specifically to partition.

## Confirmed findings

### F-05-01: field_reports and sync_conflicts have no jurisdiction-scope enforcement — a user can read and resolve another jurisdiction's field reports and conflicts — HIGH
- **Category:** idor / authz_bypass (missing row-level tenancy check)
- **Location:** `backend/src/modules/incident-ops/field-reports.ts` (`GET /api/v1/field-reports/:id/photos/:photoId`, `POST /api/v1/field-reports/:id/photos`), `backend/src/modules/incident-ops/sync-conflicts.ts` (`GET /api/v1/sync-conflicts`, `GET /api/v1/sync-conflicts/:id`, `POST /api/v1/sync-conflicts/:id/resolve`)
- **Description:** Every route in both files is gated by `requirePermission('field_reports', <action>)`, which checks only the feature-level `role_id → {feature: [actions]}` grant via OPA — confirmed by reading the full 15-line `backend/opa/policy.rego`, which has no jurisdiction concept whatsoever (identical root cause to Phase 3's F-02, independently re-confirmed here against this phase's own OPA policy). None of the 7 routes join to `incidents`/filter by `jurisdiction_id = ANY($N)` the way every other incident-ops module does (`tasks.ts:197-198`, `resource-requests.ts`, `plans.ts`, `incidents.ts` — all confirmed to carry this exact pattern in `03-SECURITY.md`'s own audit trail). `sync-conflicts.ts`'s `GET /api/v1/sync-conflicts` lists ALL unresolved conflicts system-wide with no jurisdiction filter (`sync-conflicts.ts:61-76`); `GET /api/v1/sync-conflicts/:id` looks up any conflict by bare UUID with no scope check (`:94-114`); `POST /:id/resolve` likewise loads and mutates any conflict by bare UUID (`:131-137`). `field-reports.ts`'s photo GET/POST routes resolve `:id` to a `field_reports` row with no jurisdiction check either (`:330-333`, `:382-385`).
- **Exploit:** 05-05's seed grants `field_reports: ['view','resolve']` to `incident_commander` and `eoc_director`, and `['view','create','resolve']` to `field_responder` — none of these grants are jurisdiction-scoped anywhere in the authorization chain (OPA has no jurisdiction input; the route handlers never check `req.epmpUser!.jurisdiction_scope` against the conflict's/report's own incident). A field_responder or incident_commander whose `jurisdiction_scope` covers only Jurisdiction A can: (1) `GET /api/v1/sync-conflicts` and see every unresolved conflict system-wide, including ones tied to Jurisdiction B's incidents; (2) `GET /api/v1/sync-conflicts/{B's-conflict-id}` (trivially enumerable since the list route already handed out the id) and see Jurisdiction B's field-report content and the EOC's live incident metadata (`eoc_version.incident_name`, `incident_updated_at`); (3) for `field_responder`/`incident_commander`/`eoc_director` (who all hold `resolve`), `POST /api/v1/sync-conflicts/{B's-conflict-id}/resolve` with `{resolution:'keep_mine'|'keep_eoc'}` — committing a real state change (flipping `field_reports.sync_status`, appending a Timeline entry to Jurisdiction B's incident attributed to the Jurisdiction-A caller) on data outside the caller's authorized scope entirely. `field-reports.ts`'s photo routes have the identical gap: any `field_reports:view`/`create` holder can `GET`/`POST` a photo against any `field_reports.id` or `client_report_id` in the system regardless of jurisdiction, since the id-or-client_report_id lookup added by B1's fix (`field-reports.ts:330-333`) only disambiguates WHICH identifier shape matched — it adds no jurisdiction predicate at all.
- **Fix:** Thread `req.epmpUser!.jurisdiction_scope` through every route in both files, mirroring the exact pattern `tasks.ts`/`resource-requests.ts`/`plans.ts` already use: join `sync_conflicts` → `field_reports` → `incidents` and require `(incident_id IS NULL OR i.jurisdiction_id = ANY($N))` on the list/get/resolve routes (standalone field reports with no `incident_id` are, per the FRD, valid and have no jurisdiction to scope against — same "unfiltered when incident_id IS NULL" convention `tasks.ts:197` already established); apply the same join+filter to the photo GET/POST routes' `field_reports` lookup. Return the same 404-style `SYNC_CONFLICT_NOT_FOUND`/`FIELD_REPORT_NOT_FOUND` convention already used elsewhere in these files for an out-of-scope id, consistent with every other incident-ops module's not-found-not-403 pattern for scope violations.
- **Resolution:** fixed (`76d2f24`) — all 5 named routes (`sync-conflicts.ts`'s list/get/resolve, `field-reports.ts`'s photo GET/POST) now join `sync_conflicts`/`field_reports` → `incidents` and filter on `(incident_id IS NULL OR i.jurisdiction_id = ANY($N))`, returning the existing `SYNC_CONFLICT_NOT_FOUND`/`FIELD_REPORT_NOT_FOUND` 404 on an out-of-scope id (never 403), matching `tasks.ts`'s established pattern exactly. `field-reports.ts`'s `POST /field-reports` and `POST /field-reports/sync-batch` were independently re-verified and found exempt: both only ever INSERT new rows (never read/mutate an existing record by id), and `tasks.ts`'s own `POST /api/v1/tasks` create route establishes the same precedent of never jurisdiction-checking a caller-supplied `incident_id` on create — only read/mutate-by-id routes carry the scope check anywhere in this codebase. Verified via 9 new integration tests in `field-reports.test.ts` (out-of-scope 404 on list/get/resolve/photo-get/photo-post, plus in-scope regression checks for the same 5 routes) — all 16 tests in the file pass; full backend suite (`npm run test`) passes 86/86 across 15 files; `npx tsc --noEmit` clean.
