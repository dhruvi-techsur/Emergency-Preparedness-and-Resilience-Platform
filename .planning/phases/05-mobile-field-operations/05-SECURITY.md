## Resolved findings

### F-05-01: field_reports and sync_conflicts had no jurisdiction-scope enforcement — a user could read and resolve another jurisdiction's field reports and conflicts
- **Status:** Fixed — re-confirmed fixed and non-regressed as of this 2026-11-19 re-audit. (Note: the prior report cited fix commit `76d2f24`, which is no longer resolvable in this repository's current history — `git log --all` shows only `b29c7d5`→`42e7a49` — indicating the branch was rebased/squashed between audits. This re-audit therefore verified the fix by DIRECT CODE READ and a LIVE test run rather than by trusting the stale commit reference, per this audit's own adversarial standard of not accepting prior-report prose as evidence.)
- **Prior finding:** Every route in `field-reports.ts` (photo GET, photo POST) and `sync-conflicts.ts` (list, single-get, resolve) was gated only by `requirePermission('field_reports', <action>)`, a feature-level check with no jurisdiction concept (OPA's `policy.rego` has none). None of the 7 routes joined to `incidents`/filtered by `jurisdiction_id = ANY($N)` the way every other incident-ops module (`tasks.ts`, `resource-requests.ts`, `plans.ts`) does. A `field_responder`/`incident_commander`/`eoc_director` whose `jurisdiction_scope` covered only Jurisdiction A could list, read, and — for 3 of those 4 roles — resolve conflicts/photos belonging to Jurisdiction B's incidents, a cross-jurisdiction IDOR structurally identical to Phase 3's F-01/F-02.
- **Fix applied:** `field-reports.ts:337-344` (photo POST lookup), `field-reports.ts:396-403` (photo GET lookup), `sync-conflicts.ts:72-96` (list), `sync-conflicts.ts:119-141` (single-get), `sync-conflicts.ts:152-180` (resolve) — all 5 named routes now `LEFT JOIN incidents i ON i.id = fr.incident_id` (or the equivalent `sync_conflicts → field_reports → incidents` double join) and filter on `(incident_id IS NULL OR i.jurisdiction_id = ANY($N))`, returning the pre-existing `SYNC_CONFLICT_NOT_FOUND`/`FIELD_REPORT_NOT_FOUND` 404 (never 403) for an out-of-scope id — matching `tasks.ts`'s established not-found-not-403 convention exactly. `POST /field-reports` and `POST /field-reports/sync-batch` (create-only routes, never read/mutate an existing record by id) were confirmed exempt, matching `tasks.ts`'s own `POST /api/v1/tasks` precedent of not jurisdiction-checking a caller-supplied `incident_id` on create.
- **Verification (this audit, 2026-11-19):**
  - Re-read both implementation files in full (`field-reports.ts`, 428 lines; `sync-conflicts.ts`, 248 lines) — confirmed the join+filter pattern is present on all 5 named routes, byte-for-byte consistent with the prior report's description.
  - Ran `cd backend && npx vitest run src/modules/incident-ops/field-reports.test.ts` against the live Postgres+OPA compose stack (already running) — **16/16 tests pass**, including the dedicated `describe('F-05-01: jurisdiction-scope enforcement', ...)` block's 9 tests (5 OUT-OF-SCOPE 404 assertions across sync-conflicts list/get/resolve and field-report photo GET/POST; 4 IN-SCOPE regression assertions proving the same 5 routes still work correctly for the owning jurisdiction, including a full photo upload→read round-trip).
  - Ran the full backend suite (`npx vitest run`, no file filter) — **86/86 tests pass, 15 files, 0 failures** — identical totals to the prior audit's own reported numbers, confirming zero regression anywhere else in the codebase in the (empty) diff window between audits.
  - `git diff b29c7d5..HEAD --stat -- backend frontend` independently confirms no file has changed since the prior audit, so there is no code path by which this fix could have silently regressed.
