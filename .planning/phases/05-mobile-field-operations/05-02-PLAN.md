Create `frontend/app/src/lib/offline-queue.ts`. Schema (client-side, NOT TechArch-specified per the FRD's explicit "Schema Surface" note leaving this to implementation discretion):

```ts
export interface QueuedFieldReport {
  client_report_id: string;       // crypto.randomUUID(), generated at enqueue time — this IS the idempotency key 05-01's API matches on
  incident_id?: string;
  observation_type: string;
  description?: string;
  location?: { lat: number; lng: number };
  location_accuracy_m?: number;
  captured_at: string;            // ISO timestamp set at the MOMENT of local capture, never at sync time — FRD hard requirement
  queue_status: 'pending' | 'syncing' | 'synced' | 'conflict' | 'failed';
  conflict_id?: string;
  created_at: string;             // local enqueue timestamp, for Queued Submissions View's "Captured: ..." display
}

export type SyncStatusState = 'online' | 'syncing' | 'offline' | 'conflict';
export interface QueueSnapshot {
  state: SyncStatusState;
  queuedCount: number;            // count of queue_status==='pending' items — what SyncStatus's `detail` renders as "N queued"
  items: QueuedFieldReport[];
}
```

Open one IndexedDB database (`epmp-field-queue`, version 1) with one object store (`field_reports`, keyPath `client_report_id`) via `idb`'s `openDB`. Export:

1. **`enqueueFieldReport(report: Omit<QueuedFieldReport,'queue_status'|'created_at'>): Promise<void>`** — generates `created_at`, sets `queue_status:'pending'`, `put()`s into the object store IMMEDIATELY (before any network attempt) — this is the literal mechanism satisfying "every edit remains possible while offline" and "a queued submission shows Queued rather than appearing to fail": the write to IndexedDB happens synchronously-enough (same tick, awaited) regardless of `navigator.onLine`, so there is no code path where a submission is attempted over the network FIRST and only falls back to the queue on failure — it is ALWAYS queue-first, then synced opportunistically. After enqueueing, call `notifySubscribers()` (below) and, if `navigator.onLine`, kick off `syncQueueNow()` (fire-and-forget, not awaited by the caller) so an online submission still gets a near-immediate best-effort sync without blocking the caller's own "queued successfully" return.

2. **`getQueueSnapshot(): Promise<QueueSnapshot>`** — reads all rows, computes `state` as: `'conflict'` if any row has `queue_status==='conflict'`; else `'syncing'` if a sync is currently in flight (module-level `let syncInFlight = false` flag); else `'offline'` if `!navigator.onLine`; else `'online'`. This single derivation is what every screen's `SyncStatus` state prop reads — no screen computes connectivity itself.

3. **`subscribeToQueue(cb: (snapshot: QueueSnapshot) => void): () => void`** — maintains a module-level `Set<callback>`; calls `cb` immediately with the current snapshot, then on every subsequent queue mutation or `online`/`offline` window event; returns an unsubscribe function. This is what `AppShell`/field-mobile screens use in 05-03/05-04 to drive `SyncStatus` without each independently polling IndexedDB or attaching its own `window.addEventListener('online', ...)`.

4. **`syncQueueNow(): Promise<void>`** — reads all `queue_status==='pending'` rows IN THE ORDER they were enqueued (IndexedDB's keyPath iteration is insertion-order by default for a non-indexed cursor walk; if ordering needs to be explicit, sort by `created_at` ascending before sending — document inline whichever is used), sets `syncInFlight=true` + notifies subscribers (so `SyncStatus` flips to `syncing` immediately), POSTs `{ reports: [...] }` to `/api/v1/field-reports/sync-batch` via `apiPost` from `../lib/api-client` (reuse the EXISTING `apiPost` helper rather than a raw `fetch` — same auth-header/401-handling convention every other frontend API call follows), then for each item in the response's `results` array (matched back to the local row by `client_report_id`), `put()`s the row with the matching `queue_status` ('synced'/'conflict'/'failed') and `conflict_id` if present. Sets `syncInFlight=false`, notifies subscribers again. Wrapped in try/catch — a network failure (not a per-item failure, a totally failed request) leaves every attempted item's `queue_status` unchanged at `'pending'` (NOT marked `'failed'` — a network-level failure is retried on the next reconnect, not given up on) and logs via `console.warn`, never throwing uncaught.

At module load time, attach `window.addEventListener('online', () => { void syncQueueNow(); })` once — this is the "no manual upload step required" mechanism: the moment the browser's own connectivity detection fires `online`, a sync attempt starts automatically, with no user action.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client-local-storage→API | Data captured and persisted entirely client-side (IndexedDB) while offline, later transmitted to the server with no server-side validation having occurred at capture time |
| service-worker-cache→render | Cached API responses served back to the UI when offline, potentially stale |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-06 | Tampering | `frontend/app/src/lib/offline-queue.ts` IndexedDB rows, browser-devtools-editable before sync | accept | IndexedDB content is inherently editable by anyone with device/devtools access to the browser profile — this is a property of client-side storage, not a bug in this plan. The server-side (05-01) still re-validates every field on sync (REPORT_EMPTY check, jurisdiction-scope check on `incident_id`), so a tampered local queue entry cannot bypass server-side validation; it can only submit a plausible-but-false report, which is a data-integrity/trust-of-the-field-responder concern outside this plan's threat surface, not a security vulnerability in the offline-queue mechanism itself. |
| T-05-07 | Information disclosure | `frontend/app/vite.config.ts` VitePWA runtimeCaching of `/api/v1/(tasks|me)` | mitigate | The service-worker's `NetworkFirst` cache is scoped to the SAME origin and the SAME auth-cookie/header-bearing requests the app already makes — it caches responses the user's own session already successfully fetched, not a bypass of `requirePermission`. No caching rule is added for any route outside `tasks`/`me`, keeping the cached surface minimal and matching exactly what the field-mobile screens need available offline. |
| T-05-08 | Denial of service | `frontend/app/src/lib/offline-queue.ts` unbounded IndexedDB growth | accept | No queue-size cap is enforced client-side in this plan (the FRD's `507 QUEUE_STORAGE_FULL` error is documented as a "client-side guard" the TechArch API contract anticipates but does not mandate a specific threshold for). Owner: 05-03/05-04's Report Observation screen is the natural place to add a storage-quota check (`navigator.storage.estimate()`) before enqueueing and surface `507`-equivalent UI if ever needed — documented here as a known, intentionally deferred gap, not an oversight. |
</threat_model>
