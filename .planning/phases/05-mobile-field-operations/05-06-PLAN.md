**UAT-8 (blocker) + UAT-1 (major) — SAME underlying nav-config mechanism, TWO
distinct symptoms, ONE closure:**

- UAT-8: `AppShell.tsx:91`'s `flatItems = navGroups.flatMap((g) => g.items)`
  flattens EVERY nav group (in the backend's fixed emission order
  Prepare→Monitor→Activate→Coordinate→Improve→Field→Admin) before handing the
  first 4 to the mobile bottom-bar. A real field_responder holds broad
  Phase-1-4 view-only grants (plans/incidents/tasks/resource_requests/
  notifications/reporting — seeded for legitimate situational-awareness
  reasons), so 5 groups populate before the Field group's own items ever
  appear at index 9. The bottom bar renders "Plans & playbooks / Operating
  picture / Incidents / Tasks" instead of the Field group's own items.

- UAT-1: independently, on desktop/tablet (where the rail SideNav renders the
  Field group correctly and in isolation — NOT affected by UAT-8's flattening
  bug), the Field group's 4th item is labeled "Profile" but routes to `/field`
  (Field Home — the screen with the task list AND the sticky Report button
  together). A user looking for "today's tasks + Report button" naturally
  clicks "My Tasks" first (which routes to the narrower, Report-button-less
  `/field/tasks`), and never discovers that the unrelated-sounding "Profile"
  label is the actual combined landing screen.

Fix: give `nav_groups` a stable, machine-readable `id` per group (not just the
existing display `label`) so a consumer can reliably target "the Field group"
regardless of emission order or label wording — this closes UAT-8. Relabel the
Field group's 4th item away from "Profile" to something that signals it is the
tasks+Report landing screen — this closes UAT-1. Both fixes land in the SAME
`nav_groups` construction this plan already touches for the `id` addition, so
one plan closes both gaps with no duplicated nav-rendering work.

Purpose: a field_responder's phone-sized device must show the correct 4
field-mobile destinations in the bottom bar (the ONLY nav surface available
below `bp-md`, since `AppShell.tsx` renders no rail SideNav there at all) —
right now the field-mobile UI (05-01 through 05-05's entire deliverable) is
structurally unreachable on an actual field-responder's real permission set
on mobile, which is this platform's primary device for this persona.

Output: `nav_groups[].id` field (backend + SideNavGroup type), AppShell's
bottom-bar selection logic rewritten to target the Field group specifically,
Field group's 4th item relabeled, plus regression coverage proving every
other role's nav-config/rendered-nav output is unchanged.
