- timestamp: 2026-11-16T18:50:00Z

  found: This doc explicitly documents this EXACT class of bug under "Login and SSO redirects, OAuth/OIDC callbacks and issuers... all depend on it [the forwarded-header-derived origin]" and separately spells out a concrete, already-proven fix pattern for "Identity providers" in general (not just cert-based ones) that sit on their own origin inside the sandbox: (1) proxy the IdP's browser-facing paths through the frontend's own dev server same-origin, (2) configure the IdP itself to trust forwarded headers and not pin its own hostname (Keycloak-specific: `KC_PROXY_HEADERS=xforwarded`, no `KC_HOSTNAME`, `KC_HOSTNAME_STRICT=false`, `KC_HTTP_ENABLED=true`), (3) accept the per-request forwarded-header-derived issuer on the backend's JWKS/token-validation side alongside the configured internal one. The doc frames this profile as mandatory specifically for client-cert IdPs because "trust the forwarded headers" alone can't carry a TLS client cert through the preview proxy — but the underlying mechanism (proxy + KC_PROXY_HEADERS + per-request issuer) is exactly the general-purpose fix for ANY same-origin-incapable IdP running on its own port inside the sandbox, username/password or not. This EPMP realm uses password-based seeded test users (confirmed by 01-10-PLAN.md's Playwright test credentials `admin@epmp.local`/`devpass123`), so the simpler of the two paths applies: no client-cert complication, but the same same-origin proxy + KC_PROXY_HEADERS + per-request-issuer mechanism is still required, because Keycloak itself is on a separate port the browser cannot reach directly.
  implication: This is not a novel problem needing an invented fix — the framework's own reference doc already prescribes the viable solution shape for this exact scenario. No sandbox-profile compose override implementing this pattern currently exists in this repo (confirmed by the `find` in the prior evidence entry), which is itself part of the root cause: Phase 1's 01-10 plan built the OIDC client assuming direct sandbox-internal reachability and never implemented the same-origin IdP proxy pattern this architecture requires.

## Resolution

root_cause: "frontend/app/src/auth/oidc-config.ts:20 hardcodes `KEYCLOAK_AUTHORITY = 'http://localhost:8081/realms/epmp'`, which oidc-client-ts's `signinRedirect()` uses to build a full top-level browser navigation to Keycloak's `/protocol/openid-connect/auth` endpoint. Independently reproduced: Vite serves this literal string unchanged to any requesting browser (confirmed via direct curl of the dev-served module), Keycloak itself is healthy and correctly serving the epmp realm at 127.0.0.1:8081 INSIDE the sandbox (confirmed via its own OIDC discovery document), and `.pivota/start-dev.sh` now correctly routes a preview session to the real SPA on port 5173 (ruling out the earlier, unrelated, already-resolved port-routing bug as a contributing factor here). The defect is specifically that 'localhost:8081' is sandbox-internal-only addressing — reachable from server-side code and from a browser running physically inside the sandbox, but NOT from the human tester's actual browser, which reaches the app only through Pivota's port-7777 preview proxy to a public preview URL. When that browser executes `signinRedirect()`, 'localhost:8081' resolves to the human's own machine, which has nothing listening on that port — the navigation goes nowhere renderable, which is indistinguishable, from the human's perspective, from 'no login option exists at all.' This is confirmed as a genuine code defect (not an environment/infra gap) by the asymmetry within the SAME file: `redirect_uri` on line 26 already correctly derives from `window.location.origin` at call time — proving the author knew and used the correct browser-safe pattern for one URL but not the other. Compounding the defect: Keycloak itself (docker-compose.yml) has no `KC_PROXY_HEADERS`/forwarded-header trust configured, so even a same-origin-proxied request would still receive Keycloak-authored HTML/redirects pointing back at the internal 127.0.0.1:8081 address; and the realm's registered `redirectUris` (`backend/keycloak/epmp-realm.json`) only allow-list sandbox-internal addresses (localhost:5173, localhost:8080), not a preview-host-derived pattern. No sandbox-only compose profile or Vite proxy route for Keycloak's browser-facing paths (`/realms`, `/resources`, `/js`) exists anywhere in the repo — runtime-environment.md §9 documents exactly this class of problem and its fix pattern (same-origin IdP proxy + forwarded-header-aware IdP config + backend accepting a per-request forwarded issuer alongside the configured one), but Phase 1's 01-10 plan never implemented it, having built the OIDC client to assume direct sandbox-internal reachability that only ever holds for sandbox-internal test tooling (e.g. Playwright run from inside the sandbox), never for Pivota's actual human Preview-panel users."
